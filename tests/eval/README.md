# Eval-датасет: сравнение vision-моделей

Полная спецификация — `docs/05_implementation/llm-eval-dataset.md` (SSOT). Этот файл — только "как добавить кейс".

Не путать с `eval/nutrition/` в корне репо — это другой, отдельный (пока не принятый к скаффолду) харнесс по `docs/04_specs/spec-nutrition-eval.md`, с другой схемой ярусов.

## Структура

- `manifest.yaml` — SSOT: кейсы + эталоны + разметка. Схема — в шапке файла.
- `images/` — фото, имя `<id>_<trap>.jpg` (например `A-01_kj-only.jpg`).
- `runs/` — сюда раннер (`run_eval.py`) кладёт сырые ответы, usage/латентность и отчёты (`<дата>_<модель>.json`, `<дата>_report.md`).

## Как прогнать раннер

Раннер — НЕ pytest (делает живые сетевые вызовы). Гоняет ярус A через тот же путь,
что прод (`LLMExtractor`), меняя лишь цель (провайдер/модель) — ADR-0017 §6.

```
# дефолт = прод-цель (openai / gpt-5.4-mini), из корня репо в активном .venv:
python -m tests.eval.run_eval run
python -m tests.eval.run_eval run --provider openai     --model gpt-5.4
python -m tests.eval.run_eval run --provider openrouter --model <любая> --limit 5   # быстрая проба

# свести все runs/*.json в markdown-таблицу:
python -m tests.eval.run_eval report
```

**Дефолт раннера обязан совпадать с прод-целью** (`app/config.py`: `llm_base_url`,
`llm_vision_model`, `llm_max_images`, `llm_max_tokens_param`, `llm_reasoning_effort`).
Это не удобство, а предусловие ТЗ контракта §0.1: пока прод и раннер смотрят в разные
модели, промпт настраивается вслепую. Сходимость проверяет
`test_manifest.py::test_eval_default_matches_prod_target` — расхождение красит pytest.

Провайдеры и ключи — `PROVIDERS` в `run_eval.py`, ключи берутся из `settings`
(`.env`: `OPENAI_API_KEY` / `OPENROUTER_API_KEY` / `CLAUDE_API_KEY`; прод-путь ходит
по отдельному `LLM_API_KEY`). Раннер повторяет клиентское сжатие фото прода (длинная
сторона ≤1280, JPEG q82) — иначе кормит модель не тем, что видит прод, и упирается
в 413 на больших PNG.

## Тесты датасета (обычный pytest, без сети)

- `test_manifest.py` — целостность манифеста (§3D.5): схема по ярусам, дубли ID,
  файлы-сироты и записи-сироты, Атуотер по эталонам A, связность C→A, пригодность
  ингредиентов C, поля яруса B.
- `test_scoring.py` — негативные контроли метрик (§3D.1): 17 синтетических мутантов,
  каждый обязан быть забракован. **Метрика без негативного контроля не считается
  введённой** — это правило, а не пожелание.

```
pytest tests/eval -q
```

**Free-тир OpenRouter (`:free`) ненадёжен для сплошного прогона:** модели отдают
`429 "temporarily rate-limited upstream"` при насыщении общего пула (не личный лимит,
не бюджет). Гонять с `--sleep 5+`, принимать частичные результаты, повторять позже.

## Как добавить кейс (сейчас — ярус A, этикетки)

1. Фото этикетки → `images/<id>_<trap>.jpg`.
2. Эталон (цифры с упаковки, как есть) → запись в `manifest.yaml`.
3. Если тестовое фото намеренно плохо читается (блик, мятая упаковка — категория `glare-crumpled`) — эталон берётся не с него: либо отдельное чистое фото того же продукта, либо цифры называются напрямую. Обратное — эталон, списанный с нечитаемого кадра, — самообман: ошибка чтения станет частью "истины" и будет засчитана модели как её собственная ошибка.
4. Двойная проверка: числа в `ground_truth` — то, что напечатано на упаковке, не то, что скажет модель при прогоне.

## Как добавить кейс яруса B (тарелки)

Дизайн — `llm-eval-dataset.md` §3B. Коротко:

1. **В кадре не должно быть читаемой таблицы пищевой ценности или узнаваемой упаковки** — иначе `readout="label"` становится законным ответом и метрика B2 обессмысливается. Фиксируется полем `package_in_frame: false`.
2. Кадрирование: тарелка и стол. Без лиц, без узнаваемого интерьера, без документов и экранов. Приватность репозитория — обратимая настройка, содержимое кадра — нет.
3. Для взвешенных кейсов (`subset: B-w`) — протокол тарирования: тарелка на весы, tare, компонент, запись, tare, следующий. **Взвешивается состояние «как подано»** (гречка — варёная), и `per100g` берётся для того же состояния: сырое и варёное различаются втрое, это главный способ незаметно испортить эталон.
4. Источник `per100g` компонента записывается всегда: `case: A-NN` (товар есть в ярусе A, истина напечатана) либо `ref_source: "<справочник, позиция>"`. Эталон без записанного источника неаудируем.
5. Разметка состава — с `synonyms`, иначе сопоставление меряет лексику, а не сегментацию.

## Как добавить набор яруса C (составное блюдо)

Дизайн — `llm-eval-dataset.md` §3C. **Снимать ничего не нужно** — наборы «бумажные»: ингредиенты берутся из уже отснятых кейсов яруса A по ссылке `case:`, граммовки объявляются, блюдо не готовится.

- `expected_total` и хранится в манифесте, и пересчитывается тестом из текущих записей A. Расхождение = кто-то поправил эталон A и не заметил, что истина набора C уехала.
- Один набор обязан иметь фото больше `llm_max_images` (батчи), один — повторный кадр того же товара в другом батче (дедуп), один — заявленный вес, не сходящийся с Σ граммовок (положительный контроль C6), остальные — сходящийся (отрицательный контроль).
- У каждого ингредиента обязателен `text_name` — формулировка для режима `dish_text`. Имя с этикетки для этого не годится: оно не сообщает состояние продукта (сухой/варёный), а модель по умолчанию отдаёт `per100g` варёных — метрика C9 запишет верное поведение как промах втрое.
- **Формула C6 — из ТЗ контракта §6.4:** `|Σ граммовок − declared_weight_g| / declared_weight_g > 0.30`. Знаменатель — **заявленный вес**, не Σ. На C-05 разница решающая: от Σ выходит ровно 30.0% и строгое `>` не срабатывает, то есть положительный контроль умирает молча. Пин формулы — `test_scoring.py::test_c6_denominator_is_declared_weight_not_sum`.

### История яруса A

Ярус A закрыт (2026-07-25): 28 кейсов. clean/dual-table/small-font-ru/glare-crumpled перекрыты с запасом; per-portion и composite-product — по 1/2; kj-only — 0/3. Дефицит осознанный (редкие паттерны для этого домохозяйства — см. `llm-eval-dataset.md` §9), не недобор.

Раннер (`run_eval.py`) реализован (2026-07-25). Замер 12 моделей выполнен и закрыт 2026-07-27: победитель — `gpt-5.4-mini` (92% kcal-hit ≤2%, 83% БЖУ, 1.3 с, $0.41/мес), ADR-0017 принят. Сырьё и отчёты — `runs/`; прогоны до исправления рассинхрона — `runs/_pre-fix-2026-07-27/`.

> ⚠ **Условие сопоставимости с baseline.** Прогоны `gpt-5.4-mini` и `gpt-5.4` от 2026-07-27 сделаны с ЯВНО переданным `reasoning_effort="none"` (видно в поле `reasoning_effort` файлов прогона). ТЗ контракта §10 предписывает `llm_reasoning_effort = ""` — параметр не передавать вовсе. Это разные конфигурации вызова, и первый регресс-прогон волны 1 сравнивается с baseline, снятым при другой. Разрешается одним из двух способов: пере-снять baseline `gpt-5.4-mini` при `""` (один прогон, ~$0.02) либо вернуть в §10 значение `"none"`. Решение — за С.
