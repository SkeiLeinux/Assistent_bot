# `tests/eval/runs/` — артефакты РАННЕРА eval

Здесь и только здесь лежат прогоны `python -m tests.eval.run_eval run` и сводки
`… report`. Форма файла фиксирована: `provider`, `model`, `records` и остальное,
что читает `build_report` (список — `run_eval._RUN_REQUIRED_KEYS`).

## Чужим файлам здесь не место

Замеры источника (`scripts/check_off_*.py`) писали свои артефакты сюда же, и
сводка раннера дважды падала на них `KeyError` — один посторонний файл делал
недоступной сводку по ВСЕМ прогонам, то есть блокировал приёмку. С блока 13
(2026-08-03) их каталог — `tests/eval/probes/`; уже снятые артефакты замеров
перемещены туда же.

## Тег версии промпта в имени файла

**С 2026-08-03 версия промпта пишется в имя файла всегда** — `…_p-v3.json`.
Раньше тег ставился только для не-дефолтной версии, поэтому:

Внутри JSON версия лежит в поле `prompt_version` — оно и есть первоисточник;
имя файла его лишь повторяет, чтобы прогоны различались, не открывая каждый.

| файл | на какой версии снят |
|---|---|
| `2026-07-27_*.json` | v1 (`label_complete`, до волны 1). Поля `prompt_version` в них ещё нет — версия выводится из даты, отсюда и правило «тег всегда» |
| `2026-08-01_gpt-5.4-mini_p-v1.json` | v1 — тег есть, версия была не дефолтной |
| `2026-08-01_gpt-5.4-mini.json`, `…_v2-run1.json`, `2026-08-01_*_tierC_*.json` | **v2** (дефолт на тот момент) |
| `2026-08-03_gpt-5.4-mini_p-v2.json` | v2 — сравнительная рука регресса блока 11 |
| `2026-08-03_gpt-5.4-mini.json` | **v3** (дефолт на тот момент) |

Переименовывать снятое не стали намеренно: файлы поимённо названы в отчётах
(`llm-eval-results-2026-07-27.md`, `wave1-block11-c3a-secrets-2026-08-03.md`), и
переименование рассинхронизировало бы отчёты с диском — тот самый механизм,
которым в проекте уже рождался рассинхрон «фото ↔ эталон». Эта таблица и есть
недостающая привязка.

`_pre-fix-2026-07-27/` — прогоны до исправления рассинхрона фото↔эталон
(11 кейсов, `llm-eval-dataset.md` §7a). Их метрики недостоверны, они сохранены
как история, а не как baseline.
