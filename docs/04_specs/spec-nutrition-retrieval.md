## 0. Что меняем в одном абзаце

Сейчас `/analyze` одним LLM-вызовом сегментирует ввод на продукты и для каждого даёт **оценку** КБЖУ (`_SYSTEM_PROMPT`, `items[]`). Числа модель берёт «из головы» — для брендовых продуктов неточно. Инкремент R сохраняет сегментацию и один LLM-вызов, но (а) расширяет извлечение полями идентификации (`brand/fat_pct/portion_g/barcode/label_complete`) и просит **per100g на 100 г** для каждой позиции, (б) вставляет **резолвер**, который для каждой позиции пытается заменить оценку на **точные данные из Open Food Facts** (а в R2 — из веба). Источник каждой позиции фиксируется в **провенансе** (`label`/`off`/`estimate`). Инвариант `analyze → confirm → save` (I5) сохраняется; найденное кэшируется в `SharedFood` при сохранении.

**Ключевой факт (комментарием в коде):** LLM сам не ищет в интернете. Retrieval — отдельные адаптеры (OFF; в R2 — Groq Compound). `llama-4-scout` используется для сегментации/извлечения (и в R2 — для парса веб-выдачи). «estimate» — это per100g, которое извлекатель уже вернул; **отдельного LLM-вызова на оценку нет**.

## 1. Целевое поведение

`/analyze` возвращает **список** позиций; резолвер применяется к каждой. Примеры:

| Кейс | Вход | Поведение |
|---|---|---|
| **1a. Текст, 1 продукт** | «200гр молоко Домик в деревне 3.2%» | 1 позиция: извлечь `{name,brand,fat_pct,portion_g, per100g(оценка), label_complete=false}` → OFF по `brand+name+fat` → нашли: per100g из OFF × 200/100, `source=off`; не нашли → оценка, `source=estimate`. |
| **1b. Текст, N продуктов** | «гречка 200, курица 150» | 2 позиции (сегментация в одном LLM-вызове). Каждая резолвится отдельно: «гречка»→OFF/estimate, «курица»→OFF/estimate. `test_text_input` сохраняется. |
| **2. Фото этикетки + «200г»** | изображение + portion | Обычно 1 позиция. Если этикетка читается на 100% → `per100g` точные с этикетки, `label_complete=true`, `source=label`. Иначе → OFF по названию → estimate. *(barcode — fast-follow, §16.)* |
| **3. Фото продукта / тарелки** | изображение | 1..N позиций. У каждой: `label_complete=true` (если своя этикетка видна) → label; иначе → OFF → estimate. |

Во всех случаях — существующий **confirm-экран** (список позиций; у каждой бейдж источника; правка работает), затем save.

## 2. Архитектура

Новый изолированный подпакет `app/contexts/nutrition/resolve/` (границы — ADR-0004; import-linter: `resolve` зависит от `services`/`models`, не наоборот; delivery — только через `FoodService`).

```
nutrition/
  resolve/
    __init__.py
    ports.py          # Protocol ProductResolver, NutritionSource; DTO ExtractedItem, ResolveQuery, ResolvedNutrition, Macros
    pipeline.py       # ResolverPipeline.refine(item) — лестница на ОДНУ позицию
    extractor.py      # LLM-сегментация+извлечение (vision/text) → list[ExtractedItem]   (1 вызов)
    sources/
      __init__.py
      openfoodfacts.py  # OpenFoodFactsSource (адаптер)
      estimate.py       # EstimateSource — возвращает per100g из самого item (БЕЗ LLM-вызова)
      # compound_web.py — добавляется в R2
    errors.py
    cache.py          # нормализация ключа; синергия со SharedFood — в FoodService
```

- **`NutritionSource`** — контракт ступени: `async def lookup(q: ResolveQuery) -> ResolvedNutrition | None`. Каждый источник — адаптер (как ACL, ADR-0002): добавить/сменить = новый адаптер (так R2-web встанет без правки лестницы).
- **`ProductResolver.refine(item: ExtractedItem) -> ResolvedNutrition`** (реализует `ResolverPipeline`): прогоняет ступени для ОДНОЙ позиции, первый успех — победитель; в пределе — `estimate` (per100g из item).
- **`extractor.extract(text|image) -> list[ExtractedItem]`** — один LLM-вызов сегментирует ввод и заполняет каждую позицию (§6).
- `FoodService` получает `ProductResolver` инъекцией (дефолт — реальный pipeline; тесты инжектят фейк — живых вызовов из pytest нет).
- Контракт `NutritionLLM` сохраняется (его использует `extractor`).
- **`/foods/analyze` резолвер НЕ использует** — остаётся текущий расчёт по составу (`_DISH_PROMPT`/`_COMBINED_PROMPT`), `source=estimate`.

## 3. Конвейер (точная последовательность)

```
# /analyze (дневник) — мульти-продукт
items = extractor.extract(text | image)        # 1 LLM-вызов → list[ExtractedItem]
out = []
for it in items:                               # резолв КАЖДОЙ позиции
    r = resolver.refine(it)                     # лестница §4 → ResolvedNutrition(+source)
    out.append(scale(r.per100g, it.portion_g) + {source, source_ref, matched_name})
return {"items": out}                           # БЕЗ сохранения (I5)
confirm (UI, список) → user правит/подтверждает
save_entries(items) → INSERT FoodEntry(+source,+source_ref) ×N
    → для позиций с source ∈ {label, off, web}: upsert SharedFood (кэш, §11)

# /foods/analyze (каталог) — одно блюдо, БЕЗ резолвера
result = current_dish_calc(name, weight, text?, images?)   # как сейчас
return {... , source: "estimate"}
```

Псевдокод refine одной позиции:

```python
async def refine(self, it: ExtractedItem) -> ResolvedNutrition:
    if it.label_complete:                       # этикетка прочитана — поиск не нужен
        return ResolvedNutrition(it.per100g, source="label", confidence=it.confidence)
    q = it.to_query()                           # name/brand/fat/barcode + fallback per100g (=it.per100g)
    for source in self.network_sources:         # R1: [OFF]   (R2: [OFF, CompoundWeb])
        try:
            r = await asyncio.wait_for(source.lookup(q), source.timeout_s)
        except (TimeoutError, SourceError) as e:
            log.warning("source %s failed: %s", source.name, e); continue
        if r is not None:
            return r
    return ResolvedNutrition(it.per100g, source="estimate", confidence=it.confidence)  # fallback = оценка extractor
```

Латентность: на ввод из N позиций — **1 LLM-вызов** + до N сетевых запросов (только не-`label` позиции). OFF-запросы выполнять с уважением к лимиту (≤10/мин): последовательно или семафором ≤2–3. Общий мягкий бюджет `resolver_total_budget_s` на весь ввод; если вышел — оставшиеся позиции отдаём как `estimate` (числа уже есть, без сети). Кэш (SharedFood) гасит повторные.

## 4. Лестница фолбэков (на ОДНУ позицию)

> **Дельта v0.6 (2026-07-28).** Пункты 1–3 переработаны: label больше не коротит лестницу безусловно (ревизия ADR-0013 + гейт уверенности), barcode поднят из fast-follow в основную ветку, матчинг заменён (ADR-0019).

1. **label-preferred** — `readout="label"` и проверки §6 ТЗ-контракта пройдены → числа с этикетки становятся основными. Но при наличии `brand` и бюджета лестница **всё равно опрашивается** для сверки; расхождение >`resolver_disagree_pct` показывается пользователю обеими версиями. Сверка применяется только при `match_confidence ∈ {exact, confirmed}` (`spec-nutrition-llm-contract.md` §7.1a).
2. **barcode** — `item.barcode` прошёл C4.0 (контрольная сумма EAN, префикс не внутримагазинный) → точный lookup по коду. Ранжирования нет → `match_confidence="exact"`. Покрывает 16% позиций.
3. ~~**OFF поиск + переранжирование**~~ — **удалена 2026-08-03** (вариант D, ADR-0019 ревизия 2026-08-03). Замер `off-value-2026-08-03.md`: на ветке `estimate` выбранная поиском карточка проигрывает типовым числам модели 7:13 при 11 грубых промахах из 25 (515 %, 461 %, 381 %). Ступень не уточняла, а подменяла продукт. Поисковый запрос к OFF не выполняется ни в какой ветке; из источника остаётся только п. 2.
   *Что при этом верно и не отменяется:* данные в базе хорошие — там, где карточка проходит подпись по имени (10 кейсов из 25), лучшая ошибается на 0,6 %. Непригоден **поиск**, а не источник; поэтому lookup по коду и остаётся.
4. **estimate** — per100g из самого `ExtractedItem`, `source=estimate`. Всегда успешна — гарантия ответа. Исключение: `readout="unreadable"` (чисел нет) → позиция уходит в `unresolved` (`spec-nutrition-llm-contract.md` §6.6).

> Ступень **web** встаёт между 3 и 4 в **R2** (§8, §16).

Деградация: пустой/таймаут/ошибка/**неуверенный матч** → лог `warning` + следующая ступень. Неуверенный матч приравнивается к отсутствию результата — это и есть реализация обещания «лучше не найдено, чем не тот продукт».

## 5. DTO-схемы (pydantic; `resolve/ports.py`)

```python
class Macros(BaseModel):
    kcal: float; protein: float; fat: float; carbs: float   # на 100 г

class ExtractedItem(BaseModel):
    name: str                      # «молоко питьевое»
    brand: str | None = None       # «Домик в деревне»
    fat_pct: float | None = None   # 3.2 (дискриминатор молочки)
    portion_g: float | None = None # масса этой порции; None если не указана
    barcode: str | None = None     # EAN, fast-follow
    per100g: Macros                # ВСЕГДА заполнено: с этикетки (label_complete) или оценка модели
    label_complete: bool = False   # этикетка прочитана на 100% → per100g точные
    confidence: float = 0.0

class ExtractResult(BaseModel):
    items: list[ExtractedItem]     # JSON-режим требует объект сверху

class ResolveQuery(BaseModel):     # вход ступени-источника
    name: str; brand: str | None; fat_pct: float | None; barcode: str | None
    fallback_per100g: Macros       # = ExtractedItem.per100g (для EstimateSource)

class ResolvedNutrition(BaseModel):
    per100g: Macros
    source: Literal["label","off","web","nutritionix","estimate"]   # web/nutritionix — R2/позже
    source_ref: str | None = None   # URL/код товара/цитата (off/web)
    matched_name: str | None = None # как назван матч в источнике
    confidence: float = 0.0
```

Масштаб на порцию — в `FoodService`: `value = per100g.* * portion_g/100`, округление как в текущем коде (kcal→1 знак). `NutritionItem` (существующий) += `source: str`, `source_ref: str | None`.

**Опция C (С., 2026-06-14) — пересчёт на confirm при правке веса.** `/analyze` отдаёт на каждой позиции ещё и `per100g` (транспорт, не персистится); confirm-экран пересчитывает КБЖУ при изменении веса. Это закрывает прежний edge `portion_g=None`: начально числа = per100g, вес пуст; ввод веса даёт корректный масштаб. `NutritionItem` += `kcal_100g/protein_100g/fat_100g/carbs_100g` (транспорт).

Валидация: `name` непустой; числа `≥ 0`; невалидный ответ источника → «не найдено» (None), не краш.

## 6. Извлечение (`extractor.py`) — сегментация + идентификация (1 LLM-вызов)

Один извлекатель, два входа (текст / изображение), выход — `list[ExtractedItem]` (строгий JSON). Использует `NutritionLLM` (Scout). Для фото — vision-часть; для текста — текстовая. Заменяет нынешний прямой `_SYSTEM_PROMPT`-путь в `/analyze`.

> **Фронт:** мультифото-аплоадер уже на проде (#2) — фото-ветка переиспользует, заново не делает.

**Промпт извлечения (system) — дословно, целевой:**

```
Ты — парсер дневника питания. Раздели запрос (текст и/или фото) на ОТДЕЛЬНЫЕ продукты/блюда и для КАЖДОГО верни запись.
Верни СТРОГО JSON-объект:
{"items": [ {"name":"<родовое название без бренда, рус.>","brand":<строка|null>,"fat_pct":<число|null>,"portion_g":<число|null>,"barcode":<строка цифр|null>,"per100g":{"kcal":<ч>,"protein":<ч>,"fat":<ч>,"carbs":<ч>},"label_complete":<true|false>,"confidence":<0..1>}, ... ]}
Правила:
- Одна запись на каждый отдельный продукт/блюдо. Пример: «гречка 200, курица 150» → ДВЕ записи.
- per100g — ВСЕГДА заполни, значения на 100 г: если на фото читается этикетка — точные значения с неё и label_complete=true; иначе — твоя оценка и label_complete=false.
- name — без бренда и жирности («молоко питьевое»); brand — отдельно («Домик в деревне»); fat_pct — если указан.
- portion_g — масса именно этой порции, если понятна из запроса; иначе null.
- barcode — только если цифры штрихкода явно видны; иначе null.
- Числа без единиц. Никакого текста вне JSON.
```

> Для текста модель сегментирует и оценивает (как нынешний `_SYSTEM_PROMPT`, плюс поля идентификации). Для фото этикетки — обычно одна запись с `label_complete=true`. Для фото тарелки — несколько записей с `label_complete=false`.

## 7. Источник — Open Food Facts (`sources/openfoodfacts.py`) — **переписан, ADR-0019**

> **Дельта v0.6 (2026-07-28).** Раздел переписан по итогам замера с прод-машины (`05_implementation/off-source-probe-2026-07-28.md`). Легаси-поиск OFF мёртв, форма ответа замены другая, матчинг заменён. Реализующее решение — **ADR-0019**.

Бесплатно, **без ключа**, обязателен кастомный **User-Agent** в формате `AppName/Version (ContactEmail)` — в проде сейчас формат нарушен (нет версии).

### 7.0 Что произошло с прежним эндпоинтом

`/cgi/search.pl` и `/api/v2/search` питаются одним Perl-бэкендом OFF, который устарел и отдаёт **HTTP 503 за 0.06 с с первого запроса**, с любого IP и с любым User-Agent. Замер: 18 из 25 запросов в первой итерации, 25 из 25 в разведке второй.

**Следствие:** сетевая ступень этого ТЗ в проде **не работала никогда**, `source=off` был недостижимым состоянием, лестница сводилась к `label → estimate`. Незаметно из-за отсутствия наблюдаемости (D12 в `spec-nutrition-llm-contract.md`).

> **Сигнал был и был неверно прочитан.** Changelog v0.4 (2026-06-13) фиксирует: «форма ответа подтверждена живым curl к api/v2, **search.pl периодически 503**». Периодические 503 приняли за флапанье и отгрузили адаптер на этом эндпоинте, вместо того чтобы проверить, не закрывается ли он. Урок — в §4 отчёта замера.

### 7.1 Эндпоинты (целевые)

| Путь | Запрос | Ответ |
|---|---|---|
| ~~**Поиск**~~ | — | **не используется с 2026-08-03** (вариант D): поисковой ветки в лестнице нет |
| **Штрихкод** | `GET {off_barcode_url}/{barcode}?fields=<…>` | `{status, product}` |

`off_barcode_url` = `https://world.openfoodfacts.org/api/v2/product` — единственный путь к OFF.
Он **работает** и не затронут отказом Perl-бэкенда, положившим поиск.

`off_search_url` (`https://search.openfoodfacts.org/search`, search-a-licious) **удаляется из конфига**:
миграция на него была нужна ради поискового запроса, а запрос больше не выполняется. Вместе с ней
отпадает переписывание маппинга карточки (`brands` списком, отсутствующий `product_name_ru`,
отсутствующий `energy-kj_100g`) — оно требовалось только поисковой выдаче.

**Латентность (замер, 25 запросов):** медиана 0.10 с, максимум 0.33 с при `off_timeout_s = 2.5` — запас двадцатикратный, значение менять не нужно.

**Статус источника:** search-a-licious — **beta 0.1.0**, гарантий SLA нет. Тот же класс риска, что закрыт ADR-0018 для LLM; смягчение то же — наблюдаемость + честная деградация в `None`.

### 7.2 Маппинг полей → `Macros` (на 100 г) — изменился

Перепись по 20 карточкам реальной выдачи:

| Наш `Macros` / поле | search-a-licious | Замечание |
|---|---|---|
| `kcal` | `nutriments.energy-kcal_100g` | **`energy-kj_100g` в выдаче ОТСУТСТВУЕТ** → прежний фолбэк «из кДж» мёртв, убрать |
| `protein` / `fat` / `carbs` | `proteins_100g` / `fat_100g` / `carbohydrates_100g` | нет любого из четырёх → карточка не кандидат |
| `matched_name` | `product_name` | **`product_name_ru` НЕ СУЩЕСТВУЕТ** (0 из 20); кириллица есть в `product_name` во всех 20 |
| бренд | `brands` — **список**, а не CSV | есть у **10 из 20**; прод `_first_brand()` делает `.split(",")` → `AttributeError` |
| релевантность | `_score` | новое поле, порядок `hits` уже по нему |
| `source_ref` | `https://world.openfoodfacts.org/product/{code}` | без изменений |

Плюс отличия транспорта: параметр `q` вместо `search_terms`, контейнер `hits` вместо `products`.

**Вывод:** сменой `base_url` не обойтись — переписываются запрос, маппинг и матчинг.

### 7.3 Выбор матча — barcode-first + LLM-переранжирование (заменяет прежний скоринг)

**Прежний детерминированный скоринг упраздняется как механизм выбора.** Замер: он даёт **36%** верных выборов, и точность не превышает 42% ни при каком пороге — то есть скор с правильностью не коррелирует, а местами инвертирован (`A-13`: скор 3.70 при промахе 98%; `A-05`: скор 1.82 и попадание). Гипотеза «добавить `min_score`» **опровергнута данными**.

Причины разобраны в §2.2 отчёта: `brands` недоступен половине карточек (а это был вес 3.0), `completeness` меряет полноту заполнения, а не похожесть на запрос, и при весе до 1.0 против 2.0 за имя перебивает совпадение названия; `_score` не использовался вовсе.

**Целевой порядок:**

```
1. barcode  — если item.barcode прошёл проверку C4.0 (контрольная сумма EAN-8/13,
              префикс не 02/20–29) → GET {off_barcode_url}/{barcode}
              найдено и КБЖУ полное → match_confidence = "exact"
2. поиск    — GET {off_search_url}?q=…
              кандидаты = [hits с полными 4 значениями]     # фильтр применимости, не матчинг
              топ-N = кандидаты[:off_rerank_candidates]      # порядок Elasticsearch по _score
3. переранжирование — ОДИН текстовый LLM-вызов на ВЕСЬ разбор (не на позицию):
              на каждую позицию — её name/brand/fat_pct + пронумерованные кандидаты
              ← номер выбранной карточки ЛИБО явный отказ
              выбрана → match_confidence = "confirmed"
4. отказ    — модель отказалась / кандидатов нет / вызов не удался → ступень
              возвращает None → следующая ступень лестницы
```

**Ступень отдаёт результат только на уверенном матче.** Докстринг прежнего `select_best` обещал «лучше `None`, чем не тот продукт», но код возвращал топ-1 безусловно; здесь поведение приводится в соответствие с намерением.

**Батч на разбор, а не на позицию** — ввод из четырёх продуктов даёт один дополнительный вызов, а не четыре. Тот же приём, что в `spec-nutrition-llm-contract.md` §5.2.

**`match_confidence`** протаскивается в `ResolvedNutrition` и далее в `NutritionItem` (транспорт analyze→confirm, не персистится). Гейт применения — `spec-nutrition-llm-contract.md` §7.1a: сверка label-preferred запускается только при `exact` или `confirmed`.

**Порог приёмки переранжирования:** ≥80% верных выборов при нуле уверенных ошибок на кейсах, где верная карточка есть в выдаче (ADR-0019 §6). Не взяли — возврат к детерминированному варианту B из ADR-0019 §3.

> ⚠️ **Статус на 2026-08-01: гейт НЕ взят, раздел не реализуется в текущем виде.** Замер (`05_implementation/rerank-accuracy-2026-08-01.md`): максимум **78% при 6 уверенных ошибках**. Заодно опровергнута посылка §7.4 — см. врезку там. Ключевое для этого раздела: **ранжирование чинить не нужно** (верная карточка всегда на ранге 1 или 2), а ценность LLM-вызова — в отказе, а не в выборе (при одинаковых 6 верных: топ-1 → 15 уверенных ошибок, `select_best` → 11, LLM → 3). Развилка механизма переоткрыта — ADR-0019 §9, решение за С. До решения ступень поиска остаётся на мёртвом легаси-эндпоинте (то есть деградирует в `estimate`), а гейт сверки в `resolve/pipeline.py` не пропускает ничего.
>
> ⛔ **Дополнение 2026-08-02: замена «топ-1 + LLM-вето» гейт тоже не взяла** (`05_implementation/veto-accuracy-2026-08-02.md`) — 33% верных при 1 уверенной ошибке; каскад топ-1→топ-2 — 44% при 2. Вето даёт наименьшее число уверенных ошибок из пяти измеренных механизмов, но отказывается и от верного (приняло 3 из 6 кейсов, где верная карточка стоит на ранге 1); два ложных отказа из трёх вызваны требованием совпадения брендов, столкнувшимся с брендовым шумом извлекателя. **Решающее сравнение:** вето-каскад даёт `off` на 16% позиций с двумя уверенными ошибками, вариант D (только barcode) — те же 16% без ошибок. **Этот раздел (LLM-матчинг) в текущем виде не реализуется; при варианте D он сокращается до barcode-пути §7.2.**

### 7.4 Покрытие базы — измерено

| Показатель | Значение (замер 2026-07-28, **одна подпись**) | Уточнение 2026-08-01 (**две подписи**) |
|---|---|---|
| Подходящая карточка присутствует в выдаче | 20 из 25 (80%) | **9–17 из 25** (36–68%), после ручного разбора ~12–14 |
| Из них ранжирована первой Elasticsearch | 7 | **все: ранг 1 (6 кейсов) или 2 (3), глубже не встречается** |
| Штрихкод возвращён моделью | 12 из 25 | без изменений |
| Из них пригоден для OFF после C4.0 | **4 из 25** (16%) | без изменений |

> ⚠️ **Числа левой колонки признаны артефактом прокси (2026-08-01).** «Подходящая карточка» там определялась **только** близостью ккал к эталону, а разные продукты дают близкие ккал: онигири↔«филе тунца в масле» 178/176, стейк на кости↔«сосиски со сливками» 220/221, щавелевый суп↔«суп перловый с грибами» 43.9/44.1, карпаччо из индейки↔«фарш из индейки» 147.8/150. Тот же класс, что «339 против 342» у детектора рассинхрона — только здесь он сидел внутри числа, которым обосновывался ADR. При подтверждении двумя независимыми подписями (ккал **и** имя) картина переворачивается: **узкое место — покрытие, а не выбор из выдачи**, а ранжирования как проблемы нет. Разбор — `05_implementation/rerank-accuracy-2026-08-01.md` §4.

Следствие для этапности: если нужный товар есть в базе примерно для половины упаковок, ступень OFF не является основной, и вес веб-ступени §8 (волна 2) выше, чем закладывалось. Для тарелок и ресторанных блюд (ярусы B/C датасета) OFF неприменим по природе: это база упаковок, там работает только веб-ступень §8.

## 8. Веб-ступень — ЭТАП R2 (волна 2)

> **Дельта v0.6 (2026-07-28).** Ступень переведена с `groq/compound` на **OpenAI `web_search`** — решение С. от 2026-07-27 в рамках выбора вторичного таргета (ADR-0018): один вендор, один ключ, один SDK; Groq уходит из кода целиком. Прежний вариант на Compound сохранён в истории документа, но не реализуется.

Добавляется кодом после волны 1 как ещё один `NutritionSource` (`sources/web_search.py`), встаёт в лестницу между OFF и estimate. Без рантайм-флага — этапность кода.

**Значимость ступени выросла.** Замер показал, что OFF — база **упаковок**: для тарелок, развеса и ресторанных блюд (ярусы B/C датасета) карточек там нет по природе. Веб-ступень — не расширение, а единственный источник провенанса для этого класса ввода.

**Контракт вызова:** инструмент `web_search` у первичного таргета (`llm_vision_model`/`llm_text_model` — текстовая ветка), тарификация двойная — вызов инструмента плюс содержимое выдачи (для mini-моделей фиксированный блок ~8000 входных токенов на вызов). Оценка при ~90 обращениях в месяц — порядка 1–2 $/мес; уточняется прогоном.

**Промпт (system), целевой:**

```
Ты — нутрициолог с доступом к веб-поиску. Найди КБЖУ указанного продукта на 100 г из надёжного источника (сайт производителя, маркетплейс, база продуктов).
Верни СТРОГО JSON: {"per100g": {"kcal":<ч>,"protein":<ч>,"fat":<ч>,"carbs":<ч>}, "matched_name": "<что нашёл>", "source_ref": "<URL>"}
Если достоверно не нашёл — верни {"per100g": null}. Никакого текста вне JSON. Числа без единиц, на 100 г.
```

**User:** `Продукт: <brand> <name> <fat_pct>%`. Таймаут `web_timeout_s`. Парс — общий (`spec-nutrition-llm-contract.md` §6.1); `per100g==null` → `None` (→ estimate). `source="web"`, `match_confidence="confirmed"` при наличии `source_ref`, иначе результат не принимается.

**Бюджет лестницы пересчитывается** вместе с внедрением ступени — см. §12.1.

## 13. Ошибки, деградация, латентность

| Ступень | Сбой | Действие |
|---|---|---|
| extractor (LLM) | нет ключа/429/кривой JSON | как сейчас: `LLMNotConfigured`/`LLMRateLimit`/`LLMError` → REST 502/понятный текст |
| OFF barcode | C4.0 не пройдена / товар не найден / КБЖУ неполное | `None` → к поиску |
| OFF поиск | таймаут/HTTP≠200/пусто | лог `warning`, `None` → следующая ступень |
| OFF переранжирование | модель отказалась / вызов не удался / номер вне диапазона | лог `warning`, **`None`** — «похожий товар» не подставляем |
| (R2) веб | таймаут/ошибка/`per100g=null`/нет `source_ref` | лог `warning`, `None` → estimate |
| estimate | — | всегда успешна (per100g из item), кроме `readout="unreadable"` → `unresolved` |

**Наблюдаемость (D12) — обязательна, а не желательна.** Отказ поисковой ступени продержался незамеченным месяцами именно потому, что `warning` в логе никто не читал, а метрик не было. Логировать на каждый разбор: HTTP-коды источника, распределение `match_confidence`, долю отказов ступени, долю позиций, дошедших до `estimate`. Резкий рост последней — сигнал, что источник снова отвалился.

Мульти-латентность: 1 LLM-вызов + ≤N OFF-запросов (только не-`label`), последовательно/семафор ≤2–3 (лимит OFF 10/мин); бюджет `resolver_total_budget_s` на весь ввод — при превышении остаток позиций отдаём `estimate` без сети. Никогда не показываем `estimate`-число как «точное».

## 17. Зафиксированные решения

- **Мульти-продуктовость** (С., 2026-06-13): `/analyze` — список позиций, резолв per-item; `/foods/analyze` — одно блюдо, расчётное (`source=estimate`), без ретривала.
- **`estimate` — не отдельный LLM-вызов**, а per100g, пришедшая из извлекателя (1 вызов на ввод).
- **Фича-флаги убраны**: резолвер всегда вкл.; надёжность — деградацией; web — этап R2 кодом.
- Авто-`SharedFood` — при сохранении записи; провенанс показываем; web (R2) — с цитатой.
- Полнотекст OFF — дефолт `cgi/search.pl` (Code фиксирует выбор).
- Фиксы #1 (`add_explicit`) и #2 (мультифото) — **уже в проде**, из инкремента исключены.
