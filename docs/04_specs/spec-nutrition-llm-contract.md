## 0. Что меняем в одном абзаце

Сегодня разбор питания идёт через **четыре промпта в двух несовместимых контрактных моделях**: `_EXTRACT_PROMPT` требует `per100g` и оставляет арифметику коду (правильно), а `_SYSTEM_PROMPT`/`_DISH_PROMPT`/`_COMBINED_PROMPT` требуют абсолют за порцию и заставляют модель умножать и складывать (решение L2 из ADR-0017 §8 это запрещает, но в код не внесено). Ответ модели валидируется только по типам, `label_complete` принимается на веру и коротит лестницу фолбэков, у самого LLM-вызова нет ни таймаута, ни ретрая, ни резервного провайдера, а usage/латентность в прод не логируются. Это ТЗ схлопывает четыре промпта в **один системный промпт + режимные user-преамбулы**, вводит трёхзначное `readout` вместо булева `label_complete` (включая явный отказ), добавляет **слой проверок ответа**, который понижает доверие вместо отклонения, и закрывает единую точку отказа провайдера.

### 0.1 Почему одним заходом с ADR-0017 §16

Конфиг победителя в код не внесён: `app/config.py` на 2026-07-27 — `groq_model="qwen/qwen3.6-27b"`, `llm_base_url="https://api.groq.com"`, `groq_max_images=3`, `max_tokens_param="max_tokens"`. Промпт настраивается под конкретную модель, а единственная обратная связь по нему — раннер на ярусе A. Пока прод и раннер-дефолт смотрят в разные модели, любая правка промпта не проверяема. **Внедрение §16 — предусловие, а не параллельная задача.**

## 2. Принципы (обязательны при реализации)

1. **Модель не считает.** LLM отдаёт только `per100g` и граммовки, вычитанные из ввода. Умножение на порцию, суммирование ингредиентов, перевод кДж→ккал при необходимости — код. Это решение L2 (ADR-0017 §8): снимает и лимит фото как класс проблемы, и арифметические ошибки LLM.
2. **Ни одна проверка не отклоняет ответ.** Единственное, что даёт отказ — невалидная схема после ретрая. Проверки §6 меняют **маршрут** (короткое замыкание лестницы) и **предупреждения в UI**, но гарантия ответа из `spec-nutrition-retrieval.md` §9 сохраняется.
3. **Честность важнее полноты.** Модель, признавшая нечитаемость, полезнее модели, выдавшей правдоподобные числа: замер показал, что ошибку «верное название, неверные числа на 5–35%» пользователь глазами не поймает (~8% этикеток).
4. **Автокоррекция чисел запрещена.** Код не «чинит» подозрительные значения (например, не делит на 4.184 при подозрении на кДж). Код помечает и маршрутизирует; исправляет источник или человек.
5. **Провенанс не завышаем.** `source=label` означает «числа списаны с этикетки и прошли проверки», не «модель так сказала».

## 3. Единый контракт извлечения

### 3.1 Схема (дельта к `resolve/ports.py`)

```python
Readout = Literal["label", "estimate", "unreadable"]

class ExtractedItem(BaseModel):
    name: str                        # родовое название без бренда
    brand: str | None = None
    fat_pct: float | None = None
    portion_g: float | None = None
    barcode: str | None = None
    per100g: Macros | None = None    # ⬅ БЫЛО обязательным; null только при readout="unreadable"
    readout: Readout = "estimate"    # ⬅ ЗАМЕНЯЕТ label_complete: bool
    note: str | None = None          # ⬅ НОВОЕ: причина estimate/unreadable, факт пересчёта из кДж
    confidence: float = 0.0

    @model_validator(mode="after")
    def _readout_consistency(self):
        if self.readout == "unreadable":
            if self.note is None:
                raise ValueError("unreadable требует note")
        elif self.per100g is None:
            raise ValueError(f"readout={self.readout} требует per100g")
        return self
```

**Почему трёхзначное `readout`, а не `bool + nullable`.** Булев `label_complete` не различает два разных состояния: «этикетки нет, дал типовые числа» и «этикетка есть, но нечитаема». Первое — нормальный режим, второе — сигнал пользователю переснять. Трёхзначное поле делает это различие явным и обязывает модель выбрать, а не умолчать.

**Миграция.** `label_complete` удаляется. Поле в БД не персистится (это транспорт analyze→confirm), миграция не нужна. `FoodEntry.source` остаётся `ProvenanceSource` без изменений — `readout` влияет на него через лестницу (§7), а не напрямую.

### 3.2 Что меняется в семантике

| Было | Стало |
|---|---|
| `label_complete=true` → безусловный `source=label`, лестница не запускается | `readout="label"` + проверки §6 пройдены → **кандидат** на `source=label`; сверка с OFF по правилу §7 |
| Числа обязательны всегда | При `readout="unreadable"` — `per100g=null`, позиция уходит в лестницу без `fallback_per100g` |
| `EstimateSource` всегда успешен (числа из позиции) | При `per100g=null` `EstimateSource` вернуть числа не может → §7.3 |

## 4. Промпты

### 4.1 Системный промпт (единственный)

Один текст на все пять путей. Режим задаётся user-частью (§4.3).

```
Ты — парсер дневника питания. Раздели ввод (текст и/или фото) на ОТДЕЛЬНЫЕ
продукты и верни запись для КАЖДОГО.

Верни СТРОГО JSON-объект, без текста вне JSON:
{"items": [{
  "name": "<родовое название, по-русски, без бренда и жирности>",
  "brand": <строка|null>,
  "fat_pct": <число|null>,
  "portion_g": <число|null>,
  "barcode": <строка цифр|null>,
  "per100g": {"kcal":<ч>,"protein":<ч>,"fat":<ч>,"carbs":<ч>} | null,
  "readout": "label" | "estimate" | "unreadable",
  "note": <строка|null>,
  "confidence": <число 0..1>
}]}

ЧИСЛА
- per100g — всегда на 100 г продукта. НИКОГДА не пересчитывай на порцию, не
  складывай продукты между собой, не умножай ни на что. Всю арифметику делает
  вызывающая программа — твоя задача только прочитать или оценить.
- kcal — килокалории. Если на этикетке и кДж, и ккал — бери ккал.
  Если указаны ТОЛЬКО кДж — раздели на 4.184 и напиши в note «пересчёт из кДж».
- Числа без единиц измерения.

ОТКУДА ЧИСЛА (поле readout) — отвечай честно, это важнее полноты
- "label" — все четыре значения СПИСАНЫ с читаемой таблицы пищевой ценности.
  Ставь "label", только если видишь все четыре числа и уверен, что читаешь
  колонку «на 100 г», а не «на порцию» и не соседний столбец.
- "estimate" — числа типовые, из твоих знаний о продукте. Ставь "estimate",
  если этикетки нет, она нечитаема, обрезана, повёрнута, засвечена, или если
  ты достроил хотя бы одно из четырёх значений. Честный "estimate" лучше,
  чем "label" наугад: программа умеет уточнить оценку по внешней базе, а
  ложную «этикетку» она принимает за истину.
- "unreadable" — продукт не опознан настолько, чтобы дать даже типовые числа.
  Тогда per100g = null и note обязателен.

ПОРЦИИ
- portion_g — масса именно этой порции, если она следует из текста
  («гречка 200» → 200) или из явной надписи на упаковке («нетто 380 г»).
  Не выводи её из колонки «на порцию» и не выдумывай: не знаешь → null.

СЕГМЕНТАЦИЯ
- Одна запись на каждый отдельный продукт. «гречка 200, курица 150» → ДВЕ записи.
- Несколько снимков ОДНОГО продукта (лицо и оборот упаковки, разные ракурсы) —
  это ОДНА запись, а не две.
- Тарелка из нескольких компонентов — запись на каждый различимый компонент.

ИМЕНОВАНИЕ
- name — родовое: «молоко питьевое», не «Домик в деревне 3.2%».
- brand и fat_pct — отдельными полями.
- note — коротко и по делу: что помешало (блик, обрезан край, мелкий шрифт,
  повёрнут текст) либо факт пересчёта из кДж. Нечего сказать → null.
```

**Что изменилось против `_EXTRACT_PROMPT` и зачем**

| Изменение | Обоснование |
|---|---|
| Явный запрет любой арифметики | L2; текущий промпт запрет не формулирует, только описывает поле |
| Ветка «только кДж → раздели на 4.184 + note» | Замер: кДж-конфузий 0 у финалистов, но на кДж-этикетках модель раньше не имела инструкции; ярус A их не покрыл (0/3, `llm-eval-dataset.md` §3) — риск не измерен |
| `readout` с явным «честный estimate лучше ложного label» + объяснение последствия | Прямая цель — сдвинуть распределение на A-05/A-13-подобных кейсах из `label` в `estimate`, где лестница может исправить числа |
| `unreadable` | ADR-0017 §17: «модель, уверенно выдающая числа с нечитаемой этикетки, хуже той, что признаёт нечитаемость» |
| Запрет брать `portion_g` из колонки «на порцию» | Ловушка `per-portion` из `llm-eval-dataset.md` §3 |
| «Несколько снимков одного продукта — одна запись» | Мультифото уже в проде (фикс #2 Nutrition); без правила даёт дубли |
| `note` | Без него `estimate` при видимой этикетке неотличим от `estimate` без этикетки → нечего показать пользователю |

### 4.2 Чего в промпте намеренно НЕТ

- **Few-shot примеров.** Замер дал 92% zero-shot на ярусе A; примеры удорожают каждый вызов и рискуют заякорить формат этикетки. Вводить только если регресс-прогон (§12) покажет провал на конкретном классе.
- **Цепочки рассуждений.** Замер: `reasoning_effort=low` ухудшает извлечение (100% → 94/88% при ×3 выходных токенов). CoT в промпте — та же природа.
- **Просьбы «будь точен», «это важно».** Не измеряемы, занимают бюджет.

### 4.3 Режимные user-преамбулы

Системный промпт один; различается только текстовая часть user-сообщения.

| Путь | User-преамбула | Обработка в коде |
|---|---|---|
| `/analyze` текст (дневник) | сам текст пользователя | §5.4.a |
| `/analyze` фото (дневник) | подпись пользователя, иначе `«Определи продукты на снимках и заполни записи.»` | §5.4.a |
| `/foods/analyze` dish_text (каталог) | `Блюдо: "<name>", вес порции: <weight_g> г.`<br>`Состав: <description>.`<br>`Верни запись НА КАЖДЫЙ ингредиент состава с его per100g и portion_g из текста. Итог посчитает программа.` | §5.4.b |
| `/foods/analyze` dish_photos | `Блюдо: "<name>", вес порции: <weight_g> г.`<br>`На снимках — это блюдо. Верни ОДНУ запись: per100g блюда, portion_g = null.` | §5.4.c |
| `/foods/analyze` dish_combined | `Блюдо: "<name>", вес порции: <weight_g> г.`<br>`Состав с граммовками: <text>.`<br>`На снимках — этикетки ингредиентов. Для каждого ингредиента из состава верни отдельную запись: per100g с его этикетки (если нашёл) и portion_g из состава. Не складывай — итог посчитает программа.` | §5.4.b |

`_SYSTEM_PROMPT`, `_DISH_PROMPT`, `_COMBINED_PROMPT` **удаляются**. `LLMService.parse_text/analyze_photo/analyze_dish_*` переводятся на `LLMExtractor` + агрегацию в `FoodService`; контракт `NutritionLLM` (I7) сохраняется по сигнатурам, меняется только реализация.

## 5. Структура запроса

### 5.1 Порядок и форма частей

Текстовая часть — **первой**, изображения — после (как сейчас). Одно `system` + одно `user` сообщение. `response_format={"type":"json_object"}` — да (OpenAI поддерживает; Anthropic-ветка после решения ADR-0017 §16 не нужна).

### 5.2 Много снимков → батчи, не обрезка (D11)

```
if len(images) <= max_images:  один вызов
else:                          батчи по max_images, параллельно (семафор 2),
                               items конкатенируются, затем дедуп §5.5
```

Обоснование: обрезка теряет ровно тот снимок, ради которого пользователь его прислал (оборот упаковки с таблицей), и делает это молча. Стоимость батча линейна и на реальных вводах (2–5 фото) чаще всего не наступает. `_cap_images` удаляется вместе с молчаливым warning.

### 5.3 Бюджет вывода и обрезка (D7)

- `max_completion_tokens = llm_output_tokens_base + llm_output_tokens_per_item × n_images_in_batch`, дефолт `700 + 220×N`, нижняя граница 1500.
  Основание: фактический расход на ярусе A — 1802–2174 токена на вызов (`llm-eval-results` §5), прогноз ~1950 сошёлся с точностью <8%.
- **Проверять `response.choices[0].finish_reason`.** `"length"` → один ретрай с удвоенным бюджетом; повторное `"length"` → `LLMError` с текстом «ответ не помещается, пришли меньше снимков за раз». Сегодня этот случай неотличим от «модель вернула не JSON».

### 5.4 Агрегация — арифметика в коде (L2, D2)

**a) Дневник.** Как сейчас в `_to_item`: `kcal = per100g.kcal × portion_g/100`, при `portion_g=null` — числа = per100g, вес пуст, фронт пересчитает после ввода веса.

**b) Блюдо по составу** (`dish_text`, `dish_combined`): позиций несколько, итог — одна.
```
total_kcal = Σ per100g_i.kcal × portion_g_i / 100      (аналогично P/F/C)
weight_g   = weight_g, переданный пользователем        (не сумма граммовок)
description= name, переданный пользователем
```
Усушка не моделируется намеренно: при выпаривании воды КБЖУ не теряется, теряется масса. Отсюда — проверка C6 (§6.4) на расхождение суммы граммовок и заявленного веса.
Позиция с `portion_g=null` в этом режиме считается ошибкой извлечения → warning в UI, вклад позиции = 0, позиция показана отдельно.

**c) Блюдо по фото** (`dish_photos`): одна позиция, `kcal = per100g.kcal × weight_g/100`.

**d)** Все суммы округляются **один раз, в конце** (`round(x, 1)`). Сейчас округление идёт на позиции — при 5 ингредиентах даёт систематическое накопление.

### 5.5 Дедуп после батчей

Ключ: `(normalize(name), brand, fat_pct)`, где `normalize` — нижний регистр + схлопывание пробелов. При совпадении записи сливаются, побеждает `readout` по приоритету `label > estimate > unreadable`; `portion_g` берётся ненулевой; `note` конкатенируются.

**Риск, принимаемый осознанно:** два одинаковых продукта, съеденных дважды, схлопнутся в один. Пользователь видит это на экране подтверждения и правит вес. Обратная ошибка (дубль от лица и оборота упаковки) встречается чаще и раздражает сильнее. Решение OQ-1..6 №5 (С.): **схлопывать**.

## 6. Проверки ответа

Новый модуль `app/contexts/nutrition/resolve/checks.py` — чистые функции, без сети и без LLM, полностью юнит-тестируемые.

### 6.1 C1 — разбор и схема (D13)

`_extract_json` переписывается: снятие ```-ограждения через `re.match(r"^```(?:json)?\s*(.*?)\s*```$", text, re.S)` вместо `lstrip("json")` (последний режет по набору символов, а не по префиксу). Далее — `json.loads`. Невалидный JSON → **один ретрай** с той же user-частью и добавленной строкой `«Предыдущий ответ не был валидным JSON. Верни только JSON-объект.»`; повторный провал → `LLMError`.

### 6.2 C2 — сходимость по Атуотеру

*Порог откалиброван на данных: `05_implementation/llm-checks-calibration-2026-07-27.md`.*

```
computed = 4·protein + 9·fat + 4·carbs
delta    = |kcal − computed| / max(computed, 1)
delta ≥ check_atwater (0.20)  → флаг arith_mismatch + понижение readout: label → estimate
```

**Один порог, не два.** Исходная пара `0.20 warn / 0.35 fail` на реальных данных ведёт себя идентично: в распределении есть разрыв — неверные ответы либо ≥43.9%, либо ≤7.9%, между ними пусто. Любое значение в коридоре 13–40% даёт один и тот же результат. Нижняя граница коридора задана физикой продуктов: на **корректно** прочитанных этикетках Атуотер расходится до 12% (клетчатка, полиолы, органические кислоты, округление производителем), поэтому порог ниже ~13% начинает браковать верные ответы.

**Чем C2 на самом деле является — важно не перепутать.** На выбранной прод-модели `gpt-5.4-mini` проверка ловит **0 из 2** её ошибок; на `gpt-5.4` — 0 из 2; на `qwen/qwen3.6-27b` — 5 из 9. Обе ошибки победителя (A-05, A-13) внутренне согласованы: модель списывает непротиворечивый набор чисел не из той строки или колонки, `delta` = 3.8% и 1.7% — в пределах естественного разброса реальных этикеток.

Отсюда роль C2–C4: это **не защита от ошибок текущей модели, а детектор её подмены** — регресс станет виден в логах в тот же день, а не через месяц (провайдер менял модель под проектом трижды за 5 месяцев). Плюс страховка вторичного таргета ADR-0018. Единственный механизм против остаточных 63% — сверка с внешним источником, §7.

### 6.3 C3 — кДж-утечка

```
ratio = kcal / max(computed, 1)
ratio ∈ [check_kj_lo, check_kj_hi] = [3.6, 4.8] → флаг kj_suspected
                                                 → понижение readout: label → estimate
```
Диапазон шире, чем 3.8–4.5 в раннере, потому что раннер сравнивает с эталоном, а прод — с атуотеровской оценкой, у которой своя погрешность до 12%. **Автоделение на 4.184 запрещено** (принцип §2.4): если модель прочла кДж, она могла ошибиться и в остальном.

**Подтверждено данными** (`llm-checks-calibration-2026-07-27.md` §4): три реальных случая на текущей прод-модели `qwen` — 380 ккал вместо 90, 918 вместо 221, 137.3 вместо 32.6, все с `ratio` 4.15–4.29. Ложных срабатываний ноль на 84 верных ответах; `ratio` эталонов лежит в 0.96–1.12, до полосы далеко. Это же закрывает **B4 из триажа MVP** (P0, «кДж пишется в ккал») — баг реален и воспроизводим, детерминированный гард ловит его без обращения к эталону.

### 6.4 C4–C6 — границы и сходимость

| Код | Правило | Действие |
|---|---|---|
| C4.0 | **штрихкод:** контрольная сумма EAN-8/13 сходится и префикс не внутримагазинный (`02`, `20`–`29`) | не сходится → `barcode = null` + `barcode_invalid` |
| C4.1 | `kcal ≤ 900` (чистый жир = 900 ккал/100 г — физический потолок) | > → `bounds_fail`, `label → estimate` |
| C4.2 | каждый из P/F/C ∈ `[0, 100]`; `P+F+C ≤ 102` (допуск на округление) | > → `bounds_fail`, `label → estimate` |

> **C4.0 — бесплатный детектор неверно прочитанного штрихкода.** Замер (`off-source-probe-2026-07-28.md` §2.4): модель вернула штрихкод в 12 случаях из 25, но контрольная сумма отсеяла 6 (цифры прочитаны неверно) и ещё 2 — как внутримагазинные весовые коды, которых в OFF нет по определению. Пригодных осталось 4. Без этой проверки половина штрихкодов ушла бы в точный lookup и вернула бы чужой товар с наивысшим доверием `match_confidence=exact`.

> **C4.2 — это детектор ловушки per-portion, а не только санити-граница.** Эталон A-09 (картофельное пюре) имеет `P+F+C = 125` при `basis: per_portion` — значения на упаковку 500 г. Если модель прочитает такую таблицу и объявит её значениями на 100 г, сумма макронутриентов превысит массу продукта, что физически невозможно. Второе обоснование правила, найденное при калибровке (§5 отчёта).
| C4.3 | `P+F+C ≥ 5` при `kcal < 10` | → `bounds_fail` |
| C4.4 | `kcal ≥ 50` при `P+F+C ≤ 0.5` | → `bounds_warn` (не fail: крепкий алкоголь легитимен — водка ≈ 235/0/0/0) |
| C5 | `portion_g ∈ (0, 5000]` | вне → `portion_g = null` + `portion_warn` (типовая причина — путаница мл/г или выдумка) |
| C6 | dish-режимы: `\|Σ portion_g_i − weight_g\| / weight_g > 0.30` | → `weight_mismatch` (warning в UI: «сумма граммовок ингредиентов не сходится с весом порции») |

### 6.5 Что делаем с `confidence` (D4)

**Не гейтим.** Самозаявленная уверенность LLM слабо калибрована, а порог на ней даст ложное чувство контроля. Решение: `confidence` **логируется** (§9) и используется только как тай-брейк при дедупе (§5.5) — иначе поле удалить. Явная фиксация нужна, чтобы поле перестало быть декоративным.

### 6.6 Обработка `readout="unreadable"` — отдельный массив `unresolved`

*Решение по OQ-6 принято Claude (С.: «как лучше по best practices»); Катя может переиграть UX-часть.*

Позиция без чисел проходит лестницу §7 с `fallback_per100g=None`. Если ни один источник не ответил, она **не попадает в `items`**, а возвращается в отдельном массиве:

```jsonc
// POST /api/v1/nutrition/analyze → 200
{
  "items": [ /* NutritionItem — КБЖУ всегда заполнены, как и раньше */ ],
  "unresolved": [
    { "name": "мороженое",              // null, если не опознано вовсе
      "note": "этикетка перекручена, значения не читаются",
      "reason": "unreadable" }          // unreadable | no_source
  ]
}
```

**Почему отдельный массив, а не nullable-КБЖУ + `ProvenanceSource: unreadable`** (вариант из v0.1):

1. **Не ослабляем контракт ради редкого случая.** Сделать `kcal` nullable — значит заставить каждого потребителя (фронт, `save_entries`, аналитика, дайджест) проверять на null в пути, где числа есть в 99% случаев. Опциональное поле, осмысленное «иногда», — известный запах в API-дизайне; частичный успех правильнее выражать структурой ответа, а не разрешающими null-ами.
2. **`ProvenanceSource` описывает происхождение чисел.** Значение «чисел нет» в эту ось не ложится: `unreadable` — не источник. Перечисление осталось бы честным (`label|off|web|nutritionix|estimate`), а поле `FoodEntry.source` — не-nullable, как сейчас.
3. **Тип ошибки становится явным.** `items: [], unresolved: [...]` читается однозначно и на клиенте, и в логах; `items: [{kcal: null}]` требует интерпретации.

**Поведение:**

- Позиции в `unresolved` **не блокируют** сохранение остальных: `save_entries` их просто не получает.
- Все позиции нераспознаны (`items: []`, `unresolved` непустой) → **200**, не 502. Сегодня пустой `items` даёт `LLMError("Не удалось распознать продукты")` — это правило меняется: 502 остаётся только когда пусты оба массива (модель не вернула ничего).
- **Сохранение позиции без чисел запрещено.** Запись с нулевым КБЖУ хуже отсутствия записи: она выглядит как данные и портит дневные итоги, прогресс к целям и дайджест.

**UX экрана подтверждения** — блок под основным списком, действия по возрастанию усилия: «Переснять» → «Выбрать из каталога» (поиск по `name`, если опознано, — переиспользует существующий `SharedFood`) → «Ввести вручную». Текст берётся из `note`.

**Правки контракта:** `openapi.yaml` — поле `unresolved` в ответах `/analyze` и `/foods/analyze`, схема `UnresolvedItem`. `ProvenanceSource` **не трогаем**, nullable-КБЖУ **не вводим**.

### 6.7 Куда попадают флаги

`NutritionItem` получает поле `warnings: list[str]` (коды флагов) — транспорт analyze→confirm, **в БД не персистится** (как `matched_name`). Фронт рендерит человекочитаемый текст по коду; коды в `openapi.yaml`.

## 7. Лестница фолбэков — пересмотр label-short-circuit (D3)

Это единственное **архитектурное** изменение к ADR-0013 §4. **Решено (С., 2026-07-27): вариант B — сверять при наличии `brand`.** Зафиксировано секцией «Ревизия 2026-07-27» в `ADR-0013-nutrition-retrieval.md`.

### 7.1 Проблема

Замер: на ~8% этикеток модель верно называет продукт и ошибается в числах на 5–35%, при этом заявляет `label`. Действующее правило `if item.label_complete: return source="label"` пропускает OFF и отдаёт эти числа с **высшим** провенансом в UI. То есть максимальная уверенность показывается ровно там, где ошибка наиболее вероятна и наименее заметна.

### 7.1a Предусловие: гейт уверенности матча (ADR-0019)

*Добавлено 2026-07-28 по итогам замера источника (`05_implementation/off-source-probe-2026-07-28.md`).*

Замер вскрыл, что посылка §7.1 верна лишь наполовину. OFF товар **содержит** — подходящая карточка присутствует для 20 из 25 позиций. Но **не опознаёт**: прод-логика `select_best` выбирает верную карточку в **36%** случаев, и точность не превышает 42% ни при каком пороге скора, то есть скор с правильностью не коррелирует. Заодно выяснилось, что поисковый эндпоинт, в который ходит прод, мёртв (HTTP 503) — сетевая ступень не работала никогда.

При таком матчинге сверка не ловила бы ошибки этикеток, а **производила** бы ложные: в двух случаях из трёх пользователю показали бы расхождение с чужим товаром. Поэтому:

```
сверка запускается ⟺ match_confidence ∈ {exact, confirmed}
```

| Значение | Когда |
|---|---|
| `exact` | штрихкод прошёл контрольную сумму EAN и товар найден по коду |
| `confirmed` | карточка выбрана LLM-переранжированием из кандидатов |
| *(нет)* | модель отказалась, кандидатов нет, вызов не удался → **ступень возвращает `None`** |

Неуверенный матч **не показывается пользователю вовсе** — ни как `alternative`, ни как предупреждение. Механизм матчинга — ADR-0019 §2.2–2.4.

### 7.2 Целевое правило: label-preferred, не label-short-circuit

```python
async def refine(item, *, allow_network=True):
    checks = run_checks(item)                 # §6 → флаги + возможно понижение readout
    label_ok = (item.readout == "label" and not checks.downgraded)

    if label_ok and not (verify_label and allow_network and item.brand):
        return Resolved(item.per100g, source="label", warnings=checks.flags)

    external = await run_network_ladder(q) if allow_network else None   # OFF (R2: +web)
    # ⬇ ГЕЙТ §7.1a: неуверенный матч приравнивается к отсутствию результата
    if external is not None and external.match_confidence not in ("exact", "confirmed"):
        external = None

    if label_ok:
        if external is None:
            return Resolved(item.per100g, source="label", warnings=checks.flags)
        if rel_diff(item.per100g.kcal, external.per100g.kcal) > resolver_disagree_pct:
            return Resolved(item.per100g, source="label",
                            warnings=checks.flags + ["label_disagrees_with_source"],
                            alternative=external)          # ⬅ обе версии на confirm-экран
        return Resolved(item.per100g, source="label", warnings=checks.flags)

    if external is not None:
        return external
    if item.per100g is not None:
        return Resolved(item.per100g, source="estimate", warnings=checks.flags)
    return Unresolved(name=item.name, note=item.note, reason="unreadable")  # → §6.6
```

Ключевые свойства: label-числа остаются основными (не подменяем их данными OFF — OFF тоже ошибается), но **расхождение показывается пользователю**, а решение принимает он. Сверка запускается только при наличии `brand` — без бренда шанс найти товар в OFF близок к нулю, а запрос стоит времени.

### 7.3 Стоимость

Сетевых запросов к OFF станет больше: сегодня label-позиции их не делают вовсе. Смягчение: (а) фильтр по `brand`; (б) общий бюджет `resolver_total_budget_s` уже есть и при исчерпании отдаёт `allow_network=False`; (в) кэш SharedFood гасит повторы; (г) переиспользуемая `ClientSession` (§8.5) снимает handshake на позицию.

**Честная оценка:** это меняет медианную латентность `/analyze` вверх на величину ответа OFF (`off_timeout_s=2.5` — потолок, типично 0.3–0.8 с) для позиций с брендом. При 1.3 с на LLM-вызов это заметно. Отвергнутая альтернатива — не сверять и жить с 8% молча неверных КБЖУ (OQ-1, вариант A).

## 8. Отказоустойчивость LLM (D8–D10)

**Решено: ADR-0018 (принят С., 2026-07-27) — вариант B, вторичный таргет `gpt-5.4`.** Этот раздел — реализационная развёртка ADR; при расхождении источник истины — ADR-0018.

### 8.1 Таймаут

`llm_timeout_s = 20.0` на вызов (медиана победителя 1.3 с — запас ×15). Передаётся в SDK (`timeout=`), не в `asyncio.wait_for`: SDK корректно рвёт соединение. Общий бюджет запроса — таймаут × (1 + число ретраев).

### 8.2 Ретраи

| Условие | Действие |
|---|---|
| 429 | до 2 попыток, экспоненциальный backoff 1 с → 4 с + jitter; уважать `Retry-After`, если есть |
| 5xx, timeout, обрыв соединения | 1 ретрай без задержки |
| `finish_reason == "length"` | 1 ретрай с ×2 бюджетом вывода (§5.3) |
| невалидный JSON / схема | 1 ретрай с ужесточающей строкой (§6.1) |
| 4xx кроме 429 | **без ретрая** → далее по матрице §8.3 |

Ретраи первичны по отношению к переключению: сначала исчерпываем попытки на модели, потом меняем цель.

### 8.3 Вторичный таргет — `gpt-5.4`, матрица сужена под общий аккаунт

`LLMTarget` уже существует и достаточен — нужен **список** целей вместо одной. Вторичная цель — `gpt-5.4`: тот же вендор, ключ, SDK и параметры вызова, паритет по качеству (92%/83%, 1.8 с). Второго кодового пути не возникает.

**Следствие общего ключа и аккаунта, обязательное к реализации.** Часть отказов резервом не лечится — переключение на `gpt-5.4` с тем же ключом лишь добавит `llm_timeout_s` перед тем же исходом. Переключаемся **тогда и только тогда, когда отказ специфичен для модели**:

| Класс | Признаки | Действие |
|---|---|---|
| Модельный | `model_not_found`, `deprecated_model`, 404 на модель | → **вторичный** + алерт админу |
| Модельный транзиентный | 5xx/timeout, ретраи §8.2 исчерпаны | → **вторичный**, алерт при устойчивом повторе |
| Аккаунтный | 401, 403, `invalid_api_key`, `insufficient_quota`, org-level 429 | **без переключения** → алерт + честная ошибка пользователю |
| Вендорский | 5xx на обеих моделях, отказ DNS/сети | **без переключения** после первой неудачи вторичного → алерт + честная ошибка |
| Пользовательский | 400 на кривой запрос, слишком большие изображения | `LLMError`, без переключения |

Позиции, посчитанные вторичным таргетом, получают `warnings += ["fallback_provider"]`. При варианте B качество не падает, поэтому плашка на экране подтверждения **информационная**, не предупреждающая — но механизм нужен: состав таргетов переживёт это решение (ADR-0018 §6).

### 8.4 Startup-guard и суточная проверка

- При старте: `GET {llm_base_url}/models` → убедиться, что `llm_vision_model` присутствует. Отсутствует → **алерт админу через существующий error-handler** и старт с вторичным таргетом. Ровно это отловило бы 17.07.26 за месяц до отказа (уведомление Groq пришло 17.06).
- Та же проверка раз в сутки через generic `scheduler/` (ADR-0003) — уведомление о депрекейшне приходит по почте, а не в бот.
- Guard не должен блокировать старт при недоступности сети: провал самой проверки → warning в лог, не падение.

### 8.5 Переиспользуемая сессия OFF (D14, minor)

`OpenFoodFactsSource` создаёт `ClientSession` на каждый `lookup`. С учётом §7.3 (запросов станет больше) — держать одну сессию на приложение (создание в `main.py`, закрытие на shutdown) либо на резолвер. Не блокер, но входит в тот же заход.

## 9. Наблюдаемость (D12)

Одна структурированная строка лога на каждый LLM-вызов, уровень INFO:

```
llm_call model=<> target=<primary|fallback> path=<analyze_photo|dish_combined|...>
         batch=<i/n> latency_ms=<> prompt_tokens=<> completion_tokens=<>
         finish_reason=<> n_items=<> readout={label:2,estimate:1,unreadable:0}
         flags=[arith_mismatch,...] retries=<>
```

И одна на разбор целиком: `sources={label:2,off:1,estimate:1}`, `total_ms`, `budget_exhausted=<bool>`.

**Зачем именно так.** Отказ 17.07.26 был немым: `APIError` маскировался под «сервис временно недоступен», и понять, что модель снята, можно было только вручную. Строки выше делают заметными: рост доли `fallback_provider`, рост `retries`, сдвиг распределения `readout`, обрезки по `length`. Плюс дают фактическую цену без раннера.

Алерт админу (существующий механизм): первое за сутки переключение на вторичный таргет; провал startup-guard.

```python

### 12.1 Калибровка порогов — ✅ выполнена 2026-07-27

Отчёт: `05_implementation/llm-checks-calibration-2026-07-27.md`. Итог: `check_atwater = 0.20` (единственный порог), полоса кДж `[3.6, 4.8]` подтверждена тремя реальными случаями, границы 900/102 оставлены. ### 12.2 Юнит-тесты (без сети, без LLM)

- `checks.py`: C2–C6 — по 2 кейса на правило (граница снизу/сверху), включая водку под C4.4 и кДж-этикетку под C3.
- Агрегация §5.4: dish по 3 ингредиентам — сумма совпадает с ручным расчётом; округление один раз; позиция с `portion_g=null` не ломает итог.
- Батчи §5.2 и дедуп §5.5 на фейковом извлекателе: 7 снимков → 2 вызова, дубль схлопнут, приоритет `label` соблюдён.
- Схема §3.1: `unreadable` без `note` → `ValidationError`; `label` без `per100g` → `ValidationError`.
- Ветка `unresolved` §6.6: позиция без чисел не попадает в `items`; остальные позиции сохраняются; **все** позиции нераспознаны → 200 с пустым `items`, не 502; оба массива пусты → 502.
- Лестница §7.2: `label` + `brand` + согласие источника → `source=label` без флага; расхождение >15% → флаг `label_disagrees_with_source` + `alternative`; `label` **без** `brand` → сетевая ступень не вызывается (проверяется счётчиком вызовов фейкового источника); проваленные проверки → понижение до `estimate` и обычный проход лестницы.
- Ретраи §8.2 и матрица §8.3 на фейковом клиенте: 429 → 2 попытки, затем переключение; `finish_reason=length` → ретрай с ×2 бюджетом; `model_not_found` → переключение без ретрая; **401 и `insufficient_quota` → переключения НЕ происходит** (это и есть проверка сужения матрицы под общий аккаунт).
- `_extract_json` §6.1: ответ в ```-обёртке, без неё, с префиксным текстом, с ответом, начинающимся на `n`/`json`.
- Живых вызовов провайдера в `pytest` нет (GAP-6 сохраняется).

### 12.3 Регресс через раннер (приёмка)

Прогон `run_eval.py` на 25 валидных кейсах яруса A новым промптом и `gpt-5.4-mini`:

| Метрика | Baseline (2026-07-27) | Порог приёмки |
|---|---|---|
| валидный JSON | 100% | 100% |
| kcal ≤2% | 92% | **≥92%** (не хуже) |
| БЖУ ≤2% | 83% | ≥83% |
| кДж-конфузий | 0 | 0 |
| медианная задержка | 1.3 с | ≤2.0 с |
| детектор рассинхрона: уверенных | 0 | 0 |

Плюс **новая метрика «отказ вместо выдумки»**: на A-07 (`status: unscorable`, этикетка физически нечитаема) правильный ответ теперь — `readout ∈ {estimate, unreadable}`. Кейс возвращается в оценку по этой метрике, не по числам. Это закрывает пункт ADR-0017 §17.

Промпт меняется — раннер должен уметь прогнать **обе** версии для сравнения (флаг выбора промпта), иначе «не хуже» недоказуемо.

### 12.4 Покрытие RU-брендов в OFF — ✅ измерено 2026-07-28

Отчёт: `05_implementation/off-source-probe-2026-07-28.md`. Итог: **покрытие 80%** (подходящая карточка есть для 20 из 25 товаров) — вопрос закрыт положительно, российские продукты в базе представлены.

Но замер вскрыл два блокера, которых никто не искал:

1. **Поисковый эндпоинт прода мёртв** — `/cgi/search.pl` и `/api/v2/search` отдают HTTP 503 (общий устаревший Perl-бэкенд). Сетевая ступень лестницы ADR-0013 не работала никогда; `source=off` — недостижимое состояние. Незаметно из-за D12.
2. **Матчинг даёт 36%** и не улучшается порогом. Гипотеза «добавить `min_score`», выдвинутая до замера, опровергнута.

Оба закрываются **ADR-0019** (миграция на `search-a-licious`, barcode-first, LLM-переранжирование, гейт уверенности §7.1a). Миграция переезжает в **волну 1**: без неё решение OQ-1 не запускается, а простая смена `base_url` уронит прод — `_first_brand()` падает на списке, которым `brands` приходит в новом API.

Новая метрика приёмки — точность LLM-переранжирования, ≥80% верных выборов при нуле уверенных ошибок (ADR-0019 §6).
