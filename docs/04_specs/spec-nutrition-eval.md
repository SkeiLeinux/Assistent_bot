**Версия:** v0.1 (черновик на ревью) · **Дата:** 2026-06-24
**Статус:** 🟡 черновик — чек-поинт перед кодом (С. ревьюит дизайн; скаффолд `eval/` не начинаем до приёмки)

## 0. Что делаем в одном абзаце

Собираем маленький **размеченный датасет** реальной еды (вход ровно как шлёт пользователь + эталонные КБЖУ/граммы) и **standalone-харнесс**, который гоняет существующий конвейер разбора (`extractor → resolver → масштаб`) на этих кейсах с **живыми** вызовами LLM/OFF и считает ошибку **по стадиям**: где именно ломается — идентификация, порция, КБЖУ-на-100г или итог. Харнесс прогоняет несколько **вариантов** (модель × ретривал × гарды) на одном датасете и выдаёт отчёт-таблицу. Это превращает «ветчина показала 500 вместо 200» в «label-OCR MAPE = X%, штрихкод-вариант роняет до Y%», и делает выбор модели/фиксов цифрой, а не спором.

---

## 1. Мотивация (диагностический кейс)

Реальный сбой (С., июнь 2026): «100г ветчины + фото этикеток» → ветчина ≈ **500 ккал** вместо ~200. Корень — **vision-OCR таблицы пищевой ценности слабой моделью (Scout 17B), которому доверяют без проверки**: в дневнике `label_complete=true` делает short-circuit и **пропускает OFF** (`resolve/pipeline.py`), а режим блюда (`/foods/analyze`, combined) вообще без ретривала (`source=estimate`). Уверенный неверный OCR проходит как «точное с этикетки».

Эта дыра — гипотеза. Прежде чем чинить (штрихкод вместо OCR панели; Atwater-проверка; модель получше; ретривал в dish-режим) — её надо **подтвердить цифрой** и убедиться, что фикс реально помогает и не ломает остальное. Это и есть задача харнесса.

## 2. Что меряем — метрики по стадиям

Разбор = цепочка из независимых стадий; смешивать их ошибки нельзя (иначе не видно, чинить модель, ретривал или UX порции). Все метрики считаем **per-tier** (см. §3), чтобы тир без эталона порции не разбавлял портретную метрику.

| Стадия | Метрика | Что изолирует |
|---|---|---|
| Идентификация / сегментация | точность числа позиций; precision/recall матча позиций к эталону (по нормализованному имени + alias-map); доля кейсов с точным набором | «понял ли вообще, что и сколько съедено» |
| Порция (вес) | MAE_g, MAPE_g — только там, где эталон граммов есть (Tier A) | боль №1 (вес по фото); чистая, без КБЖУ |
| КБЖУ на 100 г | MAPE по kcal (заголовок) + MAE по Б/Ж/У | качество OCR/ретривала, БЕЗ ошибки порции (берём `kcal_100g/..._100g` из ответа) |
| Итог ккал | MAPE на позицию и на приём | то, что чувствует пользователь (порция × 100г) |
| Atwater-консистентность | residual = \|kcal − (4·Б + 4·У + 9·Ж)\| / max(kcal,1); флаг при residual > 0.15 | внутреннее противоречие позиции — ловит «ветчину-500» **без эталона и без сети** |
| Source-mix | доля label/off/estimate; **MAPE ккал в разрезе source** | гипотеза «label-OCR — худший источник» проверяется напрямую |

Заметки по метрикам: MAPE = среднее по позициям `|pred−true|/true`; при `true→0` (углеводы ветчины) — для макросов берём MAE, не MAPE (ккал всегда >0, там MAPE корректен). Atwater игнорирует клетчатку/алкоголь → возможен лёгкий ложный флаг на клетчаточных; порог 0.15 — стартовый, тюним на данных (`# TODO(spec)` — финальный порог по факту).

## 3. Эталонный датасет — три тира

Решение С. (2026-06-24): гибрид. Тиры дают разный класс эталона и мерят разные стадии — это фича, а не компромисс.

| Тир | Источник эталона | Усилие | Мерит | Эталон порции? |
|---|---|---|---|---|
| **A. Взвешенные приёмы** (~20–30) | кухонные весы (граммы) + КБЖУ/100г с этикетки/штрихкода | высокое | порцию + итог + идентификацию | **да** (единственный тир с правдой по весу) |
| **B. Доразметка истории** | экспорт дневника (`export_period` уже есть) + ручная правка значений | низкое | идентификацию, разбор текста, охват | нет |
| **C. Пакеты по штрихкоду** | фото этикетки + штрихкод; эталон = OFF-by-barcode / производитель | низкое | OCR/КБЖУ-100г, кейс «ветчина-500» | частично |

### 3.1 Схема кейса (`cases.jsonl`, по строке на кейс)

```json
{
  "id": "case-0001",
  "tier": "C",
  "input": {
    "text": "100г ветчины",
    "images": ["img/case-0001-vetchina-label.jpg"],
    "mode": "diary"
  },
  "truth": {
    "items": [
      {
        "name": "ветчина",
        "grams": 100,
        "per100g": {"kcal": 250, "protein": 18, "fat": 20, "carbs": 1},
        "barcode": "4690228012345",
        "source_of_truth": "barcode"
      }
    ]
  },
  "tags": ["packaged", "ocr", "label-photo"]
}
```

- `input` — РОВНО то, что шлёт пользователь (текст и/или пути к фото; `mode` ∈ `diary|dish_combined|dish_photo|text` → какой путь конвейера дёргать).
- `truth.items[].grams/per100g` — эталон; итоговые ккал считаются как `per100g × grams/100`, отдельно не дублируем.
- Tier B: `grams`/`per100g` может быть `null` → метрики, требующие этих полей (порция), для кейса пропускаются.
- Фото — в `eval/nutrition/dataset/img/`, пути относительные. Датасет (особенно фото) — **личные данные**: `eval/nutrition/dataset/` в `.gitignore`, в репо только схема + синтетический пример.

## 4. Протокол сбора (для С.)

- **Tier A (взвешенные, приоритет — боль порций):** перед едой взвесь каждый компонент кухонными весами, запиши граммы; сделай ровно то фото/текст, что отправил бы боту; КБЖУ/100г компонента возьми с этикетки/штрихкода. Разнообразь тарелки (не только пакеты) — только так померим ошибку веса по фото.
- **Tier C (пакеты, дёшево, делай много):** фото этикетки + читаемый штрихкод пакетированного (ветчина, сыр, молочка…); эталон = OFF по штрихкоду (если в OFF нет — значения с панели, `source_of_truth: "label"`). Прямо закрывает кейс «ветчина-500».
- **Tier B (история, breadth):** `export_period` уже отдаёт markdown-дамп дневника — берём оттуда позиции, руками правим неверные значения. Без веса; годится для идентификации/текста.

Достаточно по **5–10 кейсов на тир** для первого сигнала; точность метрики растёт с объёмом, но даже ~30 кейсов уже разводят варианты.

## 5. Архитектура харнесса

Новый top-level пакет `eval/nutrition/` (вне `app/` и `tests/`).

```
eval/nutrition/
  __init__.py
  run.py            # CLI: python -m eval.nutrition.run --dataset ... --variant baseline
  variants.py       # описание вариантов (Extractor + resolver-config + guards)
  metrics.py        # §2: чистые функции метрик (юнит-тестируемы на синтетике)
  matching.py       # матч предсказанных позиций к эталонным (нормализация + alias-map)
  cache.py          # кэш сырых ответов LLM/OFF по hash(вход+модель+версия промпта)
  report.py         # сборка отчёта md + csv
  dataset/          # .gitignore (личные данные); в репо — cases.example.jsonl + img/.gitkeep
  .cache/           # .gitignore
```

Принципы:
- **Живые вызовы — намеренно** (в отличие от pytest, который герметичен на фейках). Поэтому харнесс живёт **вне `tests/`** и pytest'ом не собирается. Это явная и единственная точка реальных LLM/OFF из кодовой базы.
- **Тот же путь, что прод.** Харнесс строит **реальные** `extractor`/`resolver` через существующий композиционный корень (`resolve.build_extractor`/`build_resolver`), меняя только конфиг варианта. Eval гоняет ровно прод-конвейер, а не его копию → результат честный.
- **Граница `eval → app` односторонняя.** `app` НИКОГДА не импортирует `eval`. (Кандидат в import-linter forbidden-контракт — добавит интегратор, не блокер для черновика.)
- **Кэш по хэшу входа** (`вход + модель + версия промпта`) → повторные прогоны бесплатны, варианты сравниваются на идентичных входах, лимиты OFF/Groq не жгутся. Очистка — удалить `.cache/`.
- **Модель-агностичность (I7) — заодно проверяется.** Вариант = «реализация `Extractor` + конфиг resolver». Свап Scout→Maverick внутри Groq — смена `model`-строки; кросс-провайдер (OpenAI/Gemini/Anthropic vision, раз центы ок) — **тонкий новый адаптер** за тем же контрактом `Extractor`/`NutritionLLM`, мерится идентично. Если адаптер встаёт без правки домена — контракт I7 доказан.

## 6. Матрица вариантов

Один датасет, разные конфиги; отчёт показывает, какую стадию двигает каждый.

| Вариант | Модель | Ретривал | Гарды | Гипотеза, которую проверяет |
|---|---|---|---|---|
| **V0 baseline** | Scout (free) | OFF, label-short-circuit | — | текущий прод; точка отсчёта |
| V1 +Atwater | Scout | OFF | Atwater-флаг/переспрос | ловит ли «ветчину-500» дёшево, без сети |
| V2 +штрихкод | Scout | OFF + barcode | — | пакеты: точный матч вместо OCR панели |
| V3 модель | платный vision-кандидат(ы) | OFF | — | стоит ли апгрейд центов (идентификация/OCR) |
| V4 +web (R2) | Scout | OFF + Compound-web | — | хвост домашних/непакетированных |
| V5 dish-сетка | Scout | ретривал+Atwater в dish/combined | Atwater | закрыть путь без сетки (combined) |

Конкретные платные модели и их актуальные цены/vision-бенчи **подниму вебом на шаге V3** (меняются часто; по памяти числа не фиксирую). Варианты независимы — порядок прогона по приоритету С.

## 7. Прогон и отчёт

- CLI: `python -m eval.nutrition.run --dataset eval/nutrition/dataset/cases.jsonl --variant v0,v2,v3`.
- Выход: `eval/nutrition/reports/<дата>-<вариант>.md` (+ `.csv`): таблица метрик §2, разбивка **по тирам**, и **worst-N кейсов** (наибольшая ошибка ккал) — чтобы глазами увидеть провалы класса «ветчина-500».
- Сравнение вариантов — отдельная таблица «вариант × метрика» на общих кейсах.

## 8. Связь с фиксами (гейт перед прод-изменением)

Харнесс — **гейт**, а не просто отчёт: фикс уезжает в прод-домен только если eval показал выигрыш на релевантном тире **без регресса** на других. Конкретно:
- штрихкод (V2) обязан срезать MAPE ккал на Tier C/пакетах;
- Atwater (V1/V5) обязан ловить класс «ветчина-500», не зафлуживая нормальные позиции (ложные флаги < порога);
- платная модель (V3) обязана бить free на величину, оправдывающую центы;
- R2-web (V4) обязан улучшать домашний хвост, не ломая бренды.

Это прямой перенос fail-loud-философии ADR-0002 в измеримую плоскость.

## 9. Тест-план самого харнесса

Метрики и матчинг (`metrics.py`, `matching.py`) — чистые функции → юнит-тесты pytest **на синтетике** (без сети): Atwater-residual на известных Б/Ж/У; MAPE/MAE на заглушках; матч позиций с alias-map; пропуск метрики порции при `grams=null`. Кэш — на временной директории. Живых вызовов в pytest по-прежнему нет (герметичность сохраняется).
