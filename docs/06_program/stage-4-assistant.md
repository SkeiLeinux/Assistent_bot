# Этап E4 — Ассистентский слой (stage-doc)

**Статус:** каркас этапа. Самый неопределённый — намеренно самый лёгкий по фиксации; уточняется на ревизии после выхода E2/E3 (данные появятся — сценарии станут конкретными).
**Драйвер:** «идеальный день» С. (сырые ответы, Б1-Q3) + Катины сценарии «что поделать вместе» (списки активностей/фильмов).
**Грунт:** E1-дайджест (ретро) — фундамент; E4 добавляет **forward**-проактивность и связки между доменами, отложенные ради слабой связности (DOMAIN_MODEL §5).

---

## 1. Цель и ценность

Бот перестаёт быть набором разделов и начинает **сам приходить с полезным**: утром — план дня, вечером — сценарий выбора, по запросу — ответы на вопросы о своих данных. Всё — поверх данных E1–E3, без новой write-модели (расширение read-side философии Analytics).

## 2. Объём этапа (фичи)

| ID | Фича | Прио | Суть |
|---|---|---|---|
| F4.1 | **Утренний план дня** | must | Push-композиция: напоминания на сегодня + дела (OPEN из TASK-списков с ближними датами) + тренировка (расписание/фаза цикла, если расшарено) + опц. меню-идея из ужинов. Состав/время — Q4 + ADR-0012. |
| F4.2 | **Вечерний сценарий** | should | «Чем займёмся»: подборка из FAMILY-списков идей/фильмов (нерешённые, давно added) + быстрый переход «выбрали → DONE». Лёгкая механика, не рекомендательная система. |
| F4.3 | **Вопросы к данным (LLM)** | should | Свободный вопрос в боте/Mini App («что у меня с питанием за неделю», «куда утекли деньги в мае») → LLM-композиция поверх `*.read`-проекций (НЕ сырого SQL) → ответ с цифрами. Границы свободы — ADR-0012. |
| F4.4 | **План закупок** | could | Перенесённая F2.8: список покупок ↔ ожидаемая стоимость (история цен E2-F2.7) ↔ план питания. Первая настоящая межконтекстная связка Lists↔Finance↔Nutrition — только здесь, осознанно. |
| F4.5 | Сверка чек↔список | could | «Купил всё или не всё по списку» (С.): сопоставление ReceiptItems с активным списком покупок → отчёт-отклонение. |
| F4.6 | План тренировки от ИИ | out | «Подробный план на тренировку» — рекомендательная зона с ответственностью; вне программы до явного запроса обоих. |
| F4.7 | **Календарь-вид (+ GCal-чтение)** | should | Идея С. (2026-06-10). Экран «неделя/месяц»: дела с `due_date` + напоминания + (E3) витамины/врачи — **read-композиция**, без своей write-модели (расширение плана дня F4.1). Опция: чтение личных GCal-событий через **секретный ICS-URL** (без OAuth — feasibility §4). **Предусловие:** ключ `due_date` в `specific_attrs` TASK/GIFT — дешёвая доработка Lists, кандидат ретро E1. Двусторонний синк и запись в GCal — не делаем (яма конфликтов); рабочий корп-календарь недостижим. |

**Вне объёма:** фото/«воспоминания» (Катя: «не приоритет, пока нет единого хранилища» — остаётся в Telegram); голос; автоматические действия без подтверждения (LLM никогда не мутирует данные сам).

## 3. Архитектурный характер

- **Без новой write-модели:** E4 — композиции поверх `contexts.*.read` + Reminders/Notifications. Растёт `analytics`/`assistant`-слой, не домены.
- **Связки доменов (F4.4/F4.5)** — впервые легализуются рёбра, отложенные DOMAIN_MODEL §5; каждое — через read-проекции и явное обновление import-linter-контракта, не прямые импорты.
- **LLM-границы:** ответы только из предоставленных проекций (контекст-инъекция), без свободного доступа к БД; бюджет — feasibility §3 (запас многократный).
- Push-каденс: утренний план = третья job общего scheduler (паттерн дайджеста, per-user время).

## 4. ADR этапа

ADR-0012 (бюджет проактивности: состав/каденс/тон плана дня, границы LLM-свободы, opt-out). Возможен **ADR-0014** (межконтекстные связки F4.4/F4.5: через что и какой ценой), если фичи войдут. _(0013 занят: nutrition-retrieval, ПРИНЯТ.)_

## 5. Вход/выход

**Вход:** E2+E3 выпущены и дают ≥1 месяц данных · Q4 заполнен · ревизия этого stage-дока по фактическим данным · ADR-0012.
**Выход:** план дня и вечерний сценарий в реальном использовании ≥4 дней/нед обоими; «вопросы к данным» отвечают без галлюцинаций по цифрам (выборочная сверка).
