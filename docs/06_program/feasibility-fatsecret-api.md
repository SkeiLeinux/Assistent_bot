# Feasibility — FatSecret Platform API как источник КБЖУ (ресторанное/брендовое RU)

**Дата исследования:** 2026-06-24
**Статус:** 🅿️ **ОТЛОЖЕНО (parking)** — не делаем сейчас (С., 2026-06-24: «слишком громоздко и непонятно»). Возврат — только если eval покажет, что ресторанное/брендовое это значимая доля ошибок и бесплатные пути её не закрывают.
**Контекст:** вырос из кейса «Комбо среднее с чикенбургером во Вкусно и Точка» — публичные КБЖУ есть в вебе, но нет в Open Food Facts (OFF — про штрихкоды упаковки, не про ресторанные блюда). Кандидат-источник за тем же портом резолвера, что OFF (ADR-0013, ось 2).

---

## Что выяснили (подтверждено по docs, 2026-06-24)

- **API реальный и подходящий по данным:** OAuth 2.0 (client credentials, Bearer 24 ч) + OAuth 1.0; методы `foods.search`/`food.get`; 2.3M+ продуктов, типы включают **branded** и **restaurant foods** (то, чего нет в OFF).
- **RU есть как регион:** `region=RU` (дефолтный язык русский) — данные по РФ в системе присутствуют.
- **НО RU — только на платном тире.** Локализация (доступ к не-US странам) — премиум-фича, доступна лишь аккаунтам **Premier**. Бесплатные тиры (Basic 5000/день; Premier Free для стартапов/НКО/студентов, unlimited) — **US only**.
- **Цена RU не публична:** Premier = «Upon request — based on market access», прайс по числу рынков; объёмного прайса по вызовам нет. Точную цифру даёт только их contact-форма.
- **Зацепка-дисконт:** доступ к non-US датасетам для проходящих по Premier Free eligibility (стартап <$1M / НКО / студент) предоставляется **со скидкой**. Наш профиль (некоммерческий пет-проект на двоих) под это подходит — но цифру всё равно надо запрашивать.
- **Не путать** с потребительской подпиской «FatSecret Premium» в приложении — это не Platform API.

## Почему отложено

- Платная **обязательная** зависимость → против NFR «бесплатный стек» (драйвер 3 ADR-0013).
- Цена неизвестна и sales-gated → нельзя оценить ROI до eval.
- Громоздкость онбординга (заявка на Premier Free → запрос котировки RU → интеграция OAuth) не оправдана, пока не доказано, что класс ошибок значим.

## Бесплатные альтернативы для того же класса (ресторанное/брендовое RU)

1. **Ручной ввод в каталог + кэш `SharedFood`** — для регулярно заказываемых сетей (одни и те же 5–10 комбо): один раз внёс → мгновенно и точно из базы. Для 2 пользователей, вероятно, самое разумное.
2. **Веб-фолбэк Compound (R2, spec-nutrition-retrieval §8)** — бесплатно, негарантированно, с риском галлюцинации; проверяется в eval (вариант V4).
3. **Мини-адаптер под сайт конкретного бренда** — хрупко, оправдано максимум для 1–2 любимых сетей.

## Триггер возврата и план, когда вернёмся

**Триггер:** eval-отчёт показывает, что ресторанное/брендовое — значимая доля ошибки ккал, и пп. 1–3 её не закрывают.

1. Собрать и отладить адаптер на **бесплатном Premier Free (US)** — весь путь (OAuth2, `foods.search`, маппинг полей) проверяется за ноль; платим за RU только если решение оправдано.
2. Запросить котировку RU-рынка со скидкой (contact-форма, тип Premier Free → non-US, некоммерческий характер).
3. Если цена адекватна — добавить `FatSecretSource` как ступень резолвера между OFF и web (тот же контракт `NutritionSource`, ADR-0004), провенанс `source="fatsecret"` с цитатой.
