# Программный roadmap — от MVP до полного ассистента

**Дата:** 2026-06-10 · **Статус:** черновик на приёмку (С. + Катя)
**Что это:** карта этапов продукта E1–E5 поверх build-плана MVP (`05_implementation/roadmap.md` — он про срезы внутри E1 и не меняется). Источник объёма — North Star backlog (`MVP_Requirements.md` §8) + сырые ответы (`00_discovery/discovery-raw-answers.md`) + feasibility (`feasibility.md`).
**Принцип глубины:** детальное ТЗ пишется **на входе этапа**, не заранее (точность падает с горизонтом; вход = stage-doc + заполненный опросник + gate-тест + ADR этапа → `spec-writer-agent` собирает черновик ТЗ за один проход). Stage-доки здесь — стабильный каркас: цели, фичи, доменные дельты, ADR-кандидаты, гейты.

## 2. Гейты (вход/выход этапа)

Каждый этап открывается и закрывается явно — это анти-протухание доков и анти-долгострой.

| Этап | Гейт на вход (до ТЗ) | Гейт на выход |
|---|---|---|
| E2 | Опросник Q2 заполнен · gate-тест чеков пройден (10 QR через proverkacheka / ТУ ФНС прочитаны / 2 чека через vision) · ADR-0006/0007 приняты | Месяц реальных трат вносится в боте без таблицы; таблица в архивном режиме; ретро «что упростить» |
| E3 | Q3 заполнен · gate-тест Huawei-zip на своих аккаунтах (метрики читаемы) · ADR-0008/0009 приняты | Huawei-импорт раз в ≤2 недели — рутина; вес/тренировки/витамины живут в боте |
| E4 | Q4 заполнен · E2+E3 дают данные ≥1 месяц · лимиты Groq пересчитаны по факту | Утренний план и вечерний сценарий используются ≥4 дней/нед обоими |
| E5 | Триггер ADR-0005 наступил · ADR-0010 (auth) принят | Фронт работает вне Telegram у обоих; TG остаётся каналом push |

**Ревизия программы:** после каждого выхода-гейта — 30-минутная ревизия следующего stage-дока (обновить по реальности, а не по памяти полугодовой давности).

## 3. Сквозные архитектурные правила программы (E2–E5)

1. **Монолит до E5 включительно** (frozen §5 CLAUDE): новые контексты = новые пакеты в `app/`, не сервисы.
2. **Всякая внешняя интеграция = заменяемый ACL-адаптер** по образцу Import ACL финансов: xlsx бюджета (E1) → чек-канал (E2) → Huawei-zip (E3). Домен видит нормализованную модель, источник меняется заменой адаптера. Это главный переиспользуемый паттерн программы.
3. **Все LLM-вызовы — через единый провайдер-агностичный `llm_service`** (лимиты и смена провайдера лечатся в одной точке).
4. **Видимость** — только kernel-модель `scope`/`hidden_from`; health-данные по умолчанию `PERSONAL` (расшаривание — явное действие).
5. **Каждая новая фича ввода данных** наследует паттерн `analyze → confirm → save` (LLM не пишет в БД без подтверждения человека).
6. **Pipeline этапа:** stage-doc → опросник → gate-тест → ADR → ТЗ (spec-writer-agent → ревью С./Катя → принятие) → волны агентов по `build-contract.md` → приёмка reviewer'ом → выход-гейт.

## 4. Реестр ADR-кандидатов программы

Нумерация продолжает принятые 0001–0005. Решения — на входе соответствующего этапа, не раньше.

| ADR | Этап | Тема | Ключевая развилка |
|---|---|---|---|
| 0006 | E2 | Канал получения чека | proverkacheka / офиц. API ФНС / lkdr / vision-fallback; комбинация и порядок деградации |
| 0007 | E2 | Смена SSOT финансов | Когда транзакции становятся источником истины; судьба Import ACL и таблицы (двойной период? экспорт-ритуал для Кати?) |
| 0008 | E3 | Канал Huawei-данных | privacy-zip ACL (рекоменд.) vs Health Kit API; периодичность, что делать с дублями |
| 0009 | E3 | Модель медицинских показателей | универсальная `Measurement(type, value, unit, at)` vs таблицы по типам; хранение исходников (PDF/фото) |
| 0010 | E5 | Аутентификация standalone | свой логин/TOTP vs OAuth-провайдер vs magic-link; миграция whitelist |
| 0011 | E2 | Категоризация позиций чека | правила/словарь vs LLM-подсказка vs ручная; обучение на истории |
| 0012 | E4 | Бюджет проактивности | состав/каденс плана дня; push vs «открыл сам»; границы LLM-свободы в формулировках |
