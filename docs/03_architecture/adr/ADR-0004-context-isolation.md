## Контекст

Стиль зафиксирован: **модульный монолит**, один процесс / БД / деплой; **DDD-lite, пакет-на-контекст** (свои `models` / `repositories` / `services` / `api`). Нужно зафиксировать **уровень кода**:

1. структуру пакетов;
2. где живёт общее ядро;
3. правила импортов между контекстами;
4. как **легитимно** пересекают границу Analytics (read-side) и Import ACL;
5. чем это принуждается (а не держится на дисциплине).

**Граф зависимостей** (domain §2), который код обязан повторять:

- все домены (Lists, Finance, Nutrition, Reminders) → **Identity & Sharing** (kernel) — единственная жёсткая зависимость;
- **Analytics** ⤍ читает Lists / Finance / Nutrition (downstream conformist, своей write-модели нет);
- **Reminders / Analytics** → **Notifications** → **Bot**;
- **Import ACL** → **Finance** (единственная внешняя граница, заменяемый адаптер);
- **Mini App** → все домены.

Без enforced-правил монолит эрозирует в big ball of mud — это и есть боль, которую изоляция предотвращает. Параллельно держим **шов под standalone** (domain §7): доменная логика свободна от Telegram/Mini App.

### Драйверы решения

1. **Слабая связность (domain §5):** единственная жёсткая зависимость — kernel; Analytics — conformist-читатель.
2. **Простота (NFR §5):** 1–2 разработчика, монолит — без церемонии гексагона на каждом стыке.
3. **Граница реальна, а не на словах:** эрозию должно ловить что-то помимо дисциплины.
4. **Шов под standalone (domain §7):** домены не импортируют слой доставки.
5. **Заменяемость Import ACL:** адаптер таблицы изолирован внутри Finance.

---

## Решение (принято)

**Вариант B** — пакет-на-контекст + общий `kernel` + **enforced allowed-edges** (import-linter), повторяющие граф §2. Analytics читает домены через их публичные `read`-модули (не внутренности); Import ACL — подпакет Finance; Notifications — supporting; слой `delivery` импортирует контексты, контексты `delivery` — нет.

Структура (эскиз):

```
app/
  kernel/                  # Identity & Sharing: User, Family, Membership, Invite; Shareable + visible_to()
  contexts/
    lists/        { models, repositories, services, api, read }
    finance/      { models, repositories, services, api, read, importing/* }   # importing = заменяемый ACL
    nutrition/    { models, repositories, services, api, read }
    reminders/    { models, repositories, services, api }
  analytics/               # read-side: импортирует kernel + contexts/*/read (и только их)
  notifications/           # supporting: импортируется reminders, analytics, delivery
  delivery/
    bot/                   # вход (запуск Mini App, initData) + push
    miniapp_api/           # REST для Mini App
  main.py                  # композиция: один event-loop (aiogram polling + aiohttp)
```

Контракты import-linter (текстовое отражение графа §2):

- `contexts.*` → только `kernel` (+ собственный подпакет). **Sibling-context импорты запрещены.**
- `analytics` → `kernel` + `contexts.*.read`. Доступ к `services`/`models` чужих доменов запрещён.
- `notifications` → только `kernel`; импортируется `reminders` / `analytics` / `delivery`.
- `finance.importing` — изолирован, импортируется только внутри `finance`.
- `delivery.*` → `contexts.*.api`/`services`, `analytics`, `notifications`, `kernel`. **Домены не импортируют `delivery`** (шов под standalone).

## Рассмотренные варианты

### Вариант A — Строгие порты / гексагон везде

Каждый контекст публикует формальные порты (интерфейсы) в `api`-модуле; кросс-доступ только через порты + адаптеры. Enforced import-linter.

| Измерение | Оценка |
|---|---|
| Сложность | **Высокая** |
| Чистота границ | Максимальная |
| Принуждение | import-linter |

**Плюсы:** предельно чистые контракты; идеален под будущее отделение в отдельные сервисы.
**Минусы:** церемония портов/адаптеров на каждый стык — оверкилл для монолита на 1–2 разработчика; замедляет MVP; бьёт по NFR простоты (драйвер 2).

### Вариант B — Пакет-на-контекст + kernel + enforced allowed-edges — РЕКОМЕНДУЕТСЯ

Границы реальны и принуждаются import-linter из графа §2; Analytics ограничен `read`-модулями; `delivery` изолирован.

| Измерение | Оценка |
|---|---|
| Сложность | **Средняя** |
| Чистота границ | Высокая (enforced) |
| Принуждение | import-linter (из графа §2) |

**Плюсы:** границы enforced без портовой машинерии; Analytics-связность сужена до `read`-модулей (драйвер 1); `delivery` изолирован (драйвер 4); прямо операционализирует domain §5/§7.
**Минусы:** нужно поддерживать контракт линтера при добавлении легитимных рёбер; `read`-модуль на домен — немного структуры. Пока нет CI — принуждение через тест/pre-commit.

### Вариант C — Разделение по соглашению (папки), без enforced правил

| Измерение | Оценка |
|---|---|
| Сложность | **Низкая** |
| Чистота границ | Низкая (на дисциплине) |
| Принуждение | нет |

**Плюсы:** ноль инфраструктуры, быстрый старт.
**Минусы:** границы держатся только на дисциплине; в LLM-ассистированной разработке с растущим кодом эрозия почти гарантирована. Противоречит драйверу 3.

## Анализ trade-off'ов

- Реальная боль — **эрозия монолита**; её ловит только **enforced**-граница. C полагается на дисциплину → отвергнут. A даёт чистоту ценой церемонии, не оправданной на этом масштабе и команде (драйвер 2). B — середина: принуждение без портовой машинерии.
- `import-linter` — лёгкая dev-time зависимость; контракт = текстовое отражение графа §2, дёшево держать в актуальности.
- `read`-модуль на домен — минимальная структура, окупается тем, что Analytics не лезет в чужие `services`/`models` (драйвер 1).
- `delivery`-изоляция даёт **standalone-шов (§7) бесплатно**: домены Telegram-агностичны by construction, а не по обещанию.

**Решение: Вариант B.**

### Под-вопросы для С.

1. **Принуждение:** `import-linter` сразу vs отложить до CI (пока — тест/pre-commit). Рекомендую **сразу** (контракт дёшев, эрозия дорога), запускать локально/в тесте до появления CI.
2. **Доступ Analytics:** через `contexts.*.read` (рекомендую) vs прямой доступ к `services`.
3. **Размещение Import ACL:** подпакет `finance/importing` (рекомендую) vs отдельный top-level пакет.

## Последствия

**Становится проще:**
- Границы enforced, не на словах; добавление контекста = новый пакет `contexts/<name>` (+ `read`-модуль, если читается аналитикой).
- Analytics-связность ограничена и явная.
- `delivery` изолирован → standalone-шов держится без доп. усилий.

**Становится сложнее / следить:**
- Поддержка контракта import-linter при добавлении легитимных рёбер.
- Дисциплина «домены не импортируют `delivery`».
- Пока нет CI — принуждение через тест/pre-commit, легко забыть прогнать.

**Пересмотреть ADR, когда:** появится несколько deployable-юнитов (отделение standalone) — часть рёбер станет сетевыми границами; или контекст разрастётся и потребует под-контекстов.
