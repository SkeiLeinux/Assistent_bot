## Контекст

Продукту нужны **три режима видимости** для разделяемых сущностей:

- **PERSONAL** — видит только владелец. (Дневник еды, личные списки.)
- **FAMILY** — видят оба партнёра. (Списки по умолчанию, бюджет, общий каталог блюд.)
- **HIDDEN-FROM-PARTNER** — принадлежит семье, но скрыто от конкретного партнёра. (Подарки: видит дарящий, скрыто от одаряемого.)

Текущая модель **бинарна**: `family_id` (видят оба) либо `user_id` (видит один). Третьего режима нет.

Условия, формирующие решение:

- Данные **сносятся, схема greenfield** (requirements §10) — видимость проектируется в модель сразу, не ретрофитом. Стоимость заложить третий режим сейчас ≈ 0.
- Видимость — **центральный шов** (domain §4): её несёт **каждая** разделяемая сущность во всех контекстах (Lists, Finance, Nutrition, Reminders), а read-side Analytics обязан её соблюдать. Механизм кросс-контекстный и выбирается **один раз**.
- Фильтр видимости применяется почти на **каждом чтении** — это горячий путь.

### Драйверы решения

1. **Простота (NFR §5)** — 2 пользователя, 1 семья, 1 сервер. Не строить генерик-ACL/RBAC под систему на двоих.
2. **Видимость — first-class** — свойство сущности, а не зашитая в домен логика (domain §4).
3. **Gift-кейс** — «семья минус конкретный участник» должно выражаться чисто.
4. **Эргономика запросов** — фильтр видимости должен быть дешёвым и единообразным (один `WHERE`, а не N join'ов).
5. **Слабая связность контекстов** — единый механизм из kernel; контексты зависят только от Identity & Sharing, не друг от друга (domain §5).
6. **Расширяемость без переинженеринга** — путь к более богатой модели в будущем не должен быть тупиком, но и не оплачивается сейчас.

## Решение (принято)

Принять **унифицированную inline-модель**. У каждой разделяемой сущности — владелец и дескриптор видимости:

- `owner_id` (User) — владелец/автор.
- `family_id` (Family) — семья, которой принадлежит сущность.
- `scope` ∈ `{ PERSONAL, FAMILY }`.
- `hidden_from` — **множество** `user_id`, исключённых при `scope = FAMILY` (пустое для обычных семейных данных; `[одаряемый]` для подарков).

Разрешение видимости для зрителя `v`:

```
PERSONAL → виден  ⟺  v == owner_id
FAMILY   → виден  ⟺  v ∈ family  И  v ∉ hidden_from
```

Ключевая идея: **HIDDEN-FROM — не отдельная третья ветка**, а `FAMILY` с непустым исключением. Три продуктовых режима сводятся к одному механизму (2 состояния enum + множество-исключение). `PERSONAL` сохраняется как явный scope (а не «FAMILY, скрытое от всех»), чтобы «личное по природе» и «скрытый подарок» оставались семантически разными и не зашивали размер семьи.

**Форма реализации:** kernel-миксин `Shareable` (предоставляет Identity & Sharing), применяется к каждой разделяемой модели. Чтения идут через единый helper `visible_to(viewer)` / базовый репозиторий, который генерирует единообразный фильтр. Так видимость не переписывается в каждом контексте.

## Рассмотренные варианты

### Вариант A — Унифицированный inline (`scope` + `hidden_from`) — РЕКОМЕНДУЕТСЯ

Дескриптор на самой сущности через kernel-миксин.

| Измерение | Оценка |
|---|---|
| Сложность | **Низкая** |
| Эргономика запросов | **Высокая** — один `WHERE` на чтение |
| Связность | Низкая — контексты зависят только от kernel-миксина |
| Расширяемость | Средняя — изменение локализовано в миксине + helper |

**Плюсы:** прямое кодирование ровно трёх нужных режимов; gift без спец-ветки; новые сущности наследуют видимость применением миксина; Analytics применяет тот же фильтр.
**Минусы:** поля видимости денормализованы на каждую таблицу (приемлемо — это её неотъемлемое свойство); риск «забыть» применить фильтр на новой модели → снимается прогоном чтений через kernel-helper и тестом-инвариантом.

### Вариант B — Отдельная сущность видимости

Отдельная запись `Visibility(object_ref, scope, hidden_from)` 1:1 на каждый объект; таблицы объектов остаются без полей видимости.

| Измерение | Оценка |
|---|---|
| Сложность | **Средняя** |
| Эргономика запросов | **Средне-низкая** — join объект→visibility на каждом чтении |
| Связность | Низкая |
| Расширяемость | Высокая (централизованно) |

**Плюсы:** логика видимости в одном месте; легко перечислить «всё скрытое»; единый аудит.
**Минусы:** полиморфная ассоциация (object_ref на разнотипные сущности) неудобна в SQL/SQLAlchemy; join/подзапрос на каждом чтении горячего пути; индексация по гетерогенным типам. Накладные расходы не оправданы на этом масштабе.

### Вариант C — Полноценный ACL-слой

Генерик-доступ: тройки `(subject, object, permission)`, RBAC-стиль.

| Измерение | Оценка |
|---|---|
| Сложность | **Высокая** |
| Эргономика запросов | **Низкая** — резолв прав подзапросами; нужен кэш |
| Связность | Низкая |
| Расширяемость | Максимальная |

**Плюсы:** произвольное шаринг, роли, внешние пользователи, гранулярные права — ложится на далёкий North Star (standalone, мультиюзер).
**Минусы:** грубый переинженеринг под 2 пользователей / 1 семью / 3 фиксированных режима. Жёстко нарушает NFR простоты. Мы строим ACL-движок под проблему, которой нет.

## Анализ trade-off'ов

- Нужны ровно **три фиксированных режима**, выражаемых как 2 состояния scope + множество-исключение. Это **закрытое крошечное правило** — Вариант A кодирует его напрямую с почти нулевой машинерией. B и C покупают обобщённость (централизация / произвольные ACL), под которую **нет требования**, ценой сложности на самом горячем пути (фильтр видимости — почти на каждом чтении).
- Слабая связность достигается в A через kernel-миксин: контексты зависят только от Identity & Sharing (domain §5). B/C тоже развязывают, но добавляют машинерию.
- Будущее: локальность изменения в A (один миксин + один helper) делает эволюцию к более богатому шарингу **сдержанным изменением, а не тупиком**. B/C сейчас не оплачиваем. Появится standalone/мультиюзер (North Star) — пересмотрим под реальные требования.
- Главный риск A — «забыть» фильтр на новой модели — снимается **структурно**: чтения идут через kernel-helper/базовый репозиторий, видимость не реализуется заново в контекстах.

## Под-решение: хранение `hidden_from`

Концептуально `hidden_from` — **множество** `UserId`. Варианты персистентности:

- **H1 — один nullable FK `hidden_from_user_id`.** Проще всего (1 колонка, тривиальный фильтр), но **зашивает «семья = 2»** (исключён максимум один). Не рекомендуется.
- **H2 — JSON-массив на миксине `Shareable`. РЕКОМЕНДУЕТСЯ для MVP.** Сохраняет семантику множества, без доп. таблицы и полиморфных join'ов; на SQLite — JSON-колонка, при переезде на Postgres → `jsonb`/`int[]` (+ GIN-индекс при необходимости). Фильтрация JSON БД-специфична — изолируется в kernel. На текущем объёме данных стоимость нерелевантна.
- **H3 — join-таблица `shareable_hidden_from(shareable_id, user_id)`.** Нормализовано, масштабируется на N исключённых, но доп. таблица + `NOT EXISTS`-подзапрос на каждой проверке. Уместно, если хочется нормализации с первого дня.

Рекомендация ADR была **H2** (множество сохранено, «2 пользователя» не зашиты, SQLite-дружелюбно). **→ Принято решением С. (2026-06-04): H3** — нормализованная join-таблица с первого дня.

> **Уточнение (2026-06-07, ТЗ Identity §7 + аудит F4.1):** H3 конкретизирован до **H3-a** — ассоциативная таблица **на каждую shareable-сущность** (`list_item_hidden_from` и т.п.) через mixin `declared_attr`, без единой полиморфной `shareable_hidden_from`. Единая-таблица форма (H3-b) рассмотрена и **отклонена** (общая база + join на каждом чтении). Семантика множества и «не зашито семья=2» сохранены.

## Последствия

**Становится проще:**
- Единый фильтр видимости во всех контекстах; подарки работают без отдельной кодовой ветки.
- Новые разделяемые сущности наследуют видимость применением kernel-миксина.
- Analytics read-side применяет тот же фильтр — нет видимостной логики по доменам.

**Становится сложнее / следить:**
- **Дисциплина:** каждая разделяемая модель обязана использовать миксин и ходить за чтениями через helper; пропущенный фильтр = утечка приватности. Митигировать базовым репозиторием + тестом-инвариантом «каждая shareable-модель фильтруется».
- Запрос по `hidden_from` БД-специфичен (SQLite JSON vs Postgres) — изолировать в kernel, остальной код агностичен.
- Модель предполагает **одну семью из двух**; богатый шаринг явно вне MVP.

**Пересмотреть ADR, когда:** появятся >2 участника в семье, несколько семей на пользователя, роли/права, или внешние (не-Telegram) пользователи (всё — North Star). Любое из этого → переоткрыть ADR-0001.
