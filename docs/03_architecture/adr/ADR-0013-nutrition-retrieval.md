## Контекст

Сейчас разбор еды (`POST /analyze`, `POST /foods/analyze`) считает КБЖУ **только оценкой модели** (`llama-4-scout`, промпты `_SYSTEM_PROMPT`/`_DISH_PROMPT`/`_COMBINED_PROMPT`). Локальной базы состава нет — числа выдаёт модель «из головы». Для брендовых продуктов это неточно: «молоко Домик в деревне 3.2%» имеет конкретный КБЖУ на упаковке, а не усреднённый.

Запрошенный сценарий (3 кейса, North Star «vision→поиск»):
1. **Текст** «200гр молоко Домик в деревне 3.2%» → найти КБЖУ именно этого продукта, вернуть на порцию.
2. **Фото этикетки + «200г»** → распознать название, найти КБЖУ, вернуть на порцию.
3. **Фото продукта (название/этикетка)** → распознать; если КБЖУ читается с этикетки на 100% → вернуть (масштаб на граммы); иначе → искать и вернуть.

**Ключевая техническая истина (фиксируем, т.к. ставилась как «Groq должен искать»):** LLM сам в интернет не ходит. Retrieval — **отдельная способность**: либо встроена у провайдера (Groq **Compound** — агентный веб-поиск на Tavily, отдаёт цитаты), либо реализуется своим tool-loop (Scout поддерживает function-calling) с вызовом внешнего API. Текущая `llama-4-scout` искать не умеет. **Смена модели поиск не добавляет** — поэтому DeepSeek не рассматривается как решение (к тому же его API не бесплатен и встроенного веб-поиска не имеет; см. feasibility).

### Драйверы решения
1. **Точность по брендам (RU):** реальный КБЖУ с упаковки, а не усреднённая прикидка.
2. **Анти-галлюцинация (health-инструмент):** числа — из проверяемого источника; цена тихой ошибки высока (ср. драйвер 4 ADR-0002).
3. **Бесплатный стек (NFR §5):** без новых платных обязательных зависимостей.
4. **Заменяемость источников (как ACL, ADR-0002):** каждый источник = адаптер за единым контрактом; добавить/сменить источник, не трогая домен.
5. **Модель-агностичность (I7):** retrieval ортогонален выбору LLM; контракт `NutritionLLM` сохраняется.
6. **Простота (NFR):** 2 пользователя — без векторной БД и тяжёлого RAG.
7. **Сохранить I5:** analyze→confirm→save; человек подтверждает (с провенансом — ещё важнее).

---

## Решение (принято)

Новый изолированный подпакет `nutrition/resolve/` (границы — по ADR-0004), порт `ProductResolver`. Конвейер **извлечь → разрешить → масштабировать → вернуть с провенансом**:

**1. Извлечение** (LLM, Scout; vision для фото, text для текста) →
`ExtractedProduct{ name, brand?, fat_pct?, portion_g, barcode?, per100g?, label_complete: bool, confidence }`.

**2. Разрешение КБЖУ** — детерминированная лестница, первый успех побеждает:
1. `label_complete` → значения с этикетки (поиск не нужен) — удачная ветка кейса 3;
2. `barcode` → Open Food Facts by barcode (самый точный матч);
3. Open Food Facts полнотекст (`brand + name + fat%`);
4. *(опц.)* Nutritionix NL / USDA — generic/англоязычные;
5. веб → **Groq Compound** (Tavily, цитаты) → Scout извлекает КБЖУ из выдачи;
6. оценка моделью (текущий путь) — помечается «прикидка».

**3. Масштаб** на `portion_g` (×g/100); возврат `ResolvedNutrition{ per100g, scaled, source ∈ {label, off, nutritionix, web, estimate}, source_ref? }`.

**4. Кэш = синергия со `SharedFood`:** найденное (кроме `estimate`) авто-кладём в каталог семьи → далее мгновенный пик из базы без LLM и без сети; каталог становится самонаполняющимся кэшем (гасит латентность и лимиты).

Контракт `NutritionLLM` остаётся (путь `estimate` и извлечение). `ProductResolver` — новый порт; источники (`OpenFoodFactsAdapter`, `CompoundWebAdapter`, …) — адаптеры за ним, заменяемы как finance-ACL. Без фича-флагов (решение С., 2026-06-13): резолвер всегда включён, надёжность — встроенной деградацией в estimate, откат — git; web — этап R2 (добавляется кодом, не рантайм-флагом).

## Рассмотренные варианты

### Ось 1 — Механизм retrieval

| Вариант | Сложность | Плюсы | Минусы |
|---|---|---|---|
| M1. Только Groq Compound (built-in web search) | Низкая | Готовый веб-поиск без своего ключа; цитаты; в экосистеме Groq | Чёрный ящик; веб-КБЖУ нестабилен/галлюцинабелен; vision у Compound не подтверждён → для фото всё равно 2 ступени |
| **M2. Свой резолвер: структурная база (OFF) первой + веб-фолбэк** (рек.) | Средняя | Точные per-100g для брендов; контроль; провенанс; источники-адаптеры заменяемы (драйвер 4) | Больше кода (HTTP-клиент, маппинги, кэш) |
| M3. «Пусть модель гуглит» (наивный) | Низкая | Минимум кода | Галлюцинации чисел в health-инструменте (драйвер 2) — отвергнуто |
| M4. Сменить LLM на DeepSeek | — | — | Не даёт поиск; API не бесплатен; vision не закрывает retrieval — **отвергнуто** |

→ **M2**, веб-фолбэк (ступень 5) реализуем **через Compound** (Tavily включён в Groq-использование — «бесплатный» веб без отдельного ключа).

### Ось 2 — Первичный структурный источник

| Вариант | Доступ | За | Против |
|---|---|---|---|
| **Open Food Facts** (рек.) | Free, без ключа (нужен User-Agent); barcode + полнотекст | Бренды + штрихкоды; КБЖУ на 100 г; 1.3M+ товаров | RU-хвост покрыт частично → нужна лестница |
| Nutritionix | Free 1000/мес, ключ; NL-эндпоинт | Хорош для generic «200g milk» | Англоязычно/USDA; слаб по RU-брендам |
| Web-only | — | Максимум охвата | Хрупко, без структуры, галлюцинации |

→ **OFF первой**, Nutritionix/USDA — опц. ступень для generic.

### Ось 3 — Чтение штрихкода

| Вариант | За | Против |
|---|---|---|
| В MVP резолвера | Топ точности по брендам сразу | +зависимость (JS ZXing/quagga или серверный pyzbar), +UX |
| **Фаза 2** (рек.) | MVP проще; barcode добавляем как ступень позже | Часть кейса 2 до фазы 2 идёт через OFF-поиск по названию |
| Не делать | Минимум | Теряем самый надёжный матч |

### Ось 4 — Провенанс и кэш

- **Рек.:** показывать пользователю `source` (и цитату для `web`); авто-сохранять найденное в `SharedFood`.
- Альтернативы: прятать источник (хуже доверие в health-инструменте); без кэша (лишние вызовы/лимиты).

## Анализ trade-off'ов

- **Структурная база первой** убивает главный риск — галлюцинированный КБЖУ (драйвер 2) — и даёт точные per-100g для брендов; веб остаётся фолбэком, не основным путём. Это тот же принцип «лучше громко не найти, чем тихо соврать», что и fail-loud в ADR-0002.
- **Compound для веб-ступени** даёт поиск без отдельного платного ключа (в 2026 бесплатные generic-search API почти исчезли: Tavily платный, Brave убрал вечный free-tier) — закрывает драйвер 3, не вводя новой обязательной интеграции.
- **Резолвер как набор адаптеров за портом** (драйвер 4, ADR-0004) — добавить Nutritionix/штрихкод/сменить базу = новый адаптер, домен не трогаем. Прямой аналог finance-ACL.
- **Синергия со `SharedFood`** превращает находки в кэш: латентность (1–2 LLM + 1–2 сети = несколько секунд) и лимиты (OFF 10–15/мин, Groq free) гасятся со временем; для 2 пользователей запас есть.
- **Vision у Compound не подтверждён** → для фото берём 2 ступени (Scout vision-извлечение → Compound/текст-поиск), а не одну.
- **RU-покрытие OFF частично** → лестница фолбэков обязательна; авто-кэш постепенно закрывает длинный хвост.

**Рекомендация: M2 + OFF-first + Compound-веб-фолбэк + штрихкод фазой 2 + провенанс показываем.**

## Последствия

**Становится проще / лучше:**
- Точный КБЖУ по брендам; меньше ручных правок на confirm-экране.
- Источники заменяемы; домен и контракт `NutritionLLM` не зависят от способа retrieval.
- Каталог `SharedFood` самонаполняется и ускоряет повторные вводы.

**Становится сложнее / следить:**
- +HTTP-клиент, маппинги внешних схем, кэш, нормализация запроса (риск дублей в `SharedFood`).
- Латентность выше (спиннер уже есть; кэш помогает).
- Зависимость от доступности OFF/Compound; нужны таймауты и graceful-деградация по лестнице.
- Поддержка провенанса в контракте и UI.

**Пересмотреть, когда:** Compound получит подтверждённый vision (упростит фото-ветку до 1 вызова); появится своя/локальная база состава; RU-покрытие потребует платного источника; при переходе на E3-Health (общий слой извлечения из фото — возможна унификация с медблоком F3.5/F3.7).

## Ревизия 2026-07-27 — label-preferred вместо label-short-circuit

**Что пересматривается:** правило №1 лестницы («Решение», ось 1; ТЗ `spec-nutrition-retrieval.md` §4). Было: `label_complete=true` → немедленный возврат `source=label`, сетевые ступени пропускаются. Стало: **label-preferred** — числа с этикетки остаются основными, но при наличии `brand` позиция всё равно сверяется с внешним источником, и расхождение показывается пользователю.

**Почему.** Замер vision-моделей на ярусе A (`05_implementation/llm-eval-results-2026-07-27.md` §7) выявил остаточный режим ошибки, о котором при принятии ADR-0013 не было данных: примерно на **8% этикеток** модель **верно опознаёт продукт и ошибается в числах на 5–35%** — списывает внутренне согласованный набор значений не из той строки или колонки таблицы. Такая ошибка:

- не ловится проверкой Атуотера — сумма сходится (тот же класс, что уже был зафиксирован в `llm-eval-dataset.md` §9 как урок процесса);
- не ловится пользователем — название верное, числа правдоподобные;
- получает **высший** провенанс `source=label` в UI.

То есть действующее правило показывает максимальную уверенность ровно там, где ошибка наиболее вероятна и наименее заметна. Это инверсия смысла провенанса, введённого этим же ADR (ось 4).

**Целевое правило** (решение С., 2026-07-27, вариант B из `spec-nutrition-llm-contract.md` OQ-1):

- `readout="label"` + проверки пройдены + `brand` есть + бюджет позволяет → запускается сетевая ступень;
- расхождение по kcal > `resolver_disagree_pct` (15%) → возвращаем **числа с этикетки** как основные, версию источника — как `alternative`, флаг `label_disagrees_with_source`, выбор делает пользователь на экране подтверждения;
- `brand` нет → сверка не запускается (шанс найти товар в OFF близок к нулю, а запрос стоит времени);
- проверки не пройдены → `readout` понижается до `estimate`, и позиция идёт в лестницу обычным порядком.

**Что НЕ меняется:** состав и порядок ступеней (OFF → web(R2) → estimate), заменяемость источников за портом `NutritionSource`, гарантия ответа, кэш в `SharedFood`, семантика `/foods/analyze`.

**Цена.** Сетевых запросов к OFF станет больше — сегодня label-позиции их не делают вовсе. Медианная латентность `/analyze` растёт на время ответа OFF (типично 0.3–0.8 с, потолок `off_timeout_s=2.5`) для позиций с брендом. Смягчение: фильтр по `brand`, существующий общий бюджет `resolver_total_budget_s`, кэш `SharedFood`, переиспользуемая `ClientSession`. Принято сознательно: 8% молча неверных КБЖУ дороже секунды ожидания.

**Реализация:** `04_specs/spec-nutrition-llm-contract.md` §7.

### Уточнение 2026-07-28 — гейт уверенности (обязательное условие)

Замер источника с прод-машины (`05_implementation/off-source-probe-2026-07-28.md`) показал, что посылка этой ревизии выполняется лишь наполовину: OFF товар **содержит** (подходящая карточка есть для 20 из 25), но **не опознаёт** — прод-логика `select_best` выбирает верную карточку в 36% случаев, и точность не растёт ни при каком пороге скора. При таком матчинге сверка не ловила бы ошибки этикеток, а производила бы ложные: в двух случаях из трёх пользователю показали бы расхождение с чужим товаром.

Поэтому сверка запускается **только при уверенном матче** — `match_confidence ∈ {exact, confirmed}` по **ADR-0019**: точный lookup по штрихкоду, прошедшему контрольную сумму, либо карточка, подтверждённая LLM-переранжированием. Неуверенный матч не показывается пользователю вовсе — ни альтернативой, ни предупреждением; ступень OFF в этом случае возвращает `None`.

Решение С., 2026-07-28. Само правило label-preferred не отменяется — добавляется предусловие его применимости.
