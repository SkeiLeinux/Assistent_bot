## Контекст

Reminders — новый контекст. Нужен механизм **срабатывания** напоминаний (`Reminder`: текст, время / recurrence, владелец) с доставкой push через Notifications → Telegram-бот. Тот же механизм расписания должен обслуживать **периодический ретро-дайджест** (push по каденсу).

Жёсткие условия среды (CLAUDE §9, requirements §5):
- **Один процесс, один event-loop:** aiogram polling + aiohttp уже крутятся в одном `asyncio`-loop; планировщик должен жить **внутри** него, без отдельного демона.
- **Без брокеров** (frozen §5): Celery/RQ/Kafka вне рассмотрения (2 пользователя, 1 сервер).
- **VPS ~3 ГБ / 1 CPU; systemd:** рестарты и деплои случаются → напоминания обязаны **переживать рестарт** и не теряться/не дублироваться.
- **SQLite сейчас → PostgreSQL планово:** состояние расписания должно быть DB-агностичным.
- Объём крошечный: единицы напоминаний, минутная точность достаточна (не секундная).

### Драйверы решения
1. **Жизнь в одном event-loop** — без внешнего процесса/демона.
2. **Простота (NFR), без брокеров** — не тащить тяжёлую инфраструктуру под 2 юзеров.
3. **Переживание рестарта/деплоя** — состояние в БД, не только в памяти; явная обработка пропусков (misfire).
4. **Без двойного срабатывания** — один процесс ⇒ простой guard, без распределённых локов.
5. **DB-агностичность** — переезд SQLite→Postgres не должен ломать планировщик.
6. **Один механизм на напоминания и дайджест.**

## Решение (принято)

**Собственный async poll-loop** в существующем event-loop; **таблица `Reminder` — единственный источник истины** (у каждого `next_fire_at`).

- Одна `asyncio`-задача-«тик» раз в **N сек (30–60)** выбирает «созревшие» (`next_fire_at <= now()`), для каждого: доставляет через Notifications, затем в одной транзакции вычисляет следующий `next_fire_at` (по recurrence) либо помечает одноразовое выполненным. Так состояние всегда в БД → рестарт/деплой переживается **бесплатно**.
- **Recurrence — простой:** `none | daily | weekly | interval(N)` + время. RRULE (iCal) — North Star.
- **Misfire (процесс лежал в момент срабатывания):** при старте/тике просроченные в пределах **окна-грейса** (конфиг, напр. ≤ несколько часов) срабатывают один раз («догнать»); за окном — **skip + пометка missed**. Без «шторма» повторов.
- **Без двойного срабатывания:** один процесс + переход состояния (`claimed→fired`/advance `next_fire_at`) в той же транзакции.
- **Дайджест — тот же loop:** периодическая job (например, ежедневно вечером / еженедельно) дёргает Analytics-композицию и шлёт push. **Каденс и состав — за продуктом** (Катя), на уровне ТЗ; планировщик лишь предоставляет триггер.
- Доставка — через **Notifications** (существующие алерты + новый push).

## Рассмотренные варианты — механизм срабатывания

| Вариант | Сложность | Плюсы | Минусы |
|---|---|---|---|
| **B. Свой async poll-loop** (рек.) | Низкая | Живёт в текущем loop; ноль новых зависимостей; `Reminder` = SSOT ⇒ переживает рестарт даром; DB-агностичен; полный контроль над misfire | Сами пишем recurrence + misfire (немного); гранулярность опроса 30–60 с (достаточно) |
| A. APScheduler (AsyncIOScheduler + jobstore) | Средняя | Готовые cron/interval-триггеры, misfire_grace_time, персистентный jobstore | Новая зависимость; jobstore — **вторая** персистенция рядом с `Reminder` (риск двух источников истины); pickled-jobs; переезд на Postgres тащит и jobstore; тяжеловато для объёма |
| C. Системный cron / systemd timers | Средняя | ОС держит расписание | **Ломает one-process/one-loop**; отдельные инвокации, общий bot-session/состояние неудобны; не ложится на пер-напоминание время. Отвергнут |

→ **B.** APScheduler (A) — разумная альтернатива, если предпочитаешь библиотечные recurrence/misfire вместо своих ~50 строк; но за SSOT всё равно держим `Reminder`, а не jobstore.

## Под-решения и подбор недоспек

- **Recurrence-модель:** `none | daily | weekly | interval(N)` + время (покрывает витамины/задачи MVP). RRULE — North Star.
- **Каденс ретро-дайджеста** (недоспека): планируется как периодическая job; **значение каденса — продуктовое** (рекомендация по умолчанию: еженедельно, вечер; подтвердить с Катей). Архитектурно — поддержано.
- **Источники дайджеста** (недоспека): состав (включая «выполненные/просроченные напоминания») — на уровне Analytics/ТЗ. Рекомендация была: включить сводку напоминаний. **→ Решено продуктом (Катя, 2026-06-07): сводку напоминаний в дайджест НЕ включать** (ТЗ Analytics I5). Состав — Списки+Финансы+Питание.
- **Семантика напоминаний** (недоспека):
  - *недоставка push* — Notifications: лог + один ретрай, при стойком фейле — алерт админу (переиспользуем существующий error-alert);
  - *ack / выполнено* — кнопка «выполнено» в push (минимум MVP);
  - *snooze* — «напомнить через 1 ч» опционально; глубокий snooze — пост-MVP.

## Анализ trade-off'ов

- Реальное требование — несколько напоминаний + периодический дайджест в **одном процессе**, переживая рестарты. Poll-loop (B) решает это с нулём зависимостей и **одним** источником истины (`Reminder`), что прямо отвечает драйверам 1–5. APScheduler покупает готовые триггеры ценой второй персистенции и переноса jobstore через миграцию БД — невыгодно при таком объёме. Cron ломает one-process — отвергнут.
- «Самописная recurrence/misfire» звучит как минус A→B, но для `daily/weekly/interval` это ~десятки строк, и мы получаем **явный контроль** над политикой пропусков (что важнее для «витаминного» сценария, чем универсальность RRULE).
- Один процесс снимает самую дорогую проблему планировщиков — координацию/локи; не платим за то, чего нет.

**Решение: B (poll-loop, `Reminder` = SSOT) + простая recurrence + misfire-грейс + дайджест как job.**

## Последствия

**Становится проще:**
- Планировщик — часть приложения; деплой/рестарт без потери напоминаний (состояние в БД).
- Один механизм на напоминания и дайджест; переезд на Postgres ничего не ломает.
- Нет новых инфраструктурных зависимостей.

**Становится сложнее / следить:**
- Свои recurrence + misfire (тесты обязательны: пропуск, повтор, переход через рестарт, грейс-окно).
- Гранулярность опроса = задержка до N сек (приемлемо).
- Каденс/состав дайджеста ждут продуктового решения (Катя) — отмечено как ТЗ-вход.

**Пересмотреть, когда:** появится много напоминаний/высокая частота (тогда индекс по `next_fire_at` и/или событийный таймер), несколько процессов (тогда лок/лизинг job), или потребность в сложных правилах (RRULE).
