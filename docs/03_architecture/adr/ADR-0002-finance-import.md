## Контекст

Источник истины финансов в MVP — **существующая Google-таблица** (`Бюджет_общий_2026.xlsx`); данные **импортируются → анализируются**, ввод транзакций в боте в MVP отсутствует. ACL должен превратить нерегулярный лейаут таблицы в чистую доменную модель Finance (`Category`, `BudgetPlan`, `ActualAmount`, `Income`).

**Структура источника** (выверено по реальному файлу `docs/Бюджет общий 2026.xlsx`, 4 листа Март–Июнь):
- один **лист на месяц** (Март/Апрель/Май/Июнь; до 12/год);
- **одна строка-шапка** (стр. 1); доход и расход — **параллельные колонки**, не вертикальные блоки:
  - доход — `A` источник, `B` План, `C` Факт, `D` Разница (источники: «Переход с предыдущего месяца», партнёры Катя/Сережа, Кэшбек, Прочее); ниже — **сводные строки** «Доход» (итог), «Дельта» (доход − расход), «Расход» (зеркало «Итога»);
  - расход — `E` категория, `F` План, `G` Факт, `H` % (доля, дробь); справа **дневная матрица** `I…AM` = дни 1–31;
- **иерархия двухуровневая, закодирована заливкой строки** (не отступом/жирностью; merge нет): родитель — заливка `FFF9CB9C`, подкатегория — без заливки, «Итог» — `FFD9D9D9`;
- **структурный инвариант** (держится на всех 4 листах, 10/10): `Факт` родителя = Σ `Факт` детей; дневная строка родителя = Σ детей;
- позиции строк и состав категорий **плавают по месяцам** (строка «Итог» 52/55/54); имена подкатегорий **не глобально уникальны** («Прочее» — и родитель, и подкатегория) → идентичность подкатегории = (родитель, имя); бывают пустые/незаполненные месяцы (Июнь).

> **Уточнение (2026-06-07, сверка с файлом в ТЗ Finance):** заливка `FFF9CB9C` маркирует родителя расхода **в колонке `E`**, но тем же цветом залита и сводная строка «Дельта» в доходном блоке (`A`). Поэтому детект родителя **скоупится на колонку `E`**, а доходные сводные (Доход/Дельта/Расход) распознаются **по имени**; расходные «Итог» — по `FFD9D9D9`/`FFFFE599`. Страховка прежняя — инвариант «родитель = Σ детей».

> **Уточнение (2026-06-10, реализация — Q-fin-1):** проверка 10/10 устарела вместе с живым файлом: на листе Май дневная строка **родителя** в источнике не пересчитана (производная/формульная, своей информации не несёт — мы её и не храним). Валидация скорректирована: `Факт родителя = Σ Факт детей` **и** `Факт ребёнка = Σ его дневных ячеек` (оба ≤1 ₽); дневная строка родителя **не валидируется**. Связка транзитивно покрывает целостность дневного агрегата. Принято С. (2026-06-10); ТЗ Finance I3/§7 v0.4.

Жёсткие условия:
- **Таксономия +/- фиксирована**, но строки иногда добавляются → категории — **управляемая расширяемая сущность**, импорт обязан **абсорбировать новые** (requirements §9).
- **Структура таблицы волатильна** — будет существенно переработана через несколько месяцев (переезд). Поэтому ACL — **заменяемый адаптер**; доменная модель от формы таблицы **не зависит** (requirements §10, domain §3.3).
- Разбивка по картам сознательно не нужна.

### Драйверы решения
1. **Заменяемость ACL:** смена таблицы → меняется только адаптер, не домен.
2. **Устойчивость к добавлению строк:** частое изменение — новые категории/строки, не смена структуры.
3. **Простота (NFR):** 2 пользователя, ~12 листов/год, импорт по требованию — без тяжёлой инфраструктуры.
4. **Безопасность данных:** лучше громко упасть на непонятной структуре, чем тихо импортировать мусор.
5. **Без лишних внешних зависимостей** (NFR §5): новые обязательные интеграции/авторизации — только при необходимости.

## Решение (принято)

ACL `finance/importing` (изолированный подпакет Finance, по ADR-0004) со связкой:

- **Доступ — загрузка `.xlsx`-файла** (через Mini App; пользователь экспортирует и загружает). Без Google API/OAuth в MVP.
- **Парсинг — структурный/эвристический:** колонки — по шапке (стр. 1: доход `A–D`, расход `E–H`, дни `I–AM`); **родитель определяется заливкой строки** (`FFF9CB9C`), подкатегория — без заливки; сводные строки («Доход»/«Дельта»/«Расход»/«Итог») распознаются и не путаются с категориями; **иерархия валидируется инвариантом «родитель = Σ детей»** (по Факту и по дневной матрице) — он же fallback, если заливка изменится. Без хардкода номеров строк (позиции плавают по месяцам).
- **Промежуточное представление → валидация → upsert:** парсер выдаёт структурированный intermediate (распознанные строки), затем валидация (родитель = сумма детей; План/Факт числовые; согласованность дневной матрицы), затем идемпотентный upsert в домен **по месяцу** (повторный импорт месяца перезаписывает его данные).
- **Нормализация таксономии:** детерминированная (trim/регистр/пробелы) + **таблица алиасов** для известных дублей (напр. «Тренировки»/«Тренеровки»); невиданная категория **создаётся как есть** и помечается на ревью (пользователь решает: алиас/слияние). **Без авто-слияния по нечёткому совпадению** (риск ложного склеивания разных категорий).
- **На структурном несоответствии — fail loud:** понятный отчёт о том, что не распозналось, без частичного «грязного» импорта.

## Рассмотренные варианты

### Ось 1 — Способ доступа

| Вариант | Сложность | Плюсы | Минусы |
|---|---|---|---|
| **A1. Загрузка `.xlsx`** (рек.) | Низкая | Ноль авторизации/инфры; ACL = чистая `bytes → домен`, максимально заменяема; импорт по требованию | Ручной шаг экспорта/загрузки |
| A2. Google Sheets API | Высокая | Живые данные без экспорта | OAuth/сервис-аккаунт + креды на VPS, сетевая зависимость, лимиты; жёсткая связка с Google; таблицу всё равно переработают → интеграцию тоже |
| A3. CSV-выгрузка | Средняя | Просто парсить | Теряет мульти-лист и дневную матрицу; лоссы структуры |

→ **A1.** Сервис-аккаунт Sheets API — North Star (когда таблица стабилизируется после переезда).

### Ось 2 — Стратегия парсинга

| Вариант | Сложность | Плюсы | Минусы |
|---|---|---|---|
| P1. Позиционный (хардкод диапазонов) | Низкая | Быстро написать | Хрупкий; ломается на любой сдвиг; противоречит волатильности |
| **P2. Структурный/эвристический** (рек.) | Средняя | Толерантен к вставке строк (частый случай — рост таксономии); изолирован в ACL | Нужны маркеры/эвристики; крупная переработка структуры = переписать адаптер |
| P3. Конфиг-описание маппинга | Высокая | Максимально rework-friendly (меняем спеку, не код) | Оверкилл для ~12 листов / 2 юзеров в MVP |

→ **P2.** P3 — естественная эволюция, если после переезда захотим переконфигурацию без кода.

### Ось 3 — Нормализация таксономии

- **Рекомендуется:** детерминированная нормализация (trim/регистр) + **таблица алиасов** известных дублей + создание невиданных категорий с пометкой на ревью.
- Отвергнуто: **авто-слияние по fuzzy-match** (Levenshtein и т.п.) — риск молча склеить разные категории; цена ошибки выше экономии ручного алиаса при таком объёме.

## Анализ trade-off'ов

- Самое частое изменение источника — **добавление строк/категорий**, не смена структуры. P2 это поглощает; P1 — нет. Полная переработка (переезд) ударит по любому парсеру — поэтому ACL изолирован и заменяем (драйвер 1), а не «защищён навечно».
- A1 держит ACL **чистой функцией `xlsx → домен`** — самый заменяемый и беззависимый вариант (драйверы 1, 5). A2 даёт живость ценой авторизации/связки с Google, не оправданной до стабилизации таблицы.
- Fuzzy-авто-слияние выглядит «умно», но молча портит данные (драйвер 4). Алиас-таблица + ревью безопаснее и расширяемо.
- Идемпотентный per-month upsert + greenfield-данные (сносятся) → никаких миграционных сложностей; повторный импорт безопасен.

**Решение: A1 + P2 + алиас-нормализация + fail-loud ACL.**

## Последствия

**Становится проще:**
- ACL — заменяемый `xlsx → домен`; переезд таблицы затронет только `finance/importing`.
- Новые категории абсорбируются автоматически (создаются), дубли лечатся алиасами без потери данных.
- Домен Finance чист и не знает про форму таблицы.

**Становится сложнее / следить:**
- Ручной шаг загрузки файла (приемлемо при каденсе «неделя/месяц»).
- Признак иерархии — **заливка строки** (хрупко к переформатированию); страховка — инвариант «родитель = Σ детей» и fail-loud при расхождении. Крупная переработка структуры = переписать адаптер (ожидаемо by design).
- Поддержка таблицы алиасов и очереди «категории на ревью».

**Пересмотреть, когда:** таблица стабилизируется после переезда (→ возможно Sheets API A2 и/или конфиг-маппинг P3); появится ввод транзакций в боте (North Star) — тогда таблица перестаёт быть источником истины.
