## Контекст

Сейчас — **SQLite + async SQLAlchemy 2.0 + Alembic**; переезд на PostgreSQL значится планово (requirements §5). Вопрос: **когда** — до постройки новых доменов (Finance/Reminders/Analytics), или позже по триггеру.

Условия:
- **Данные greenfield** (сносятся, схема с нуля) — раннего data-migration нет.
- **Один процесс / один event-loop** (aiogram polling + aiohttp + poll-loop ADR-0003) ⇒ фактически **один писатель**; single-writer SQLite не упирается.
- **VPS ~3 ГБ / 1 CPU**: отдельный Postgres-демон + бэкапы + пул = заметный ops-оверхед на крошечном сервере.
- **ORM DB-агностичен** (SQLAlchemy 2.0) + Alembic ⇒ порт малорисковый, если избегать SQLite-only SQL.
- Под `hidden_from` выбрана **join-таблица** (ADR-0001 H3), а не массив ⇒ Postgres-only типы не требуются.

### Драйверы решения
1. **Простота / YAGNI (NFR):** не вводить инфраструктуру без потребности.
2. **Низкая стоимость порта:** ORM + Alembic + малый объём + greenfield.
3. **Конкуренция записи:** один процесс ⇒ single-writer SQLite достаточно; станет узким при мультипроцессе/standalone.
4. **Эволюция схемы:** SQLite ограничивает `ALTER` (Alembic идёт через batch/пересоздание); но пока greenfield — схему **пересоздаём**, миграции реально нужны лишь с появлением ценных данных.
5. **Postgres-only фичи:** сейчас не требуются (массив не нужен; поиск списков в MVP — портируемый `LIKE`, FTS — North Star).

---

## Решение (принято)

**Остаться на SQLite в MVP; мигрировать на PostgreSQL по явному триггеру.** Код держать **DB-агностичным** (SQLAlchemy 2.0, без SQLite-only SQL; поиск — за абстракцией). До срабатывания триггера SQLite — более простой и корректный выбор (NFR).

**Триггеры пересмотра (любой → открыть миграцию):**
- появление **второго процесса / standalone** (например, отделение Mini App API или фронта) — нужен конкурентный доступ;
- переход к **реальной эксплуатации с данными, которые нельзя потерять** (с этого момента схема живёт через миграции, а не пересоздание);
- **рост данных/нагрузки** сверх комфортного для SQLite;
- потребность в **Postgres-only возможности** (конкурентные записи, специфические типы/индексы).

---

## Рассмотренные варианты

| Вариант | Сложность сейчас | Плюсы | Минусы |
|---|---|---|---|
| **A. SQLite в MVP, миграция по триггеру** (рек.) | Низкая | Ноль DB-ops сейчас; быстрый dev; greenfield-пересоздание; порт дешёвый (ORM) | Держать SQL портируемым; миграцию сделать позже (но осознанно) |
| B. Мигрировать на Postgres сейчас, до доменов | Средняя | Строим сразу на целевой СУБД; без порта потом; полноценный `ALTER` для миграций | Ops-оверхед на 3 ГБ/1 CPU; преждевременно; SQLite боли не создаёт; нет текущего триггера |
| C. Миграция на конкретной вехе | Низкая→средняя | Привязка к понятному моменту (первый домен в прод) | «Веха» = по сути триггер из A; отдельный вариант избыточен |

→ **A.** Учебная ценность переезда сохраняется: миграцию делаем **осознанно при реальном триггере** — это поучительнее преждевременной.

---

## Анализ trade-off'ов

- Текущей боли SQLite нет: один писатель, крошечный объём, greenfield. Postgres сейчас (B) платит ops-цену за выгоды, которых пока некуда приложить (драйверы 1, 3, 5).
- Главный довод за B — «не делать порт потом» и удобный `ALTER` при эволюции схемы. Но при greenfield ранняя схема **пересоздаётся** без миграций; необходимость миграций возникает ровно тогда же, когда возникает триггер на Postgres (реальные данные) — то есть A не создаёт лишнего порта, а откладывает его до точки, где он всё равно осмыслен.
- Риск A низок, потому что держим ORM-портируемость; стоимость соблюдать её мала.

**Решение: A — SQLite в MVP, переезд по триггеру, код портируемый.**

---

## Последствия

**Становится проще:**
- Ноль DB-ops на MVP; самый быстрый цикл разработки; свободное пересоздание схемы на greenfield.

**Становится сложнее / следить:**
- Дисциплина портируемости: избегать SQLite-only SQL. **Поиск списков в MVP — портируемый `LIKE`** (работает и на SQLite, и на Postgres); полноценная FTS-абстракция (SQLite FTS5 → Postgres FTS) **осознанно отложена в North Star** (аудит F4.4, объём крошечный). Движок поиска не «зашивается» в домен — замена остаётся дешёвой.
- Помнить про триггеры — не проспать момент, когда single-writer/ops станут узким местом.
- Alembic на SQLite использует batch-режим — учитывать при ранних миграциях (если они появятся до переезда).

**Пересмотреть, когда:** сработает любой из триггеров выше (мультипроцесс/standalone, реальные данные, рост, Postgres-only фича).
