## Часть 1. Блок 11 — отказоустойчивость LLM (ТЗ §8, ADR-0018)

### 1.1 Таймаут (§8.1)

`llm_timeout_s = 20.0` уже есть в конфиге и **не используется**. Передавать в SDK параметром
`timeout=`, не оборачивать в `asyncio.wait_for`: SDK корректно рвёт соединение, обёртка оставит
висящий сокет.

### 1.2 Ретраи (§8.2)

Реализовать таблицу §8.2. Уже сделано: ретрай на `finish_reason == "length"` и на невалидный JSON —
не переписывать, встроить в общую схему. Добавить:

- 429 → до `llm_retry_429` попыток, backoff 1 с → 4 с + jitter, уважать `Retry-After`;
- 5xx / timeout / обрыв → 1 ретрай без задержки;
- 4xx кроме 429 → **без ретрая**, дальше по матрице §8.3.

Ретраи первичны по отношению к переключению: сначала исчерпать попытки на модели, потом менять цель.

### 1.3 Вторичный таргет (§8.3)

`LLMTarget` уже существует — нужен **список** целей вместо одной. Вторичная — `gpt-5.4`, тот же вендор,
ключ, SDK и параметры. **Второго кодового пути возникнуть не должно**: если появляется ветка «если
вторичный, то иначе» — решение реализовано неверно.

**Матрица §8.3 сужена намеренно, это не упрощение.** Ключ и аккаунт общие, поэтому 401,
`insufficient_quota` и org-level 429 переключением не лечатся: вторичная цель добавит ещё
`llm_timeout_s` ожидания перед тем же отказом. Переключаемся **только** на отказах модельного уровня.
Реализуй классификацию из таблицы §8.3 явной функцией, а не цепочкой `except` — её надо тестировать.

Позиции, посчитанные вторичным таргетом, получают `warnings += ["fallback_provider"]`.

### 1.4 Startup-guard и суточная проверка (§8.4)

- При старте `GET {llm_base_url}/models` → есть ли `llm_vision_model`. Нет → алерт админу через
  существующий error-handler + старт на вторичном таргете.
- Та же проверка раз в сутки через generic `scheduler/` (ADR-0003).
- **Guard не блокирует старт.** Сеть недоступна → warning в лог и продолжаем. Бот, который не поднялся
  из-за недоступного `/v1/models`, хуже бота с неизвестным статусом модели.

### 1.5 Сессия OFF (§8.5, minor)

`OpenFoodFactsSource` создаёт `ClientSession` на каждый lookup. Держать одну на резолвер.
Приоритет низкий: после варианта D запросов стало ~16 % от позиций.

## Часть 2. C3a — сверка кДж с ккал (ТЗ v0.5: §3.1, §4.1, §6.3a)

### 2.1 Контракт

- `ExtractedItem` += `energy_kj_100g: float | None = None` — кДж «как напечатано». Транспортное поле,
  в БД не персистится, `Macros` не трогать.
- Промпт (§4.1): модель **транскрибирует обе величины и не пересчитывает ни одну в другую**. Строка
  `450 кДж/110 ккал` даёт `energy_kj_100g=450` И `kcal=110`. Плюс явный запрет подгонять макросы под
  калорийность.
- Убрать из промпта прежнюю инструкцию «если только кДж — раздели на 4.184»: это арифметика в модели,
  запрещённая L2 абзацем выше. Именно она и выстрелила.

### 2.2 Проверка

```
обе есть:   |kcal − kj/4.184| / max(kcal,1) > check_kj_kcal (0.05) → kj_kcal_conflict,
                                                                     readout: label → estimate
только kj:  kcal = kj / 4.184 в КОДЕ + note о пересчёте
оба null и readout == "label" → нарушение схемы (C1)
```

`check_kj_kcal = 0.05` в конфиг. **Порог не калибровать на эталонах и не расширять**: обе величины
печатает производитель, расходиться им можно только на округление (факт: 0.3–2.2 %). Это единственная
проверка, независимая от величины, которую проверяет, — расширение порога её обесценивает.

C3a **не отклоняет ответ**, как и все проверки §6 — только флаг и маршрут.

### 2.3 Границу применимости C3 зафиксировать, а не чинить

C3 (полоса `[3.6, 4.8]`) на дефекте F-01 молчит — модель подогнала макросы, и отношение вернулось к 1.03.
Это не баг порога: проверка, выведенная из тех же чисел, что проверяет, против согласованной подгонки
бессильна по построению. Полосу **не трогать**, она подтверждена данными для своего класса.

## Часть 3. SecretStr на ключи

- В `app/config.py` перевести на `pydantic.SecretStr`: `bot_token`, `llm_api_key`, `openai_api_key`,
  `openrouter_api_key`, `claude_api_key`, `gemini_api_key`.
- Все места использования → `.get_secret_value()`. Проверить особенно:
  - `default_target()` — там `if not settings.llm_api_key` и передача в `LLMTarget`;
  - `make_client()` — `api_key=` в `AsyncOpenAI`;
  - инициализация бота `bot_token`;
  - `scripts/check_*.py` — они читают ключ из `.env` напрямую, не через `Settings`, их можно не трогать.
- Проверка результата: `ValidationError` при лишнем ключе в `.env` больше не печатает значение.

## DoD

1. `pytest` целиком зелёный, `lint-imports` 8/8.
2. Юнит-тесты **C3a — 7 кейсов из ТЗ §12.2**, обязателен приграничный негативный контроль:
   - `kcal=450, kj=450` (реальный F-01) → срабатывает;
   - `kcal=110, kj=450` → молчит (2.2 %, округление);
   - `kcal=210.9, kj=873.2` → молчит (0.3 %, эталон A-16);
   - смещение на 4 % → молчит, на 6 % → срабатывает;

   - `kcal=null, kj=450` → `kcal` = 107.6 в коде, `note` выставлен;
   - полный F-01 (`kcal=450, protein=17, fat=40, carbs=2.5, kj=450`) → C2 и C3 **молчат** (это
     фиксация границы их применимости, а не баг), C3a срабатывает, `readout` понижен.

   `insufficient_quota` — это и есть проверка сужения матрицы.

   бюджетом. `model_not_found` → переключение без ретрая.
5. Тест: startup-guard при недоступной сети **не роняет старт**.
6. Тест: `ValidationError` конфига не содержит значения ключа.

8. **Регресс раннера обязателен** — промпт изменился, а это тот самый компонент, который мерился.
   `tests/eval/run_eval.py` на ярусе A: не хуже baseline (kcal ≤2 %: 92 %, БЖУ ≤2 %: 83 %,
   кДж-конфузий 0). Прогон делает С., ключ на его стороне. Если просядет — правка промпта, а не
   правка baseline.
