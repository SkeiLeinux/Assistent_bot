## 2. Три развилки, которые пришлось решать (не домысливать молча)

### 2.1 `NutritionLLM` как пятиметодный контракт распущен

ТЗ §4.3 требует одновременно: (а) «агрегация уезжает в `FoodService`» и (б) «контракт `NutritionLLM` сохраняется по сигнатурам». Вместе они несовместимы: методы `NutritionLLM` возвращают `NutritionResult`, то есть **уже агрегированный** итог — если оставить их, арифметика возвращается в LLM-слой. Попытка реализовать их поверх `LLMExtractor` даёт цикл `services ↔ resolve` и ломает контракт import-linter.

**Что сделано:** пять точек входа сохранены по сигнатурам **на `FoodService`** (`analyze_text`/`analyze_photo`/`analyze_dish_*`) — это и есть поверхность, от которой зависит API, роуты не менялись. Единственной LLM-зависимостью сервиса стал инжектируемый `Extractor`: одна операция, режим — параметр. Инвариант I7 сохранён (сервис вендора не знает), число швов уменьшилось с двух до одного.

**К решению С.:** формулировку §4.3 стоит поправить — «сохраняются сигнатуры пяти путей», а не «контракт `NutritionLLM`».

### 2.2 Проверки применяются в извлекателе, а не в `refine`

Псевдокод §7.2 ставит `run_checks(item)` внутрь `refine`. Но режимы блюда лестницу **не проходят вовсе** (расчётный путь, ADR-0013 §17) — при таком размещении половина путей осталась бы без проверок, а C6 (свойство набора, а не позиции) было бы негде считать. Проверки применяются один раз, сразу после схемы; `refine` читает уже понижённый `readout`, что эквивалентно `label_ok = readout=="label" and not checks.downgraded`. Поведение то же, покрытие шире.

### 2.3 Гейт `match_confidence` — заглушка асимметричная, и это осознанно

Блок 10 не входил в заход, но `refine()` по §7.2 содержит и проверки (блок 5), и гейт (блок 10). Гейт заведён функцией `pipeline.match_confidence()` с `TODO(блок 10)`: поля в ступени ещё нет, `getattr` вернёт `None`, гейт закрыт — блок 10 добавит поле, и гейт откроется сам.

**Но накрывает он пока только ветку сверки, а не обе, как в §7.2.** Причина: сверка с этикеткой — новое поведение (OQ-1), и без уверенности матча она производила бы ложные расхождения в двух случаях из трёх (матчинг 36%, `off-source-probe` §3). А выдача OFF на ветке `estimate` — поведение существующее (R1), и глушить его «до блока 10» значило бы снять ступень лестницы под видом заглушки. Отмечено комментарием в коде.

## 4. Приёмка: ярус A (25 кейсов, живой прогон)

Прогнаны **обе версии промпта на одном и том же коде** (ТЗ §12.3), v2 — дважды.

| Метрика | Baseline 27.07 | **v1 (тот же код)** | **v2 прогон 1** | **v2 прогон 2** | Порог |
|---|---|---|---|---|---|
| валидный JSON | 100% | 100% | 100% | 100% | 100% ✅ |
| kcal ≤2% | 92% | 92% | **92%** | **92%** | ≥92% ✅ |
| БЖУ ≤2% | 83% | 83% | **81%** | **81%** | ≥83% ❌ |
| кДж-конфузий | 0 | 0 | 0 | 0 | 0 ✅ |
| медиана задержки | 1.3 с | 1.19 с | 1.38 с | 1.14 с | ≤2.0 с ✅ |
| детектор рассинхрона: уверенных | 0 | 0 | 0 | 0 | 0 ✅ |
| **отказ вместо выдумки (A-07)** | — | 1/1 | **0/1** | **0/1** | все ❌ |

**v1 совпал с baseline покейсно, не только в среднем** — то есть код блоков 2–6 сам по себе регрессии не внёс, и сравнение версий промпта корректно.

### 4.1 Откуда −2 п.п. по БЖУ: ровно один кейс, воспроизводимо

Из 25 кейсов различается **один — A-31** (dual-table, батончик Bombbar; эталон 432 / 15 / 32 / 13):

| Прогон | name | per100g | БЖУ |
|---|---|---|---|
| v1 | «шоколад молочный с начинкой» | 432 / **7** / 32 / 13 | 2 из 3 |
| v2 ×2 | «макароны» | 432 / 15 / **1.5** / **73 (32)** | 1 из 3 |

Обе версии читают этот ярлык неверно, но **разные ячейки**: v1 промахивается по белку, v2 — по жирам и углеводам, зато берёт верный белок. Сальдо −1 макрос из 69. Kcal обе берут точно (432). Побочно v2 даёт абсурдное имя («макароны» на батончике) — отсюда же просадка `name` 96% → 88%.

Это не шум: два независимых прогона v2 дали одно и то же. Гипотеза — новая строка §4.1 про «колонку на 100 г, а не на порцию и не соседний столбец» на настоящей двойной таблице (40 г и 100 г параллельно) сдвигает внимание модели на соседний столбец вместо целевого. **Проверить это можно только правкой промпта, а его текст задан ТЗ дословно — поэтому не трогал.**

### 4.2 «Отказ вместо выдумки» на A-07 — v2 стало хуже, и это главный результат прогона

A-07 — этикетка, которую не смог прочитать человек (эталон продиктован С.). Правильный ответ — `readout ∈ {estimate, unreadable}`.

- **v2: `readout="label"`, kcal 281 при эталоне 425.8, `note=null`.** Модель заявляет, что списала числа с читаемой таблицы.
- v1: `label_complete=false` → в новом контракте это `estimate`, формально 1/1.

Оговорка, без которой сравнение вводит в заблуждение: **1/1 у v1 — не доказательство его честности**, а следствие того, что в двоичном контракте «неполная этикетка» была дефолтом. Содержательный факт другой: **трёхзначный `readout` вместе с формулировкой §4.1 «честный estimate лучше ложного label» не только не сдвинул модель к признанию, но и получил от неё активное `label`.** Ровно тот пункт ADR-0017 §17, ради которого поле вводилось, на единственном кейсе, который его проверяет, не выполнен.

Заодно это цифра в пользу решения из ADR-0013: экран подтверждения обязателен, автосохранение по фото недопустимо.

### 4.3 Детектор рассинхрона — 2 слабых сигнала, оба ложные

A-13 (общий токен «тунец»), A-31 (модель назвала батончик «макаронами» — совпало с именем эталона A-39). Уверенных — 0. Оба объясняются §4.1: подмены снимков нет, kcal совпадает со своим эталоном точно.

## 5. Приёмка: ярус C (живой прогон, режим `dish_combined`)

| Набор | C1 | C2 | C3 | C4 (эталон) | **агрег. (код)** | C5 | **C6 (код)** | C7 | C8 | вызовов |
|---|---|---|---|---|---|---|---|---|---|---|
| C-01 | ✗ | ✓ | 100% | 0.29% | **0.293%** | ✓ | ✓ | ✗ | ✓ | 1 |
| C-02 | ✓ | ✓ | 75% | 10.40% | **0.308%** | ✓ | ✓ | ✓ | ✓ | 1 |
| C-03 | ✓ | ✓ | 83% | 36.05% | **0.241%** | ✓ | ✓ | ✓ | ✓ | **2** |
| C-04 | ✓ | ✓ | 83% | 9.94% | **0.292%** | ✓ | ✓ | ✓ | ✓ | **2** |
| C-05 | ✗ | ✗ | 75% | 5.73% | **0.118%** | ✓ | **✓** | ✗ | ✗ | 1 |

**Гейт кода взят полностью:**
- C-03 обязан дать 2 вызова — дал 2. C-04 обязан дать 2 вызова и **одну** позицию на повторный товар — дал 2 и 6 позиций на 6 ингредиентов (было 11 до фикса §5.1).
- C-05 обязан поднять `weight_mismatch` — поднял. C-01…C-04 обязаны промолчать — промолчали.
- Агрегация: расхождение прод-итога с независимым пересчётом **0.118–0.308%**, то есть только округление последнего знака на самом мелком макросе.

### 5.1 Ярус C поймал настоящий дефект блока 6 — дважды

Первый прогон дал у C-03 **10 позиций вместо 6**, у C-04 — **11**, итог C-04 384.7 вместо 208.7, и `weight_mismatch` ложно срабатывал на отрицательных контролях.

Причина: в составных режимах **текст состава уходит в каждый батч**, поэтому каждый батч перечисляет все ингредиенты. Второй батч честно отвечает `unreadable` по товарам, чьих этикеток на его снимках нет (новый контракт работает), либо `estimate` без бренда. Ни те, ни другие не схлопывались:

1. У `unreadable` нет бренда **по определению** — а бренд входит в ключ §5.5. Значит правило приоритета `label > estimate > unreadable` из того же §5.5 было **мёртвым кодом**: сработать оно не могло никогда.
2. У `estimate`-двойника бренда тоже нет, если этикетку видел только другой батч.

Исправлено двумя правилами: (а) отказ по продукту, который другой батч прочитал, сливается в прочитанную позицию по имени (и его `note` не показывается пользователю — иначе на прочитанной позиции появилось бы ложное «этикетка не читается»); (б) в **составных режимах** ключ дедупа — только имя: множество позиций задано составом, который модель получает дословно в каждом батче, поэтому два имени-близнеца это заведомо одна строка состава. На дневниковом пути ключ прежний — там разные бренды это разные товары.

**Это уточнение §5.5, а не отклонение по вкусу:** без него правило приоритета не исполнимо. Оба правила закрыты юнит-тестами (`test_dedup_unreadable_twin_merges_into_readable_one`, `test_dedup_by_name_only_in_composed_dish_modes`, сквозной пин `test_composed_mode_does_not_double_count_across_batches`).

### 5.2 Найдено: C4 в текущем определении не может быть «гейтом кода»

§3C.4 датасета объявляет C4 (допуск 0.5%) детектором бага **в коде агрегации**. Но считается он как «итог из per100g **модели** vs истина из эталонов», то есть в него напрямую протекает ошибка модели, которую C3 разрешает до 2%. Допуск 0.5% при разрешённой ошибке входа 2% — противоречие в определении: на C-03 C4 = 36% при полностью исправной арифметике.

Поэтому в раннер добавлена отдельная колонка **«агрег.»** — прод-итог против независимого пересчёта из **тех же** позиций. Эталон в неё не входит, ошибка модели не протекает, ожидается ~0. Это и есть чистый гейт кода; C4 оставлен как есть и трактуется как совместная метрика «модель + код».

**К решению С.:** либо переопределить C4 в §3C.4 на самосогласованность агрегации, либо поднять допуск до уровня C3 и признать его метрикой модели. Сейчас в отчёте показаны обе колонки.

### 5.3 C1/C7/C8 на C-01 и C-05 — артефакт сопоставления имён, не модели

- C-01: модель сказала «изделия макаронные», эталон — «Макароны "Спиральки-экспресс"». Токены не пересекаются («макаронные» ≠ «макароны»), позиция считается фантомом. **Итог при этом 450.3 — точно эталон.**
- C-05: обе творожные позиции матчатся на A-34 по общему токену «творог», A-35 остаётся непокрытым.

Лечится полем `synonyms` у ингредиентов набора C (в схеме яруса B оно уже есть) или лемматизацией. Кода не касается.

### 5.4 C9 (`dish_text`) — калибровочный прогон, порога нет

Средний промах `per100g` из памяти модели против этикеточной истины: **C-01 21%, C-05 156%, C-02/03/04 ≈ 200%**. То есть на брендовых товарах «типовые числа» расходятся с упаковкой в разы — это количественное подтверждение того, ради чего заводились и лестница источников, и сверка label-preferred. Пороги C9 назначать по этому прогону, как и планировалось (§7b шаг 6).
