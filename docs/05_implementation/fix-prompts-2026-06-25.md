## Промпт 1 — B1: ack повторяющегося напоминания висит вечно (фронт)

```
Контекст: app/delivery/miniapp_api/static/reminders.jsx. Баг (#1 в mvp-feedback-triage):
тап ✓ (ack) на ПОВТОРЯЮЩЕМСЯ напоминании → спиннер на карточке висит вечно.

Причина (подтверждена): функция doAck (~стр 363) ставит setBusyId(rem.id), затем в try
после reload() НЕ сбрасывает busyId; setBusyId(null) есть только в catch, в finally нет.
По ТЗ Reminders (форк C) ack повторяющегося — это «отметить этот раз», бэкенд оставляет
статус ACTIVE (пишет только last_fired_at). Поэтому после reload() карточка остаётся,
а busyId всё ещё = rem.id → спиннер не гаснет. У разового баг незаметен (карточка уходит в DONE).

Сделай:
1. В doAck перенести сброс busy в finally: setBusyId(null) выполняется и при успехе, и при ошибке
   (убрать его из catch, добавить блок finally { setBusyId(null); }).
2. Для повторяющегося — тост вида «Отмечено на этот раз» (для разового — текущий «Отмечено
   выполненным»); карточку повторяющегося оставить активной (она повторится в следующий цикл).
   Журнал срабатываний НЕ вводить.

Проверка: по возможности запусти Mini App локально и проверь оба сценария — ack recurring
(спиннер гаснет, карточка остаётся) и ack разового (карточка уходит). Если локальный auth
мешает — хотя бы убедись в корректности потока состояний и отсутствии висящего busyId.

Не коммить, не пушить. Покажи дифф.
```

## Промпт 2 — B2: push-кнопки в боте не убираются после нажатия (бэк)

```
Контекст: app/delivery/bot/setup.py (on_callback, ~стр 91-97) и app/delivery/bot/callbacks.py
(CallbackDispatcher). Баг (#11): после тапа по инлайн-кнопке push (ack/snooze) кнопки остаются
в сообщении, можно жать повторно.

Причина (подтверждена): on_callback делает только query.answer(...), сообщение не редактируется
(нет edit_message_reply_markup / edit_text). Диспетчер возвращает CallbackResult(answer, alert),
но никто не убирает клавиатуру. (Идемпотентность данных частично есть: повторный тап по DONE
даёт ReminderClosed → ответ «Напоминание уже закрыто», состояние не меняется — это сохранить.)

Сделай:
1. После УСПЕШНОЙ обработки callback в on_callback — убрать/перерисовать клавиатуру исходного
   сообщения: query.message.edit_reply_markup(reply_markup=None) (или заменить текст статус-строкой).
2. Статус-строка по типу действия (форк C):
   - recurring ack → «✅ Отмечено, повторится …»; разовый ack → «✅ Выполнено»; snooze → «⏰ Отложено до …».
   Чтобы прокинуть нужный текст, можно расширить CallbackResult полем (напр. edit_text: str | None,
   clear_markup: bool=True) и заполнять его в обработчиках reminders; минимальный вариант — всегда
   снимать клавиатуру после успешной обработки.
3. Сохранить идемпотентность: повторный тап по уже обработанному/закрытому → query.answer без эффекта.

Проверка: pytest на delivery/bot — после dispatch разметка снимается (edit_reply_markup вызван);
повторный callback по обработанному не меняет состояние. Фейки aiogram, как в существующих тестах.

Не коммить, не пушить. Покажи дифф и список затронутых файлов
(setup.py, callbacks.py, возможно reminders callback-handlers и notification_service).
```

## Промпт 3 — B4: кДж попадает в ккал (бэк, nutrition)

```
Контекст: app/contexts/nutrition/services/llm_service.py (промпт-инструкция про кДж/ккал на
~стр 114-115). Баг (#15a): энергоценность с этикетки в кДж иногда сохраняется как ккал
(пример: «496 на 100г» при макросах на ~119 ккал — это кДж, должно стать ~119 ккал).

Причина (подтверждена): кДж/ккал различает только ТЕКСТ промпта; детерминированной рантайм-
проверки после извлечения нет. Модель ошибается — ничто не ловит.

Сделай детерминированный guard после извлечения КБЖУ (чистая функция, юнит-тестируемая):
1. Atwater-сверка на 100 г: expected_kcal ≈ 4*белки + 4*углеводы + 9*жиры.
2. Если извлечённые kcal ≈ expected * 4.184 (т.е. отношение близко к 4.18 ± допуск) → это кДж,
   делим kcal на 4.184.
3. Верхняя планка правдоподобия (kcal/100г выше физически возможного, напр. >900) → флаг/повторный
   разбор или пометка низкой уверенности.
4. Логировать провенанс коррекции (что и почему поправлено).
Помести guard так, чтобы он работал на ОБОИХ путях (дневник и режим блюда). Учти клетчатку/алкоголь
как возможный источник лёгкого расхождения Atwater — не зафлуживать нормальные позиции.

Проверка: pytest юнит на guard — вход kcal=496 при макросах ~119 → нормализуется к ~119;
нормальные значения (kcal≈Atwater) не трогаются; экстремальные → флаг. Полный pytest зелёный.

Примечание: это прод-фикс; eval-харнесс (инкремент Q, вариант V1 Atwater) потом подтвердит эффект цифрой.

Не коммить, не пушить. Покажи дифф.
```
