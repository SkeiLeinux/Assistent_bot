# Замер: полезна ли ступень OFF на ветке `estimate` — ⛔ нет

**Дата:** 2026-08-03. **План (написан до прогона):** `off-value-probe-plan-2026-08-03.md`.
**Инструмент:** `scripts/check_off_value.py`. **Сырьё:** `tests/eval/runs/2026-08-03_{memory-tierA,off-value}.json`.
**Вердикт:** поисковая ветка OFF на `estimate` **портит числа, а не уточняет**. Развилка ADR-0019
закрывается **вариантом D** (только штрихкод).

---

## 1. Результат

Знаковый счёт по 25 кейсам яруса A, первичная метрика (свободных параметров нет):

| | |
|---|---|
| ближе память модели (M) | **13** |
| ближе карточка прода (S) | **7** |
| ничья (< 1 п.п.) | 5 |
| знаменатель | 25 |

Описательное, в решение не входит:

| | M — память модели | S — `select_best` прода |
|---|---|---|
| медиана ошибки ккал | **8,4 %** | 18,3 % |
| медиана ошибки БЖУ | 18,6 % | 31,6 % |
| грубых промахов (> 30 %) | 4 из 25 | **11 из 25** |

Худшие промахи S: 515 % (A-27, щавелевый суп), 461 % (A-33), 381 % (A-06), 182 % (A-09), 85 % (A-37).
Это не «неточность», это чужие товары.

**По правилу §0 плана, зафиксированному до прогона:** S проигрывает M → поисковый вызов убирается
из лестницы, вариант D.

---

## 2. Что при этом НЕ доказано

Данные в OFF хорошие. Честный потолок — **0,6 %** медианной ошибки, но только на **10 кейсах из 25**,
где карточка вообще проходит подпись по имени. То есть непригоден **поиск**, а не источник.

Отсюда штрихкод остаётся осмысленным: точный lookup по коду матчинга не содержит вовсе, а
контрольная сумма EAN отсекает неверно прочитанные коды (C4.0). 16 % позиций с нулём подмен — это
измеренное число из `veto-accuracy-2026-08-02.md`, здесь оно не пересматривалось.

**Асимметрия выборки (объявлена в плане §5).** 25 кейсов — брендированная упаковка, лучший случай для
OFF. Проигрыш здесь решающий: на тарелках и домашней еде карточек нет вовсе, там ступень тем более
бесполезна. Обратный вывод (выигрыш → полезна везде) был бы неверен, но он и не понадобился.

---

## 3. Независимые проверки

| | Результат |
|---|---|
| П1 подставная карточка из чужого кейса | медиана 59,7 % против 18,3 % у настоящей — **OK**, метрика различает товары |
| П2 истина против истины / join `id`↔эталон | ошибка 0, расхождений нет — **OK** |
| П3 знаменатели | 25 кейсов в кэше · 25 с полной карточкой · 25 с числами модели · 25 в парном сравнении |

П3 существенен: вывод сделан на полном знаменателе, а не на остатке после фильтров.

---

## 4. Побочные наблюдения (в решение не входят)

- **Память модели тоже врёт, и предсказуемо.** Четыре грубых промаха: A-15 корейка (120 % — типовые
  числа копчёной свинины против водно-инъекционного продукта), A-27 суп (90 %), A-31 макароны (63 %,
  сухие против готовых), A-34 творог (34 %). Класс один — продукты, где «типовое» и «конкретное»
  расходятся в разы. Экран подтверждения от этого не спасает: числа выглядят правдоподобно.
- **A-29 (карпаччо из индейки): `U имя` = 105 %** при `U ккал` = 1,5 %. Карточка прошла подпись по
  имени и при этом ошибается вдвое — то есть даже верное имя не гарантирует верные числа. Ещё один
  аргумент против сверки по имени и в пользу штрихкода.
- Кэш выдачи ни разу не потребовал сети: сравнимость с пятью предыдущими замерами сохранена.

---

## 5. Что делать

1. **Убрать `OpenFoodFactsSource` из `network_sources`** (`resolve/__init__.py`). Одна строка. Снимает
   до 2,5 с ожидания на позицию и 11 из 25 грубых подмен.
2. **Штрихкод** (ADR-0019 §2.2 + C4.0) — единственная оставшаяся форма обращения к OFF.
3. **Миграция транспорта на `search-a-licious` (§2.1) отменяется.** Она заводилась ради поиска;
   поиска больше нет, а для lookup по коду достаточно `api/v2/product/<code>` — стабильного и не
   затронутого поломкой Perl-бэкенда.
4. Вопрос «жив ли `cgi/search.pl`» (`field-defect-2026-08-02-kj-leak.md` §5) **снимается как
   неактуальный**: поисковый эндпоинт больше не вызывается ни в какой ветке.

---

## 6. Метод

Замер задумывался как проверка гипотезы «OFF полезен», а сработал как проверка **правила решения**:
критерий был назначен после чисел (решение С.), и это оказалось безопасно ровно потому, что первичная
метрика — знаковый счёт без единого настраиваемого параметра. Подгонять было нечего. Если бы метрика
имела порог, тот же порядок действий дал бы неотличимый от подгонки результат.

Второе: потолок считался в двух формах, и разница между ними — 1,4 % против 0,6 % на вдвое меньшем
знаменателе — снова показала тот же дефект, что уже переворачивал выводы ADR-0019. Выбор «ближайшей по
ккал» среди десяти кандидатов находит похожее **число**, а не верный **товар**. Форму `U ккал` держим
в отчёте только как заведомо оптимистичную границу.
