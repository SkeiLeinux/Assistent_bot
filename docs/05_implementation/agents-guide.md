## 2. Запуск волны — буквально, по шагам (на примере волны A)

**Как это устроено:** брифы из `.claude/agents/` Claude Code подхватывает автоматически как кастомных субагентов (проверка — команда `/agents` в сессии). Ты открываешь **одну** сессию Claude Code в корне репо — она оркестратор: спавнит субагентов параллельно, каждый получает свой бриф как системный промпт, работает в своём куске дерева и возвращает отчёт. Сессия живёт в терминале — «полдня автономии» = терминал открыт, машина не спит.

**Шаг 0 — чистая точка.** Предусловия волны сняты (`build-contract.md §1`); рабочее дерево закоммичено (коммит — точка отката волны, и итоговый diff волны = только работа агентов).

**Шаг 1 — запуск.** `claude` в корне репо, промпт дословно:

> Волна A по docs/05_implementation/build-contract.md.
> Запусти параллельно двух субагентов: finance-agent и nutrition-agent. Каждый работает строго по своему брифу: сначала тесты по A-критериям своего ТЗ, потом код до зелёного.
> Жёсткие правила: никаких alembic-миграций; не трогать чужие пакеты и общие файлы (build-contract §3); недоспецификация → парковка в docs/05_implementation/questions/, не выдумывать.
> Сам код за агентов не пиши — ты оркестратор. Когда оба закончат, покажи сводку: их отчёты (build-contract §7), парковки, git status по границам. Integrator НЕ запускай — он после моего ревью.

(Для других волн меняется список агентов; frontend-agent'у указывается экран: «экран Finance».)

**Шаг 2 — ушёл.** Агенты: читают вход → тест-скелеты → код → самопроверка DoD → отчёт.

**Шаг 3 — вернулся: 10-минутное ревью.** Читаешь сводку; `git status` — изменения только в `contexts/finance|nutrition/**` и `tests/test_*`; глазами — парковки `questions/*.md`. Проблема у одного агента → адресуешь точечно в той же сессии: «finance-agent: по пункту X — …».

**Шаг 4 — интеграция.** Там же: «Запусти integrator-agent по его брифу» (или руками по `build-contract §6`): deps волны (openpyxl) → **одна** миграция → монтаж REST → линтер-контракты → полный pytest + lint-imports → smoke `python -m app.main`.

**Шаг 5 — приёмка.** «Запусти reviewer-agent на волну A» → вердикт в `docs/05_implementation/reviews/`. Read-only, ничего не чинит.

**Шаг 6 — ты.** Разбор парковок (мелкое — решаешь в сессии, продуктовое — к Кате/в Cowork), фиксы по вердикту (возврат конкретному агенту), **коммит волны — твой**. Выход: волна B по тому же циклу.

**Анти-паттерны:** запускать analytics-agent до приёмки волны A (его вход не существует) · давать двум агентам пересекающиеся пути · разрешать агенту или оркестратору «быстренько поправить» чужой пакет/миграцию · принимать волну без reviewer-прогона A-критериев · запускать волну на незакоммиченном дереве.

## 3. Как добавить агента под новый контекст (E2+: receipts, health, assistant)

Скопировать ближайший по типу бриф (новый домен → `finance-agent`; решейп → `nutrition-agent`; read-side → `analytics-agent`) и заменить 5 секций: **Вход** (своё ТЗ + свои ADR) · **Граница записи** (`contexts/<новый>/**` + свои тесты) · **Что строишь** (из ТЗ) · **Не фантазировать** (OQ/решения своего ТЗ) · **DoD** (свои A-критерии). Затем: добавить строку в реестр §1, путь — в таблицу ownership `build-contract.md §3`, линтер-план — интегратору.
