## 1. Зачем это нужно

Датасет отвечает на **два разных вопроса**, и путать их нельзя:

| Задача | Вопрос | Живёт |
|---|---|---|
| **T1. Регрессия / порог приёмки** | «Текущая модель считает КБЖУ достаточно хорошо, чтобы её пускать в прод?» | Постоянно, прогоняется при каждой смене модели или промпта |
| **T2. Выбор провайдера** | «Какая из моделей-кандидатов лучше на *наших* фото?» | Разово сейчас (L1), затем при каждом депрекейшне |

T1 — основная. Vision-модель под нами сменилась трижды за 5 месяцев (Maverick → Scout → qwen3.6), и `qwen3.6-27b` в статусе `preview`, то есть сменится снова. Одноразовая проверка «вроде работает» умрёт вместе с моделью — как умер хардкод `[:5]`. Нужен набор, который переживает провайдера.

**Что этот датасет НЕ делает.** Это не бенчмарк моделей вообще и не замер «кто умнее». Только: русские этикетки, домашняя еда, наши промпты, наш JSON-контракт. Модель, выигравшая на MMLU, здесь может проиграть на мелком кириллическом шрифте — и нас интересует только второе.

## 2. Кандидаты для T2

Набор задан ADR-0017 §8/G и **окончателен: гео-проверка выполнена 2026-07-25** (`scripts/check_llm_providers.py` с прод-машины). Все четыре кандидата достижимы. **Gemini исключён — закрыт по гео** (`400 FAILED_PRECONDITION`), несмотря на VPS в Нидерландах: Google банит диапазоны датацентров, а не страны. Пересмотреть только при смене хостинга.

| Кандидат | Модель | Доступ |
|---|---|---|
| Groq (текущий) | `qwen/qwen3.6-27b` | есть ключ |
| Anthropic | Claude Haiku 4.5 | нужен ключ; OpenAI-compat через `base_url=https://api.anthropic.com/v1/` — вендор рекомендует compat именно для оценки, для прода — нативный SDK |
| OpenAI | GPT-5.6 Luna | нужен ключ |

Раннер логирует `usage` и латентность каждого вызова → **фактическая цена вместо оценок**. Оценки в ADR-0017 §4 (≈$1/мес) считаны по допущению 2000/300 токенов и должны быть заменены измерением.

## 3. Ярусы датасета

Разделение по **наличию эталона**. Мерить точность там, где эталона нет, — самообман.

### Ярус A — этикетки (ядро, N ≈ 20)

Одно фото упаковки с таблицей пищевой ценности. **Эталон объективен: числа напечатаны на упаковке.** Это единственный ярус, где можно говорить о точности.

Состав — не «красивые» фото, а те, на которых модели врут. Обязательные позиции:

| # | Ловушка | Почему в наборе |
|---|---|---|
| A-1…3 | **Только кДж** или кДж крупнее ккал | В промпте уже есть отдельный абзац «496 кДж ≠ 496 ккал» — значит эту ошибку уже ловили руками |
| A-4…6 | Мелкий кириллический шрифт, таблица боком | Основной режим отказа OCR на RU |
| A-7…8 | Блик / плёнка / мятая упаковка | Реальные условия съёмки на кухне |
| A-9…10 | Значения **на порцию**, а не на 100 г | Модель обязана не перепутать базу |
| A-11…12 | Указан и «в сухом виде», и «в готовом» | Двойная таблица — классический источник мусора |
| A-13…14 | Составной продукт (готовое блюдо в упаковке) | Проверяет, что модель не начнёт декомпозировать |
| A-15…20 | Обычные корректные этикетки | База; без них метрика ловушек не интерпретируется |

### Ярус B — тарелки и готовая еда (N ≈ 15)

Фото еды без упаковки. **Эталона не существует** — точный вес и состав не знает никто, включая того, кто готовил. Поэтому здесь мерится не правильность, а:

- **сегментация** — сколько отдельных позиций модель выделила против ручной разметки «что человек видит на фото»;
- **стабильность** — 3 прогона одного фото, разброс по kcal;
- **вменяемость** — попадание в экспертный коридор (ручная оценка ±30%), а не «правильное число».

Состав: 5 простых (2–3 явных продукта), 5 сложных (тарелка с 4+ компонентами), 5 без масштаба (нет столовых приборов/руки для оценки размера порции).

### Ярус C — составное блюдо (N ≈ 5 наборов)

4–6 фото этикеток ингредиентов + текст с граммовками. Прямая проверка решения **L2** (батчинг + суммирование в коде).

**Хитрость дизайна: ингредиенты берутся из яруса A.** Тогда эталон итога не оценивается, а *вычисляется точно*: `Σ (per100g_эталон × граммовка / 100)`. Ярус C получает объективный ground truth бесплатно — и одновременно проверяет, что арифметика в коде совпадает с ручным расчётом.

Один набор обязательно должен содержать **больше фото, чем лимит модели** (≥6) — иначе батчинг не проверяется.

## 4. Метрики и порог приёмки

### Ярус A

| Метрика | Как считается | Порог |
|---|---|---|
| **JSON-валидность** | Ответ парсится и проходит `NutritionResult` / `ExtractResult` | **100%** — иначе домен падает |
| **kcal-hit** | \|kcal_модели − kcal_эталона\| / эталон ≤ 2% | **≥ 90%** |
| **БЖУ-hit** | то же по каждому из protein/fat/carbs | ≥ 85% |
| **кДж-конфузия** | kcal завышен в 3.8–4.5× | **строго 0** — это грубая ошибка, а не неточность |
| **База per100g** | Модель не выдала «на порцию» за «на 100 г» | ≥ 95% |
| **Извлечение name/brand** | Заполнены и пригодны для поиска в OFF (ADR-0013) | ≥ 80% |

### Ярус B

| Метрика | Порог |
|---|---|
| JSON-валидность | 100% |
| Совпадение числа позиций с разметкой | ≥ 80% |
| Разброс kcal между 3 прогонами (coef. of variation) | ≤ 15% |
| Попадание в экспертный коридор ±30% | ≥ 80% |

### Ярус C

| Метрика | Порог |
|---|---|
| Отклонение итогового kcal от вычисленного эталона | ≤ 5% |
| Ровно одна итоговая позиция на выходе | 100% |
| Все ингредиенты учтены при числе фото > лимита | 100% |

**Гейт приёмки модели в прод (закрывает L5):** ярус A — все пороги; ярус C — все пороги; ярус B — не хуже предыдущей модели. Провал любого порога яруса A = модель не идёт в прод, даже если «в целом отвечает».


`manifest.yaml`, один кейс:

```yaml
- id: A-01
  tier: A
  image: images/A-01_kj-only.jpg
  trap: kj-only            # тег ловушки, для группировки в отчёте
  ground_truth:
    basis: per100g
    kcal: 119
    protein: 7.8
    fat: 4.2
    carbs: 11.5
    name: творог
    brand: Простоквашино
  note: на упаковке только кДж (496), ккал не напечатаны
```

**Про git.** ~40 фото × ~200 КБ ≈ 8 МБ — влезает в обычный git без LFS. Но это фотографии еды из дома и упаковок из холодильника: **перед коммитом проверить, что `SkeiLeinux/lifeManager_bot` приватный.** Если публичный — датасет держать вне репо, а в репо оставить `manifest.yaml` с путями и эталонами (эталоны и есть ценность; фото переснимаемы).

## 6. Контракт раннера

`tests/eval/run_eval.py` — отдельный скрипт, **не pytest**: он делает платные сетевые вызовы и не должен запускаться в общем прогоне.

```
python -m tests.eval.run_eval --provider groq --model qwen/qwen3.6-27b [--tier A] [--repeat 3]
```

Обязанности:

1. Читает `manifest.yaml`, гоняет кейсы через **тот же путь, что прод** — `LLMExtractor` / `LLMService`, а не свой отдельный промпт. Иначе замер не про прод.
2. Логирует на каждый вызов: сырой ответ, `usage` (вход/выход токенов), латентность, исключение если было.
3. Считает метрики §4, пишет `runs/<дата>_<модель>.json` + markdown-отчёт со сводной таблицей и **разбивкой по тегам ловушек** (важнее общего среднего: «90% в среднем, но 0% на кДж» — это провал, а не успех).
4. Считает фактическую цену прогона из `usage` × тариф модели.
5. **Побочно бесплатно:** отдельный кейс на фактический лимит изображений (отправить 4, 5, 6 фото) — снимает расхождение доков Groq «3 vs 5» и закрывает открытый вопрос ADR-0017 §11.

Провайдер задаётся флагом → раннер обязан ходить через ту же абстракцию, что предлагает ADR-0017 §6. **То есть раннер — первый потребитель этой абстракции и способ проверить, что она вообще годная, до того как на неё переведён прод.**
