# Задача для Claude Code: блок 15 — серверный кап и фронт

Текст для вставки в Claude Code целиком.

---

## Зачем

Три вещи, реализованные в бэкенде, до пользователя не доходят:

1. **Батчи** (блок 6) недостижимы через REST: `api/routes.py` режет ввод хардкодом `[:5]` в двух
   местах. Механика покрыта тестами и раннером, боевого пробега нет ни разу.
2. **`unresolved`** (§6.6): бэкенд честно возвращает 200 с массивом отказов, фронт про него не знает.
   При `readout="unreadable"` пользователь видит просто меньше позиций и никакого объяснения — то есть
   честный отказ модели выглядит как молчаливая потеря данных. Это хуже, чем было до §6.6.
3. **`warnings` и `alternative`**: флаги проверок §6 и вторая версия чисел при расхождении с источником
   не показываются. Экран подтверждения — единственная защита от остаточной ошибки модели (ADR-0017),
   и сейчас он показывает числа без единого признака того, что с ними что-то не так.
4. **`fallback_provider`** (блок 11): плашка о работе на резервной модели. Информационная, не
   предупреждающая — качество при варианте B ADR-0018 не падает.

## Часть 1. Серверный кап (обязательно первым)

- `api/routes.py`, два места: `[:5]` → значение из конфига. **Не литерал.** Это тот же класс хардкода,
  который ADR-0017 уже вычистил из LLM-слоя и который уцелел в слое роутов.
- Кап роута и `llm_max_images` — **разные вещи**: первый ограничивает, сколько снимков примет API,
  второй — сколько уходит в один запрос к провайдеру. Второй порождает батчи. Не схлопывать в одно
  поле: они разойдутся при смене модели.
- Значение серверного капа — 10 (ТЗ §5.2). Фронтовый кап поднять с 5 до 10 туда же.
- Тест: 8 снимков доходят до извлекателя все восемь и уезжают двумя батчами (проверять счётчиком
  вызовов фейка, а не результатом); 11 снимков → 400 с внятным текстом, а не молчаливая обрезка.

## Часть 2. `unresolved` на экране подтверждения

- Отдельный блок под списком позиций: «не удалось распознать» + `note` модели как причина.
- Действия на каждой строке: **удалить** и **ввести вручную** (имя + вес + КБЖУ). Не «переснять» —
  пользователь уже съел еду, повторная съёмка часто невозможна.
- Пустой `items` при непустом `unresolved` — валидное состояние, экран не должен показывать ошибку.
- Позицию без чисел сохранить в дневник **нельзя** (§6.6): запись с нулями выглядит как данные и
  портит итоги, цели и дайджест.

## Часть 3. Флаги и альтернатива

- `warnings` на позиции → компактный значок с расшифровкой по тапу. Тексты человеческие, не коды:
  `kj_kcal_conflict` → «на упаковке кДж и ккал не сходятся»,
  `arith_mismatch` → «числа не сходятся с составом»,
  `weight_mismatch` → «сумма ингредиентов не сходится с весом»,
  `barcode_invalid` → «штрихкод прочитан неверно».
- `alternative` (расхождение с источником >15 %) → показать обе версии и дать выбрать. Не подменять
  числа молча — принцип §2.4.
- `fallback_provider` → нейтральная плашка «посчитано резервной моделью». Серым, без восклицательных
  знаков.

## Часть 4. Провенанс — не трогать, но проверить

Бейдж `SourceBadge` уже есть. После варианта D значение `off` появляется **только** по штрихкоду.
Убедись, что подпись бейджа это отражает и не обещает поиск по названию.

## Чего в этом заходе НЕ делать

- `openapi.yaml` (блок 14) — отдельно.
- Наблюдаемость (блок 13) — отдельно.
- Схема БД, миграции.
- Редизайн экрана. Только добавление недостающих состояний в существующую вёрстку.

## DoD

1. `pytest` целиком зелёный, `lint-imports` 8/8.
2. Тесты капа из части 1 (включая «11 снимков → 400, не обрезка»).
3. Тест роута: ответ с непустым `unresolved` и пустым `items` — это 200.
4. Фронт собирается и открывается; проверено вручную, что каждое из четырёх состояний рисуется:
   `unresolved`, `warnings`, `alternative`, `fallback_provider`. Состояния можно проверить, подсунув
   ответ руками — живой отказ модели воспроизводить не требуется.
5. **UAT глазами.** Экран подтверждения — единственная защита пользователя от неверных чисел;
   принимать его без живого клика нельзя. Прокликать вдвоём с Катей: понятно ли, что означает значок,
   очевидно ли действие в блоке `unresolved`, не выглядит ли плашка резерва как ошибка.

## Замечание по формулировкам

Тексты на экране пишет продукт, не разработчик: формулировки выше — рабочий вариант, Катя может
переиграть любой. Что менять нельзя — **факт показа**: если проверка сработала или числа разошлись,
пользователь обязан это увидеть. Скрыть флаг ради чистоты экрана значит вернуть немой отказ, только
уже в UI.
