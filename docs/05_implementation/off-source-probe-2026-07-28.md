# Замер источника OFF с прод-машины — отчёт

- **Дата:** 2026-07-28 (прогоны — 2026-07-27/28)
- **Основание:** `04_specs/spec-nutrition-llm-contract.md` §12.4 — незакрытый вход «покрытие RU-брендов в OFF не измерено»
- **Где выполнялось:** VPS `skylineNiderland` (Нидерланды), `/opt/Assistent_bot`, прод-машина
- **Инструмент:** `scripts/check_off_coverage.py` (только stdlib, четыре итерации)
- **Данные:** 25 активных кейсов яруса A; запросы — то, что реально выдаёт прод-модель `gpt-5.4-mini` (`tests/eval/runs/2026-07-27_gpt-5.4-mini.json`), а не полные названия из эталона

> **Зачем меряли.** Калибровка проверок (`llm-checks-calibration-2026-07-27.md` §3) показала, что C2–C4 ловят **0 из 2** ошибок выбранной модели. Единственный оставшийся механизм против остаточных ~63% — сверка с внешним источником, то есть решение OQ-1 (label-preferred, ревизия ADR-0013). Цена вопроса высокая, а работоспособность источника никем не проверялась: сквозной live-прогон R1 на VPS по ТЗ так и не выполнялся.

---

## 1. Главный результат

**Ступень OFF в проде не работает и, судя по всему, не работала никогда.** Легаси-эндпоинт `/cgi/search.pl`, в который ходит `OpenFoodFactsSource`, отдаёт HTTP 503. То же и `/api/v2/search` — оба питаются одним устаревшим Perl-бэкендом.

Последствие для лестницы ADR-0013: `503` → `SourceError` → `warning` в лог → следующая ступень. То есть резолвер давно свёлся к `label → estimate`, а провенанс `source=off` не выставлялся никогда. Незамеченным это осталось потому, что наблюдаемости нет — дефект **D12** (`spec-nutrition-llm-contract.md` §9).

Это же объясняет два факта, которые до сих пор висели без причины:

- пункт **15c** триажа MVP («ретривал не даёт результата, добить label-path») оставался открытым;
- пункт **§5.1** триажа — «verify деплоя R1 в проде» — так и не был подтверждён документально.

**Замена существует и работает.** `search-a-licious` (`search.openfoodfacts.org`, Elasticsearch, статус beta) отвечает 200 за 0.10 с при прод-бюджете 2.5 с. Barcode-путь `/api/v2/product/{code}` тоже работает.

## 2. Установленные факты

| Что | Значение |
|---|---|
| `/cgi/search.pl` | ❌ HTTP 503 за 0.05–0.08 с, с первого запроса |
| `/api/v2/search` | ❌ HTTP 503 (тот же Perl-бэкенд) |
| `search-a-licious` | ✅ 200 OK, медиана **0.10 с**, максимум 0.33 с |
| `/api/v2/product/{barcode}` | ✅ работает |
| Ошибок запроса в финальном прогоне | 0 из 25 |
| **Покрытие базы** | **20 из 25** — подходящая карточка присутствует в выдаче |
| Ранжирование Elasticsearch | нужная карточка первая лишь в **7** случаях из 20 |
| **Точность прод-матчинга `select_best`** | **9 из 25 = 36%** |
| Выбран не тот товар | **16 из 25** — с провенансом `source=off` |
| Не уложились в прод-лимит 2.5 с | 0 из 25 |

### 2.1 Порог скора не помогает

| Порог | Осталось матчей | Из них верных | Точность |
|---|---|---|---|
| 0.0 | 25 | 9 | 36% |
| 1.0 | 24 | 9 | 38% |
| 2.0 | 15 | 6 | 40% |
| 3.0 | 12 | 5 | **42%** |
| 3.5 | 10 | 4 | 40% |
| 4.0 | 4 | 1 | 25% |
| 5.0 | 1 | 0 | 0% |

Точность не превышает 42% ни при каком пороге: отсечка выбрасывает верные матчи так же быстро, как неверные. **Скор не коррелирует с правильностью.**

Слепые кейсы показывают, что местами он ещё и инвертирован:

- `A-05` (Фетакса) — скор **1.82**, отклонение 13% → **попал**;
- `A-13` (онигири ВкусВилл) — скор **3.70**, отклонение 98% → **промах**, при том что нужная карточка лежала на ранге 2.

Это опровергает гипотезу, выдвинутую до замера («добавить `min_score` в `select_best`»). Чинить надо способ выбора, а не отсечку.

### 2.2 Почему скоринг сломан

`select_best` (§7.2 ТЗ R) складывает: бренд ×3.0 + доля токенов имени ×2.0 + близость жирности +1.0 + `completeness` (до 1.0).

| Причина | Данные |
|---|---|
| `brands` отсутствует у половины карточек | **10 из 20** — сильнейший признак (3.0) недоступен |
| `completeness` меряет не то | это полнота заполнения карточки, а не похожесть на запрос; при весе до 1.0 против 2.0 за имя хорошо задокументированный чужой товар обгоняет плохо задокументированный нужный |
| `_score` Elasticsearch игнорируется | единственная величина, специально построенная под релевантность, в формулу не входит вовсе |
| Жирность как признак ненадёжна | для сыра «45%» — это доля в сухом веществе, а не жир на 100 г; бонус не сработает или сработает неверно |

### 2.3 Новая форма ответа ломает маппинг, а не только URL

Перепись полей по 20 карточкам выдачи `search-a-licious`:

| Поле | Наличие | Тип | Замечание |
|---|---|---|---|
| `product_name` | 20/20 | `str` | имя кириллицей во всех 20 |
| `product_name_ru` | **0/20** | — | **поля не существует**; прод считает его основным в `_best_name` |
| `product_name_en` | 20/20 | `str` | |
| `brands` | **10/20** | **`list`** | прод `_first_brand` делает `.split(",")` → **AttributeError** |
| `completeness` | 20/20 | `float` | |
| `code` | 20/20 | `str` | |
| `_score` | 20/20 | `float` | новый сигнал, прод не использует |
| полное КБЖУ | 19/20 | | |
| `energy-kj_100g` | отсутствует | | фолбэк «из кДж» в `map_product` мёртв |

Плюс различия запроса: параметр `q` вместо `search_terms`, карточки в `hits` вместо `products`.

**Вывод:** адаптеру требуется переписывание запроса, маппинга полей и матчинга — сменой `base_url` не обойтись.

### 2.4 Barcode как обход ранжирования — не спасает

Проверены штрихкоды, которые вернула прод-модель на тех же 25 кейсах:

| Показатель | Значение |
|---|---|
| Модель вернула штрихкод | 12 из 25 (48%) |
| Из них пригодны для OFF | **4 из 25 (16%)** |
| Отсеяно контрольной суммой EAN | 6 — цифры прочитаны неверно |
| Отсеяно как внутримагазинные (`21`/`29`) | 2 — таких кодов в OFF нет по определению |

Побочная находка, полезная сама по себе: **контрольная сумма EAN — бесплатный детектор неверно прочитанного штрихкода.** Стоит поставить в слой проверок (§6 ТЗ) рядом с C2–C4.

## 3. Что это меняет в принятых решениях

| Решение | Статус после замера |
|---|---|
| **OQ-1 / ревизия ADR-0013** (сверять label с OFF) | Посылка «OFF умеет опознать товар» **не подтвердилась**: содержать умеет (80%), выбирать — нет (36%). Без починки матчинга сверка даёт ложную тревогу в двух случаях из трёх. → решение С. от 2026-07-28: **сохранить, но с гейтом по уверенности** |
| Гипотеза «добавить `min_score`» | **Опровергнута** (§2.1) |
| `off_timeout_s = 2.5` | Подтверждён с запасом ×25; менять не нужно |
| `off_base_url` в конфиге | Указывает на мёртвый эндпоинт |
| Barcode как «fast-follow» | Остаётся полезным, но покрывает 16% — не замена поиску |
| §12.4 ТЗ («покрытие не измерено») | **Закрыт**: покрытие 80%, проблема не в нём |

## 4. Урок метода — предлагается внести в DoD

Замер занял **четыре итерации**, и первые три дали правдоподобные, но неверные числа:

| Итерация | Результат | Чем оказался |
|---|---|---|
| v1 | «покрытие 8%» | следствие HTTP 503, а не отсутствия товаров |
| v2 | «покрытие 100%» | следствие того, что Elasticsearch всегда возвращает топ-20; скрипт брал первую карточку, минуя `select_best` |
| v3 | падение `AttributeError` | `brands` оказался списком, а не CSV-строкой |
| v4 | покрытие 80%, матчинг 36% | действителен |

Все три ошибки — одного класса: **внутренне согласованное число, измеряющее не то, что заявлено.** Та же природа, что у рассинхрона фото и эталонов (`llm-eval-dataset.md` §9) и у фильтра по `reasoning_effort`, отбросившего три четверти данных при калибровке (`llm-checks-calibration-2026-07-27.md`, врезка).

Что сработало как средство самоопровержения: **отдельный вопрос «а есть ли верная карточка в выдаче вообще»**. Именно он развёл «товара нет в базе» и «товар есть, но выбран не тот» — два диагноза с противоположными выводами (менять источник против чинить матчинг).

**Предложение в DoD любого замера:** результат обязан предъявлять не только число, но и независимую проверку, которая это число опровергла бы. Для покрытия такой проверкой был ранг верной карточки; для eval-прогонов — детектор рассинхрона `check_desync()`; для калибровки — распределение на эталонах, а не только на ответах моделей.

## 5. Что осталось неизмеренным

- **Точность LLM-переранжирования** — механизм, выбранный решением С. от 2026-07-28. Меряется на этих же 25 кейсах: верная карточка известна по близости ккал к эталону, ранг известен. Входит в DoD ADR-0019.
- **Покрытие за пределами яруса A.** 25 товаров — это упаковки из одного домохозяйства. Тарелки и ресторанные блюда (ярусы B/C) в OFF отсутствуют по природе, для них работает только веб-ступень R2.
- **Стабильность search-a-licious.** Статус beta, версия 0.1.0. Отдельного гарантированного SLA нет; ровно тот же класс риска, что привёл к ADR-0018.
- **Поведение при пустой выдаче.** В 25 кейсах ни разу не встретилось; ветка не проверена живыми данными.
