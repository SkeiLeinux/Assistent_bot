## Q-finance-1: дневной инвариант I3 vs реальный файл (A1) — ✅ РЕШЕНО
> **Решение (С., влито в spec-finance v0.4; сверено `reviews/review-finance-2026-06-10.md`):** вариант 2. I3 переформулирован — `Факт` родителя = Σ `Факт` детей **и** `Факт` ребёнка = Σ его дней (оба, допуск ≤1 ₽); дневная строка родителя — производная, не валидируется и не хранится. Реальный файл (лист Май) проходит. Обход в коде стал каноном.


- **Где:** spec-finance §6 I3 / §7 шаг 4 / §15 A1.
  - I3: «`Факт` родителя = Σ `Факт` детей **и** дневная строка родителя = Σ детей. Проверяется при импорте; расхождение → fail-loud (ничего не пишем)».
  - A1: «Импорт Март–Июнь из реального xlsx … инвариант `родитель = Σ детей` (факт + дни) проходит на всех листах».
- **Проблема:** в реальном `docs/Бюджет общий 2026.xlsx` лист **Май**, родитель **«Едовое»**: помесячный `Факт` родителя = Σ `Факт` детей (64406.55 ✓, в допуске ≤1 ₽), и каждый ребёнок самосогласован (его `Факт` = Σ его дней). НО **дневные ячейки самого родителя** в источнике заполнены неполно: Σ дней родителя = 54778.8 ≠ 64406.55; на днях 18/21/22 дневная ячейка родителя ≠ Σ детей (расхождения 412/8366/850 ₽). То есть строгий дневной чек I3 (родительская дневная строка = Σ детей, fail-loud) **отклонит реальный файл**, что прямо противоречит A1. Источник просто не поддерживает дневную строку родителя в актуальном состоянии (она — производная в Excel, но руками не пересчитана).
- **Варианты:**
  1. **Строгий I3 буквально** → fail-loud на Май → A1 не проходит на реальном файле. Противоречие ТЗ внутри себя; неприемлемо для приёмки A1.
  2. **Инвариант источника = только помесячный факт-чек** (`Факт` родителя = Σ `Факт` детей, допуск ≤1 ₽), а дневная согласованность проверяется **на уровне ребёнка** (`Факт` ребёнка = Σ его дней, допуск ≤1 ₽) — она в файле держится 100%. Дневную строку **родителя** при валидации игнорируем (она в домене не хранится: факт на листьях, родитель — агрегат, §4.4). Реальный файл проходит; молчаливого импорта мусора нет (две независимые суммовые сверки всё ещё ловят битую структуру).
  3. **Допуск на дневной чек родителя задрать** до макс. наблюдаемого расхождения — произвольный порог, маскирует реальные ошибки, отвергнут.
- **Обход в коде (временно реализован):** выбран вариант 2. Валидатор (`importing/validate.py`) проверяет: (a) `parent.fact == Σ child.fact` (|Δ|≤1 ₽), (b) для каждого ребёнка `child.fact == Σ child.days` (|Δ|≤1 ₽). Дневная строка **родителя** из источника не валидируется и не хранится (родитель-агрегат восстанавливается из дней детей). Тест A1 (`test_finance_import.py::test_real_file_invariant_holds`) проверяет именно эти две сверки на всех 4 листах. Тест A4 (fail-loud) ломает структуру так, что нарушается (a) или (b). **Нужно подтверждение С.:** заменить формулировку I3 на «факт родителя = Σ факт детей; факт ребёнка = Σ его дней» (дневная строка родителя — производная, не предмет валидации).

## Q-finance-2: семантика `metric` в GET /finance/analytics — ✅ РЕШЕНО
> **Решение (С., spec-finance v0.4; `reviews/review-finance-2026-06-10.md`):** параметр `metric` **снят** из контракта (`AnalyticsDTO` и так несёт все метрики plan/fact/diff/pct). Код его не парсит — де-факто no-op; поведение «показать всё» консистентно.


- **Где:** spec-finance §10 (`GET /finance/analytics?metric=&period=&from=&to=&category_id=`) и DTO `AnalyticsDTO`.
- **Проблема:** параметр `metric=` присутствует в сигнатуре, но его допустимые значения и влияние на ответ нигде не специфицированы. `AnalyticsDTO` всегда несёт `total:{plan,fact,diff}` и `lines:[{plan,fact,diff,pct,...}]` — то есть все метрики сразу. Что выбирает `metric`?
- **Варианты:**
  1. `metric` — необязательный фильтр представления (напр. `plan|fact|diff`), сервер всё равно считает всё, UI решает что показать → параметр де-фактоно-оп на бэке.
  2. `metric` переключает «единицу» агрегации (сумма vs %) — но `pct` и так в каждой строке.
  3. `metric` зарезервирован под North Star, в MVP игнорируется.
- **Обход в коде (временно реализован):** `metric` принимается и **игнорируется** (не влияет на ответ); ответ всегда полный `AnalyticsDTO` со всеми полями (plan/fact/diff/pct). Поведение видимое пользователю не меняется относительно «показать всё». Помечено для уточнения; смена семантики не затронет доменную модель/`read`, только сериализацию в `api/`.

## Q-finance-3: `IncomeReportDTO.carryover` — что именно — ✅ РЕШЕНО
> **Решение (С., spec-finance v0.4; `reviews/review-finance-2026-06-10.md`):** вариант 1/3 — `carryover` = Σ `actual` источников `kind=CARRYOVER` по целым месяцам периода (I10); те же источники остаются в `by_source` (дубль для UI). Семантика «остаток на начало» (вариант 2) сознательно не делалась.


- **Где:** spec-finance §10 DTO `IncomeReportDTO = {range, by_source:[…], carryover, total_income, total_expense, delta}`.
- **Проблема:** `carryover` вынесен отдельным полем рядом с `by_source`. Но «Переход с предыдущего месяца» — это уже источник (`IncomeSource.kind=CARRYOVER`), он попадёт в `by_source`. Дублировать ли его отдельным полем `carryover`, и что в нём — сумма факта carryover-источников за период? за какой месяц при мультимесячном периоде?
- **Варианты:**
  1. `carryover` = суммарный `actual` всех `CARRYOVER`-источников за целые месяцы периода (агрегат, удобство для UI), при этом он **также** присутствует в `by_source` (дубль для отображения).
  2. `carryover` = только первый/последний месяц периода (семантика «остаток на начало»).
  3. Поле информационное, в MVP = Σ факт carryover-источников периода.
- **Обход в коде (временно реализован):** вариант 1/3 — `carryover` = сумма `actual_amount` источников с `kind=CARRYOVER` по целым месяцам периода (I10), и эти же источники остаются в `by_source`. Семантика «остаток на начало» (вариант 2) не реализована — нужна явная отмашка, какой месяц считать.
