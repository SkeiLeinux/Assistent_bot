# lifeManager_bot → Семейный ассистент: Требования и границы MVP

**Версия:** 1.4 (структура источника финансов §4.2 выверена по реальному файлу)
**Статус:** принято (архитектура — Sergei; продукт — Катя). Дата приёмки: 2026-06-04
**Вход интервью:** Sergei — системный анализ / архитектура; партнёр — бизнес-анализ / продукт
**Дата:** 2026-06-03
**Назначение документа:** единый источник истины (SSOT) по объёму MVP. На него ссылаются последующие фазы — доменная модель, ADR, ТЗ. Детальные хотелки за границей MVP не дублируются здесь, а живут в North Star backlog (раздел 8).

## 1. Назначение и контекст

### 1.1 Что это
Эволюция уже существующего и развёрнутого `lifeManager_bot` в общий бытовой ассистент для пары. Цель — собрать повседневные функции (списки, финансовая аналитика, дневник питания) в одном структурированном месте взамен россыпи тематических Telegram-чатов и ручной работы в Google-таблице.

Это **brownfield по коду, но greenfield по данным**: значительная часть MVP уже реализована (раздел 3), но текущие данные тестовые и **подлежат полному сносу** — схема проектируется с нуля без миграционных ограничений (см. раздел 10).

### 1.2 Зачем — двойная цель
- **Продуктовая:** работающий инструмент для двоих, который реально открывают каждый день (желательная цель).
- **Учебная (основная):** пройти полный цикл LLM-ассистированной разработки (интервью → требования → архитектура → ТЗ → домены → код) и параллельно прокачать профессиональные навыки — системный анализ/архитектура (С.) и продукт/бизнес-анализ (партнёр).

### 1.3 Пользователи
Ровно **два** пользователя — пара. Масштаб минимальный. Это сознательно влияет на архитектуру: не закладывать многотенантность сверх «семьи», очереди, горизонтальное масштабирование и прочее, что оправдано только на больших нагрузках.

## 2. Глоссарий
- **Семейное (family-scoped)** — данные, привязанные к группе/семье; видны обоим партнёрам.
- **Личное (personal)** — данные, привязанные к пользователю; партнёр не видит.
- **Скрытое-от-партнёра** — третий режим (см. подарки, раздел 6): данные принадлежат семейному контексту, но скрыты именно от конкретного партнёра.
- **Пейринг** — связывание двух пользователей в группу/семью по инвайт-коду.
- **КБЖУ** — калории, белки, жиры, углеводы.
- **Дневник (питания)** — журнал приёмов пищи по дням.
- **План / Факт** — плановое и фактическое значение по статье бюджета (терминология их таблицы).
- **Ретро-дайджест** — сводка недавних событий/изменений по сферам («что произошло»), в отличие от forward-напоминаний («что предстоит»).
- **MVP** — минимальный объём, замороженный для первой версии (раздел 4).
- **North Star** — целевое видение полноценного ассистента; backlog (раздел 8), вне MVP.
- **Bounded context** — логическая граница домена со своей моделью; нарезка границ — задача следующей фазы.

## 3. Current-state: что уже есть

Источник — инвентаризация кодовой базы, предоставленная С. Текущее состояние — **рабочая система в фазе доводки**, развёрнута на VPS (не прототип; 4 применённые миграции, сервисы, репозитории, валидация). Данные тестовые, использования не было.

### 3.1 Архитектурный тип
**Модульный монолит:** один процесс, один event-loop (aiogram polling + aiohttp), одна БД, один токен, общий `User`. Два логически обособленных модуля, разделённых по UX-каналу и по модели приватности.

### 3.2 Модуль «Списки» (chat-native)
- Канал: нативные команды/кнопки в чате Telegram.
- `/start`, `/help`, `/family` — создание группы и вступление по инвайт-коду (FSM-диалог).
- `/lists` — категории и пункты с вложенностью категорий (дерево через `parent_id`, Adjacency List).
- Приватность: **семейная** (`family_id`), видна партнёру.

### 3.3 Модуль «Еда» (Mini App)
- Канал: Telegram Mini App (React-фронт + HTTP REST API, 13 эндпоинтов, фронт из 9 файлов). Самый проработанный кусок.
- Ввод тремя способами: **текст** (LLM-разбор на позиции + КБЖУ), **фото** (распознавание; с этикетки — точно, домашнее блюдо — грубая оценка с пометкой перепроверить), **база блюд** (пересчёт по граммам без LLM).
- Создание блюда в базу (текст состава / фото этикеток / комбинированно).
- Дневник по дням, навигация, редактирование/удаление, экран подтверждения позиций.
- Цели КБЖУ, прогресс-бары, недельный график, разбивка по дням, % от цели.
- Экспорт периода в Markdown. Общая база блюд (`SharedFood`) с поиском.
- Приватность: **личная** (`user_id`), партнёр не видит.

### 3.4 Инфраструктура (готова)
- aiogram polling + aiohttp (`start_web_server()`) в одном `main()`/event-loop, один деплой.
- SQLite + async SQLAlchemy + Alembic.
- Аутентификация Mini App по Telegram `initData` (HMAC по `BOT_TOKEN`).
- Whitelist пользователей (`ALLOWED_USER_IDS`).
- Глобальный обработчик ошибок с уведомлением админу в Telegram.
- Единая БД (`data/bot.db`) на VPS; таблицы еды (`food_entries`, `shared_foods`) рядом с `families`/`users`/`list_*`.

### 3.5 Чего в current-state НЕТ (пробелы относительно MVP)
- **Напоминаний** как функции — нет (LLM-слой задействован под еду, не под reminders).
- **Финансового домена** — нет вообще.
- **Сквозной аналитики/дайджеста** поверх сфер — нет (у еды своя история, единого слоя нет).
- **Метаданных, статусов и поиска по спискам** — нет.
- **Типизации списков** (фильмы, подарки, ссылки как отдельные типы) — нет.
- **Режима приватности «скрытое-от-партнёра»** — нет (модель бинарна).
- **UI вне еды в Mini App** — нет (списки сейчас в чате; по решению переезжают в Mini App, см. 5).

## 4. MVP — функциональные требования (заморожено обоими стейкхолдерами)

### 4.1 Домен «Списки» (target)
- **Канал:** Mini App (переезд с chat-native; чат остаётся только как точка входа и push).
- **Типизированные списки:** дела, покупки, идеи, фильмы, подарки, сохранённые ссылки («тестики»).
- Сохранение иерархии/вложенности.
- **Метаданные:** дата заведения, дата выполнения, статус, история изменений.
- **Поиск/выборка** по спискам и пунктам.
- **Аналитика по типу списка:** просмотренные фильмы за период, выполненные дела, динамика.
- **Приватность подарков:** список подарков для партнёра скрыт именно от него (третий режим приватности, раздел 6).

### 4.2 Домен «Финансы» (новый)
Источник истины в MVP — **существующая Google-таблица**; данные **импортируются → анализируются**. Ввод транзакций в боте в MVP **отсутствует**.

**Структура источника** (выверено по реальному файлу `Бюджет общий 2026.xlsx`, листы Март–Июнь):
- Один лист на месяц (до 12/год); **одна строка-шапка**.
- Доход и расход — **параллельные колонки** (не вертикальные блоки): доход — источник / План / Факт / Разница (источники: переход остатка, партнёры Катя/Сережа, кэшбек, прочее; ниже — сводные строки Доход / Дельта / Расход); расход — категория / План / Факт / % (доля) + **дневная матрица** дни 1–31.
- **Двухуровневая иерархия категорий** (родитель → подкатегории, напр. Едовое → ВкусВилл/Пятёрочка/Магнит…), **закодирована заливкой строки** (родитель — цветная `FFF9CB9C`, подкатегория — без заливки, «Итог» — серая). Инвариант: родитель = Σ детей по Факту (и по дням). Имена подкатегорий уникальны **в пределах родителя**, не глобально.
- Дневная гранулярность (1–31); % — доля от общего.

**Требования к аналитике:**
- **План vs Факт vs Разница** и % от общего — по категориям и в целом (отслеживание бюджета и отклонений), а не только суммы трат.
- **Иерархия:** агрегат по родителю + drill-down в подкатегории.
- **Доходы:** по источникам и по партнёрам, с учётом переходящего остатка.
- **Каденс:** день / неделя / месяц / квартал / год + **произвольный период** (квартал/год = агрегация по месячным листам).
- Дневная гранулярность доступна (суммы по дням на подкатегорию).
- Разбивка по картам сознательно **не нужна**.

### 4.3 Домен «Здоровье / Питание»
- Дневник питания, КБЖУ, цели, история — **уже покрыто** существующим модулем; превышает минимум MVP. Переиспользуется (вариант C).
- MVP-добавление: **базовые напоминания** (см. 4.4).

### 4.4 Сквозная способность «Напоминания» (пробел — строим)
- Создание / просмотр / срабатывание напоминаний.
- Сценарии MVP: витамины, бытовые задачи.
- Канал доставки: push в Telegram.

### 4.5 Сквозной слой «Аналитика и дайджест» (пробел — строим)
- Аналитика по каждой сфере в боте (списки, финансы, питание).
- **Ретро-дайджест:** сводка недавних событий/изменений по сферам (push в чат).

## 5. Нефункциональные требования
- **UX-каналы (решено):** весь интерактивный UI — в **Mini App**. Telegram-бот = точка входа (запуск Mini App, `initData`-аутентификация) и **push** (напоминания, ретро-дайджест). Существующие chat-native списки перерабатываются в Mini App.
- **Архитектурный стиль (решено):** **модульный монолит** — один процесс, одна БД, один деплой. Микросервисы, брокеры сообщений, multitenancy — вне рассмотрения (нет смысла при одном сервере и двух пользователях).
- **Готовность к отделению в standalone-приложение:** граница API держится чистой, чтобы фронт мог в будущем работать с тем же бэкендом на другой аутентификации. Под это **не оверинженерим** в MVP — только не закладываем жёсткой связки логики с Telegram.
- **Ресурсы VPS:** ~3 GB RAM, 1 CPU. Constraint в первую очередь для LLM-вызовов и конкурентности; аналитика на текущем объёме данных нагрузки не создаёт.
- **Хранилище:** SQLite сейчас; миграция на PostgreSQL запланирована (тайминг — открытый вопрос, раздел 9).
- **LLM:** Groq (free tier, `meta-llama/llama-4-scout-17b-16e-instruct`, мультимодальная — текст+фото) для разбора питания; учитывать латентность и лимиты; новые обязательные LLM-зависимости не вводить без необходимости.
- **Аутентификация:** Telegram `initData` (HMAC), whitelist на двух пользователей. Без внешней регистрации/паролей в MVP.
- **Наблюдаемость:** сохранить уведомление об ошибках админу в Telegram.
- **Локализация:** интерфейс на русском.
- **Простота как требование:** избегать преждевременного усложнения.

## 6. Модель приватности (ключевое архитектурное требование)
Текущая модель **бинарна**: семейное (`family_id`, видят оба) либо личное (`user_id`, видит один).

MVP вводит **третий режим** на примере подарков: данные принадлежат семейному контексту, но скрыты от конкретного партнёра (того, кому готовится подарок). Это центральное дизайн-решение проекта.

Поскольку данные сносятся и схема строится с нуля (раздел 10), третий режим **проектируется в модель сразу**, а не ретрофитом — стоимость и риск минимальны. В требованиях фиксируется как требование; способ реализации (флаг видимости, пара `owner` + `hidden_from`, отдельная сущность, ACL-слой) — в ADR на этапе архитектуры (раздел 9).

## 7. Границы scope (in / out)

**В MVP:**
- Списки (в Mini App): типизация, метаданные, статусы, история, поиск, аналитика по типу; приватность подарков.
- Финансы: аналитика по импортируемой Google-таблице (план/факт, иерархия, доходы), каденс D/W/M/Q/Y + произвольный период.
- Питание: существующий дневник (переиспользуется) + базовые напоминания.
- Сквозная аналитика и ретро-дайджест.

**Вне MVP → North Star (раздел 8):**
- Любая автоматизация финансов: чеки через ФНС (item-level), ввод транзакций в боте, сравнение цен, планирование закупок от еды+бюджета.
- Расширение здоровья: Huawei Health, статистика по типам тренировок, медблок (анализы, вес/рост), цикл-аналитика, каталог и расписание витаминок, напоминания о врачах, состав тела, сон.
- Фото / «воспоминания».
- Полный ассистентский день (проактивный сценарий).
- Отделение в самостоятельное приложение вне Telegram.

## 8. North Star backlog (вне MVP)

Backlog видения, не требования к разработке.

**Финансы (автоматизация):** захват чеков через ФНС (QR → позиции); ввод транзакций в боте (чек + ручной); сравнение цен по магазинам; планирование закупок от плана питания и бюджета. *Со временем заменяет ручную Google-таблицу как источник.*

**Здоровье (расширение):** интеграция Huawei Health; статистика по типам тренировок и калориям; медблок (вес, рост, анализы) + аналитика анализов; рекомендации с учётом дня цикла; каталог имеющихся витаминов + расписание приёма; напоминания о врачах; состав тела; сон.

**Прочее:** фото по темам и «воспоминания»; проактивный ассистентский сценарий полного дня; **standalone-приложение** (отделение фронта/бэкенда от Telegram, собственная аутентификация).

## 9. Вопросы фазы архитектуры

### Решено (выведено из открытых в 0.2–0.3)
- **UX-канал по доменам** → весь UI в Mini App; бот = вход + push (раздел 5).
- **Архитектурный стиль** → модульный монолит, без микросервисов (раздел 5).
- **Вычисление аналитики под VPS** → on-the-fly агрегации; предрасчёт/материализация не нужны на текущем объёме данных (преждевременная оптимизация).
- **Миграция данных** → не требуется, чистый ребилд (раздел 10).
- **Стабильность таксономии категорий** → таксономия +/- фиксирована, иногда добавляются новые строки. Следствие: категории — **управляемая расширяемая сущность** (не фиксированный enum), импорт обязан абсорбировать новые категории. Дополнительно: таблицу через несколько месяцев существенно переработают (переезд) → импорт проектируется как заменяемый адаптер (раздел 10).
- **Границы bounded contexts** → нарезка выполнена в `DOMAIN_MODEL.md` v1.0 (6 контекстов + слой доставки, граф зависимостей, маппинг на код). Открытым остаётся уровень кода — изоляция контекстов (см. Открыто, п. 4).
- **Модель видимости** → принято **ADR-0001** (Вариант A: `scope`+`hidden_from`; персистенция hidden_from — join-таблица, H3).
- **Изоляция контекстов в коде** → принято **ADR-0004** (Вариант B: пакет-на-контекст + kernel + import-linter из графа §2).

### Открытые вопросы и статусы ADR
Вынесено в единый live-трекер — `docs/03_architecture/adr/README.md` (SSOT по статусам ADR, открытым вопросам и недоспецификациям). Здесь не дублируется во избежание рассинхрона.

## 10. Допущения и решения
- Ровно два пользователя (пара), русскоязычный интерфейс.
- **Текущие данные сносятся; схема строится с нуля** — без обратной совместимости и миграций со старого формата.
- Один VPS, один деплой; **модульный монолит** сохраняется как стиль.
- **Весь UI в Mini App**; чат — вход и push.
- Google-таблица остаётся источником финансовых данных в MVP; её структура — листы по месяцам, блоки доход/расход, иерархия категорий, План/Факт, дневная гранулярность. Таксономия +/- фиксирована (иногда добавляются строки); структура таблицы **волатильна** — будет существенно переработана через несколько месяцев в связи с переездом, поэтому импорт строится как **заменяемый адаптер**, а доменная модель финансов от формы таблицы не зависит.
- Существующие рабочие модули (еда, иерархия списков) переиспользуются (вариант C); переписывается только то, что требуют новые границы и переезд в Mini App.
- Внешние интеграции (ФНС, Huawei Health) — только North Star, с отдельной проверкой осуществимости перед включением в любой будущий объём.
