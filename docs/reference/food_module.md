# Модуль «Еда» — описание функционала

Расширение `lifeManager_bot`: дневник питания с расчётом КБЖУ рядом с
существующим функционалом списков.

Документ — актуальный источник правды по модулю. Описывает **что** делаем,
**как это ложится в архитектуру** и **в каком состоянии** находится работа.

> **Ключевое решение по форме:** модуль «Еда» делается как **Telegram
> Mini App** (веб-интерфейс внутри Telegram), а не бот-нативными кнопками.
> Списки остаются на текущих inline-клавиатурах. Backend (модель, репозиторий,
> сервисы, LLM) одинаков при любом фронте — мини-апа меняет только слой
> представления.

## 2. Модуль «Еда» — функции

### 2.1 Ручной ввод (текст)

Пользователь вводит продукты и вес одной строкой:

```
гречка 200, куриная грудка 150
```

LLM нормализует строку и считает КБЖУ. Важно: **локальной базы состава
продуктов нет**, поэтому числа КБЖУ даёт только модель (regex сам по себе
извлёк бы только «название + вес», но не калории).

Одна строка → **несколько позиций** (по продукту на запись), потому что в
модели `FoodEntry` одна позиция = одно описание + вес + КБЖУ. Это удобно для
последующего редактирования отдельных продуктов.

### 2.2 Ввод по фото + описание

Сценарий «лень считать вручную»:

1. Пользователь выбирает/снимает фото (упаковка, тарелка) + опц. подпись.
2. Фото уходит в **vision-модель** с промптом «определи продукты, верни КБЖУ в JSON».
3. Модель возвращает список позиций → мини-апа показывает их и просит
   подтвердить / поправить порцию.
4. После подтверждения записи сохраняются.

> ⚠️ Точность зависит от типа еды: этикетка → хорошо, домашнее блюдо → грубо.
> Пример из теста: «гречка 200» модель посчитала как **сухую** крупу (730 ккал),
> а не варёную (~220). Поэтому **шаг подтверждения порции обязателен**.

### 2.3 История

- просмотр за сегодня / соседние дни (переключение ‹ ›) / выбранный день;
- итоги по дню (сумма КБЖУ);
- редактирование / удаление записи.

### 2.4 Выгрузка за период (вместо автоотчётов)

Автоматические ежедневные отчёты **не делаем**. Вместо этого:

1. Пользователь выбирает период (7 дней / месяц / произвольные даты).
2. Сервис формирует **структурированный markdown-дамп**: группировка по дням,
   итоги по дню, общий итог, + готовый шаблон промпта для анализа.
3. Дамп показывается в апе (с копированием) и/или отправляется файлом в чат.
4. Пользователь сам копирует его в ChatGPT / Claude для анализа.

Реализовано в `FoodService.export_period()`.

### 2.5 Цели КБЖУ, прогресс и группировка по приёмам

- **Дневные цели** (ккал + Б/Ж/У) задаются пользователем. На главном экране
  — **4 прогресс-бара** «съедено / цель» (процент + остаток). Цель не задана
  → бар показывает только съеденное, без процента.
- **Группировка дня по приёмам пищи** (завтрак/обед/ужин/перекус) с **итогами
  по каждой группе**. Порядок фиксированный, пустые группы скрываются.

Реализовано: `DayView.progress()` (4 бара), `DayView.by_meal()` (группы с
подитогами), `FoodService.set_goals()` / `get_goals()`.

## 3. Модель данных

**`FoodEntry`** (`db/models.py`) — реализованный набор полей:

| Поле           | Тип        | Назначение                                       |
|----------------|------------|--------------------------------------------------|
| `id`           | PK         |                                                  |
| `user_id`      | FK → User  | **личный** дневник (НЕ per-family, как списки)   |
| `created_at`   | datetime   | момент приёма пищи (наивный UTC)                 |
| `meal_type`    | str?       | breakfast/lunch/dinner/snack (авто по времени)   |
| `description`  | str        | название позиции («гречка»)                      |
| `weight_g`     | float?     | вес порции, если известен                        |
| `kcal`         | float      | калории — **итог за порцию**, не на 100 г        |
| `protein`      | float      | белки, г (за порцию)                             |
| `fat`          | float      | жиры, г (за порцию)                              |
| `carbs`        | float      | углеводы, г (за порцию)                          |
| `source`       | str        | `manual` / `photo`                               |
| `photo_file_id`| str?       | Telegram file_id фото (если было)                |

Ключевые отличия от списков:
- дневник **личный** (`user_id`), партнёр чужих записей не видит, уведомлений нет;
- КБЖУ хранятся **абсолютными значениями за порцию** → сумма за день = простой `SUM()`;
- границы суток считаются в `user.timezone` (хранение в UTC, перевод в сервисе).

**Дневные цели** хранятся на уровне `User` (`db/models.py`):
`target_kcal`, `target_protein`, `target_fat`, `target_carbs` (nullable Float).
NULL = цель не задана. Используются для прогресс-баров (см. §2.5).

## 4. Интеграция с LLM

Вынесено в `services/llm_service.py` за провайдер-агностичным интерфейсом.

- **Провайдер: Groq**, модель `meta-llama/llama-4-scout-17b-16e-instruct`
  (мультимодальная: текст + изображения, есть JSON-режим).
  > Изначально планировался Gemini 2.0 Flash, но ключ получить не вышло →
  > перешли на Groq (бесплатный tier, OpenAI-совместимый SDK `groq`).
- **Два режима вызова** (оба возвращают `NutritionResult` — список `NutritionItem`):
  - `analyze_photo(image_bytes, caption)` — vision-запрос (base64 data URL);
  - `parse_text(text)` — нормализация ручного ввода.
- **Контракт:** `response_format={"type":"json_object"}` → строгий JSON;
  парсинг + валидация pydantic. Невалидный ответ / 429 → понятная `LLMError`.
- **Лимиты Groq для фото:** base64 ≤ 4 МБ, до 5 изображений на запрос.
- **Ключ** в `.env` → `GROQ_API_KEY` (грузится через `pydantic-settings`).

> На будущее: интерфейс позволит подменить Groq на локальную модель
> (Ollama + Qwen2.5-VL на 4070 Super) без переписывания вызывающего кода.

## 5. Структура кода

Следуем **реальной** структуре проекта (единый `db/models.py`, плоские
`repositories/` и `services/`):

```
db/models.py                 # + FoodEntry
repositories/food_repository.py   # CRUD + выборка за UTC-диапазон
services/food_service.py     # сохранение, агрегация по дню/периоду, выгрузка
services/llm_service.py      # обёртка над Groq (vision + text)
alembic/versions/51b617b93453_add_food_entries_table.py
```

**Разделение «анализ vs сохранение»:** `analyze_text` / `analyze_photo`
только считают (без записи в БД). Пользователь подтверждает/правит позиции в
UI → затем `save_entries(...)`. Так шаг подтверждения остаётся в интерфейсе.

**Мини-апа (реализовано):**

```
web/auth.py            # валидация Telegram initData (HMAC-SHA256 по bot_token)
web/api.py             # HTTP-API на aiohttp в том же процессе/loop, что и бот
web/static/index.html  # точка входа (telegram-web-app.js + React UMD + Babel)
web/static/api.js      # слой запросов к API + initData + сжатие фото
web/static/data.jsx    # мета приёмов пищи + хелперы
web/static/icons.jsx, components-shared.jsx, screens.jsx, goals.jsx, app.jsx
web/static/styles.css  # тёмная тема (по дизайну из docs/UI макеты/)
```

Фронт — **без сборки**: React UMD + Babel-in-browser компилируют JSX прямо в
браузере (как в дизайн-прототипе), мок-данные заменены на запросы к API.
Бот поднимает aiohttp параллельно polling (`bot.py` → `start_web_server`).

## 6. Мини-апа: экраны и флоу  ← ориентир для дизайна

Список экранов и того, какие данные/действия на них. Это и есть то, что нужно
нарисовать. Тема — нативная Telegram (свет/тёмная через CSS-переменные,
`MainButton`/`BackButton`, безопасные отступы).

1. **«Сегодня» (главный)**
   - переключатель дня `‹ дата ›`;
   - **4 прогресс-бара** «съедено / цель»: ккал, белки, жиры, углеводы
     (процент заполнения + остаток до цели; без цели — только число);
   - записи, **сгруппированные по приёмам пищи** (завтрак/обед/ужин/перекус),
     у каждой группы — заголовок и **итог по группе** (ккал + Б/Ж/У);
     внутри группы: время · название · вес · ккал · Б/Ж/У;
   - кнопка **＋ Добавить**;
   - пустое состояние («записей пока нет»).

1a. **Настройка целей** — экран/модалка ввода дневных целей (ккал, Б, Ж, У);
   пустые поля = снять цель.

2. **Добавление** — переключатель **Текст / Фото**
   - *Текст:* поле ввода («гречка 200, курица 150») → кнопка «Посчитать»;
   - *Фото:* выбор/съёмка фото + опц. подпись → «Посчитать»;
   - состояние загрузки («модель считает…»).

3. **Подтверждение позиций** (после анализа)
   - список распознанных позиций, каждая **редактируема**: название, вес,
     ккал, Б/Ж/У;
   - удалить / добавить позицию;
   - выбор приёма пищи (завтрак/обед/ужин/перекус, предзаполнен по времени);
   - кнопки **Сохранить** / **Отмена**;
   - предупреждение о грубости оценки для домашних блюд.

4. **История**
   - список дней с итогами; тап на день → его записи;
   - редактирование / удаление записи.

5. **Выгрузка за период**
   - выбор периода (7 дней / месяц / произвольные даты);
   - кнопка «Сформировать» → markdown-дамп с копированием + шаблон промпта;
   - опция «отправить файлом в чат».

6. **Состояния ошибок:** недоступен LLM / превышен лимит (429) / нет ключа.

### Черновой контракт API (для согласования фронта и backend)

Все запросы авторизуются заголовком с `initData` (проверка на бэке).

```
GET    /api/day?date=YYYY-MM-DD        → итоги дня + goals + progress(4 бара) + meals[] (группы с подитогами)
GET    /api/goals                      → текущие цели КБЖУ
PUT    /api/goals                      → {kcal?, protein?, fat?, carbs?} (null = снять)
POST   /api/analyze                    → {type:text|photo, text?, image?, caption?} → items[]
POST   /api/entries                    → {items[], meal_type?, source} → сохранённые
PATCH  /api/entries/{id}               → правка одной записи
DELETE /api/entries/{id}
GET    /api/period?from=&to=           → записи, сгруппированные по дням (+ goals на каждый день)
GET    /api/export?from=&to=           → markdown-дамп
```

Форма ответа `GET /api/day` (черновик): `{ "date", "totals":{kcal,protein,fat,carbs},
"progress":{ "kcal":{consumed,target,percent,remaining}, ... },
"meals":[ {"meal_type","totals":{...},"entries":[...]} ] }`.

## 8. Открытые вопросы

Решённые по ходу backend-этапа:
- **Неизвестная порция:** модель сама прикидывает типичную порцию и проставляет `weight_g`; пользователь правит на шаге подтверждения.
- **meal_type:** авто по времени суток (5–11 завтрак, 11–16 обед, 16–22 ужин, иначе перекус), с возможностью переопределить вручную.
- **Формат выгрузки:** markdown-дамп (в чат текстом и/или файлом).
- **Цели КБЖУ:** задаются на экране целей в мини-апе (шестерёнка в шапке / CTA на «Сегодня»); пустое поле = снять цель.
- **Загрузка фото:** клиент сжимает (длинная сторона ≤ 1280px, JPEG q≈0.82) перед отправкой — укладываемся в лимит base64 4 МБ у Groq.
- **Стиль:** тёмная тема из дизайна (фиксированная палитра), не зависящая от темы Telegram.

Ещё открыты:
- **Боевой HTTPS:** trycloudflare-URL меняется при каждом перезапуске туннеля → для постоянной работы нужен домен+TLS или именованный cloudflared-туннель.

## 9. Запуск и тест мини-апы (cloudflared)

Telegram открывает Web App **только по HTTPS**. Для быстрого теста без домена —
бесплатный quick tunnel от Cloudflare (без аккаунта).

**Важно:** бот (один и тот же токен) может слушать Telegram только в одном
месте. Тестируй **на VPS** (где бот и живёт) — либо локально, но тогда сначала
останови бот на VPS.

1. **Установить cloudflared**
   - Linux (VPS): `wget https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64 -O /usr/local/bin/cloudflared && chmod +x /usr/local/bin/cloudflared`
   - Windows: `winget install Cloudflare.cloudflared`
2. **Запустить бот** — он сам поднимает веб-сервер на `127.0.0.1:8080`
   (`webapp_host`/`webapp_port` в `.env` при необходимости поменять).
3. **Запустить туннель** в отдельном терминале:
   `cloudflared tunnel --url http://localhost:8080`
   В выводе будет адрес вида `https://<random>.trycloudflare.com`.
4. **Прописать адрес** в `.env`: `WEBAPP_URL=https://<random>.trycloudflare.com`
   и **перезапустить бот** (адрес читается на старте, тогда же ставится Menu Button).
5. **Открыть в Telegram**: в чате с ботом — кнопка-меню «🍎 Еда» у поля ввода,
   либо команда `/food` → кнопка. Должен открыться дневник.

Нюансы:
- trycloudflare-URL **меняется** при каждом перезапуске туннеля → шаги 3–4 повторяй.
- Твой Telegram-ID должен быть в `ALLOWED_USER_IDS` (или список пустой) — API
  мини-апы проверяет тот же whitelist.
- Тест без Telegram (в обычном браузере) даст 401 «initData пустой» — это норма,
  авторизация требует подписанный Telegram initData.
